## 1. 玩法设计

### 1.1 一句话

> 你是一名侦察兵，带着一盏快没电的灯，在一座被雾吞掉的要塞里找回三枚信标，然后活着离开。

### 1.2 核心循环

```
活动面板 → 选中「迷雾信标」→ 右侧读规则 → 开始探索（加载条）
  → 探索：移动一格 → 视野刷新 → 迷雾揭开/回暗
  → 决策：深入 / 绕开守卫 / 投石引开 / 躲进草丛
  → 拾取信标 0/3 → 3/3
  → 撤离回入口
  → 结算：成功/失败 + 用时 + 探索率 + 评级 + 服务端排名
  → 再来一局（扣次数）/ 返回面板
```

### 1.3 胜负与数值

| 项 | 规则 |
|---|---|
| 胜利 | 集齐 3 信标后回到入口格 |
| 失败 | 被发现条满（5 层）或超时（180s / 120 回合，先到者） |
| 地图 | 40×40，房间+走廊程序生成；**每日种子**（同一天同一张图） |
| 玩家 | 视野 6 格，4 向移动，蹲伏（发现速度减半） |
| 守卫 | 3~5 个，视野 5 格 + 朝向 ±60° 扇形 + 巡逻；警觉链：可疑→搜索→追击 |
| 草丛 | 不挡视线；玩家在草丛内且距离 >1 时守卫看不见 |
| 投石 | 冷却 3 回合，指定 6 格内落点制造噪音，吸引 8 格内守卫 |
| 发现条 | 回合结束在守卫视野内 +1，脱离 -1，满 5 判负 |
| 评分 | 剩余时间 40% + 探索率 30% + 未被发现回合 30% → S/A/B/C |

### 1.4 迷雾三态（技术脊椎）

| 状态 | 玩家看到 | 数据 |
|---|---|---|
| 未探索 | 纯黑 | `explored=false, visible=false` |
| 已探索·不可见 | 压暗 55% + 去饱和的地形，**没有敌人** | `explored=true, visible=false` |
| 可见 | 全亮，敌人/血条/小地图图标全显 | `visible=true` |

三条铁律：

1. **记住路 ≠ 知道敌人现在在哪**：离开只清 `visible`，`explored` 永久保留。
2. **多源合并**：任一友军仍覆盖就不变暗；每回合先清空再重标。
3. **逻辑与表现分离**：边缘平滑只影响显示，判定永远读原始网格；模型隐藏 ≠ AI 停止。

### 1.5 操作

| 平台 | 操作 |
|---|---|
| 键鼠 | WASD/方向键移动，Q 蹲伏，E 投石，Esc 暂停/设置，Tab 小地图 |
| 触屏（后续） | 点格移动，长按蹲伏，拖到目标格投石 |

### 1.6 为什么是回合制

回合制让「视野每步重算」成为可读的节奏，单人可玩、无需服务器权威视野；实时潜行需要感知/寻路/动画状态机（工作量 ×3），迷雾战棋 PVP 需要匹配与服务器防透视（超出本期）。

### 2.3 Lua 页面骨架（示意）

```lua

    pageFogHunt = ui.NewRect(parent, "FogHuntPage")
```

### 2.4 进入与返回

```
点击开始 → MiniGameBridge.EnterFogHunt()
  → 关活动面板（UIManager.Close(UIType.ActivityView)）
  → 先问服务端 StartMiniGameRun(activityId)
      · 无次数 → toast「今日次数已用完」
      · 有次数 → 返回 seed + 剩余次数
  → SceneLoader.LoadAsync("fog_hunt")   // 加载条复用
  → 局内 → 结算 → SubmitMiniGameResult → 显示排名 → 返回 zhuye（重新打开活动面板可选）
```

## 3. 服务端设计（次数 + 排行）

### 3.1 次数

| 项 | 设计 |
|---|---|
| 表 | 新表 `activity_run`（player_id, activity_id, day, used）或复用活动模块计数表 |
| 规则 | 每日 3 次（可配置），`StartMiniGameRun` 时原子 +1；未完成也算一次 |
| 协议 | `StartMiniGameRunRequest{activityId}` → `StartMiniGameRunResponse{success, remainCount, seed}` |
| 防作弊 | 服务端只信「开局/结算」配对，单局时长下限校验（< 20s 视为异常） |

### 3.2 排行

| 项 | 设计 |
|---|---|
| 榜单 | 复用 `LeaderboardRepository`，新增 `challenge_id = 3`（迷雾信标），加入 `KnownChallengeIds` |
| 分数 | `score = 评级分×10000 + 剩余时间秒×10 + 探索率`（越高越好，整数） |
| 协议 | `SubmitMiniGameResultRequest{activityId, score, timeMs, explored}` → `{best, rank, newRecord}`；榜单查询复用现有 `LeaderboardRequest(challengeId=3)` |
| 展示 | 结算页显示「我的最佳 / 当前排名 / Top3」 |

> 现有的 `SubmitScore` / `GetLeaderboard` 已经做了 MySQL + Valkey 双写与 TopN，**不需要新写排行榜**，只要注册第 3 个榜单 + 一个分数换算。

## 5. 技术方案：战争迷雾

### 5.1 数据

```csharp
byte[] cell;      // 每格 2bit：bit0 explored，bit1 visible
bool[] blocked;   // 墙/岩石：挡视线也挡移动
byte[] cover;     // 0=无，1=草丛（不挡视线，提供藏身）
int width = 40, height = 40;
```

### 5.2 每回合重算

```csharp
void Recalculate()
{
    ClearVisible();                        // 只清 visible
    foreach (var src in sources)           // 玩家 + 可扩展的侦察技能
        MarkSight(src.cell, src.radius, src.facing, src.fov);
    // explored |= visible 在 MarkSight 内顺便写
}
```

### 5.3 视线

```csharp
bool HasLineOfSight(Vector2Int from, Vector2Int to)
{
    foreach (var c in Bresenham(from, to))
        if (c != to && blocked[c]) return false;
    return true;
}
```

玩家：半径 6 + LOS；守卫：半径 5、±60° 扇形 + LOS；玩家在 `cover` 且距离 >1 → 不可见。草丛/高低地/技能规则只加在这一层。

### 5.4 渲染

```
FogGrid --每回合--> Texture2D(R8, 40×40) --> Material(_FogMask) --> 全屏 Quad（跟随相机）
```

| 状态 | shader |
|---|---|
| 未探索 | 纯黑 alpha 1 |
| 已探索不可见 | 黑 55% + 去饱和 |
| 可见 | alpha 0 |

`filterMode=Bilinear` + shader `smoothstep` 做边缘柔和；判定永远读 `bool` 网格。平滑开关只换采样，不改数据。

### 5.5 显隐规则

敌人模型 / 血条 / 意图图标 / 小地图图标：只在 `visible` 时显示；`explored` 只画地形。敌人 AI 照常运行。

### 5.6 性能

40×40×6 源 ≈ 9600 次格判定/回合（<0.3ms）+ 1600 字节贴图上传（<0.1ms）；回合制无逐帧开销。

### 5.7 联网注意

本期是单机玩法 + 服务端只存分数/次数，不涉及实时同步；若以后做对抗，视野必须服务端过滤（视频最后一条），客户端只做表现。

## 8. 风险与对策

| 风险 | 对策 |

| Lua 热更包与服务端活动配置不一致 | 活动 `ContentVersion` 与包版本绑定；发布脚本 `ActivityPackagePublisher` 一起升版本 |

### 10.3 关键实现备忘（踩过的坑）

1. `FogHuntHud` 的所有面板/文本必须挂在 Canvas 的 `RectTransform` 下；挂到 HUD 自身 `transform` 会导致 `children=0` 且完全不渲染。
2. 工程 `UICameraService.SweepAll()` 会每秒把 `ScreenSpaceOverlay` 画布强制转成 `ScreenSpaceCamera` 并绑到 `UICamera`、整棵子树改 UI 层；它同时会把 UI 相机注册进世界相机的 stack，所以运行时**不要**跟它抢 Canvas 模式。
3. `ActivityUi.NewLabel` 原本只有 6 参/12 参重载，Lua 用 4 参会得到 `nil` 且后续节点静默不创建；已加 4 参重载，并**必须重跑 `XLua/Generate Code`** 才在 Lua 侧生效。
4. `ActivityPackagePublisher.BuildAndPublish()` 在 Play Mode 调用会失败（SBP 的 `SceneStateCleanup` 禁止），且 `TaskPrepare` 会先删包目录；发布前一定先退 Play。
5. 活动内容默认走 `LuaActivityHost.UseHostPlayMode=true`，从 8899 拉热更包；**只改工程内 Lua 不生效**，必须重新构建发布活动包并把 `activity.version` 指到新版本。
6. `manage_input` 的 `key_press` 走 Input System 虚拟设备，legacy `Input.GetKeyDown` 读不到；自动化驱动本游戏要用 HUD 按钮点击。
7. 服务端 `LeaderboardRepository.MaxScore = 1_000_000`，分数公式必须压在该上限内（`评级分×100 + 剩余回合 + 探索率`）。
