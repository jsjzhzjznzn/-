## 0. 一分钟电梯演讲

> "我做了一个 Tuanjie 客户端 + .NET 8 服务端的**双端全栈游戏项目**，协议层用 protobuf，落盘 MySQL（聊天消息用 MongoDB，排行榜实时层用 Valkey）。业务上实现了登录注册、心跳保活、背包、邮件、聊天、好友、任务、叙事任务、副本掉落、Lua 热更活动与抽卡、排行榜共 11 个系统，消息号按业务段位划分（10xx 登录、24xx 背包、28xx 副本、30xx 心跳……）。
>
> 架构上我最想讲的三个点：**第一，信任边界**——所有玩法系统都遵循'客户端只报事实、服务端裁决结果'：副本客户端只上报'杀了哪类怪'，掉什么由服务端规则表决定；任务进度由服务端读背包实时重算，客户端篡改镜像会被全量快照覆盖。**第二，并发正确性**——背包/邮件领取/抽卡这类'多表多行'写操作全部走'每玩家写锁 + 单事务 SELECT FOR UPDATE + 守卫式 UPDATE 核对受影响行数'，放不下的奖励同事务转溢出邮件，杜绝双重发放。**第三，一致性降级设计**——排行榜 MySQL 真相层 + Valkey 实时层双写（`GREATEST` 与 `ZADD GT` 同语义），Valkey 宕机时成绩仍入账、查询自动降级直查索引并可重建缓存。
>
> 客户端侧我也做了不少深挖：聊天乐观发送用 FIFO 在途队列配对回执、副本万级掉落用 DrawMeshInstanced + GPU Compute 小地图（tiled 分块把成本从 O(全标记) 降到 O(本 tile)）、活动 UI 用独立 LuaEnv 热更并处理了'Lua 回调栈内销毁虚拟机导致 SIGSEGV'的原生崩溃问题。这些在后面的章节都有源码级细节。"

## 1. 总体架构

### 1.1 三端结构与协议同源

```
                 ┌────────────────────────────────────────────┐
                 │        protobuf\protos\  (11 个 .proto)     │
                 │  MessageID.proto 统一登记全部消息号          │
                 │  build_proto.bat: protoc 33.1 → C#          │
                 └───────┬────────────────┬───────────────────┘
                         │ 一次生成三处同步  │
        ┌────────────────▼──┐        ┌────▼─────────────────────┐
        │ Tuanjie 客户端     │  TCP   │ competeserves 服务端      │
        │ RedDotSystem-main │◄──────►│ .NET 8 控制台 :8888       │
        │ Assets\Scripts\   │        │ Server\                  │
        │  Generated\ 协议副本│        │  Generated\ 协议副本      │
        └───────────────────┘        └──────────┬───────────────┘
                                                 │
        ┌───────────────────┐        ┌───────────▼───────────────┐
        │ TestClient (控制台)│        │ MySQL(compete 库) +        │
        │ 同一帧格式的假客户端│        │ MongoDB(聊天) + Valkey(排行)│
        └───────────────────┘        └───────────────────────────┘
```

- **协议三处同步**：`protobuf\output\csharp\` 共享产物 → `RedDotSystem-main\Assets\Scripts\Generated\` 客户端副本 → `competeserves\Server\Generated\` 服务端副本。改协议只改 .proto 跑一次 `build_proto.bat`，双端 C# 类型同源，杜绝手写序列化不一致。
- **命名空间约定**：消息体在 `Common.Network`（proto package `common.network`），消息枚举在 `Common.Enum.MessageID`。
- 一个值得在面试里提的细节：**MessageID.proto 单独放在 `common.messageid` package**。原因是 protoc 生成的 C# 里，枚举值 `LoginRequest` 与 message 类型 `LoginRequest` 若在同一命名空间会按 C++ 作用域规则冲突，单独 package 隔离掉——这是"踩过坑才知道"的设计。

### 1.2 MessageID 段位规划（工程化加分点）

| 段位 | 业务 | 段位 | 业务 |
|---|---|---|---|
| 1001/1002 | 登录 | 2401–2412 | 背包 |
| 2001/2002 | 注册 | 2501–2511 | 任务 |
| 2103–2112 | 好友/玩家查询 | 2601–2615 | 邮件 |
| 2201–2205 | 聊天 | 2701–2710 | 叙事任务 |
| 2301–2304 | 排行榜 | 2801–2804 | 副本 |
| 2901–2914 | 活动/抽卡 | 3001/3002 | 心跳 |

编号规律：**请求为奇数（或较小号），响应 = 请求 + 1**；推送独占段尾（如 2511 任务进度推送、2611 邮件收件通知、2710 叙事状态快照、2911 活动变更全服广播）。按百位分模块，加新系统直接开新段位，永不冲突。

### 1.3 身份模型：会话绑定，请求不带 ID

所有 Request 消息体里**一律没有 player_id / sender_id 字段**。身份来源唯一：登录成功时 `SessionManager.TryBindPlayer` 把 `session.PlayerId` 绑定到 TCP 会话（`ClientSession`），之后每个包处理时服务端从 `session.PlayerId` 推导"你是谁"，未登录（PlayerId<=0）直接拒绝。

> **面试话术**："这是结构性防伪造——客户端连'谎报自己是谁'的机会都没有，不是靠校验挡住的，而是协议面上根本表达不出来。同理 `ChatSendRequest` 刻意不含 sender_id 字段。登录时还会做单点登录：同 playerId 已有在线会话则拒绝，回'该账号已经在线'。"

## 2. 网络基建：帧格式、登录、注册、心跳、重连

### 2.1 帧格式与粘包/半包

```
[4字节 小端长度头] [4字节 消息ID] [protobuf 消息体]
  长度头 = 4(消息ID) + 体长，不含自身；校验 4 ≤ length ≤ 1MB
```

两端接收逻辑对称（客户端 `ClientNetworkManager.ReceiveLoop` / 服务端 `ClientSession.ReceiveLoop`），都是**两段式精确读取**：先读满 4 字节长度头 → 校验上界 → `ReadExactly` 读满 length 字节。长度上界 1MB 同时是防内存耗尽的护栏（恶意大帧直接断）。

发送侧：客户端 `SendRawAsync` 用 `SemaphoreSlim(1,1)` 串行化写入——两个协程同时发包时，A 的 header/body 不会被 B 的包插队交错。TestClient 用 `lock(sendLock)` 达到同一目的。

**坏包即断线**：客户端 `HandlePacket` 里 protobuf 解析抛异常 = 字节流已经失步（帧边界不对了，后续全是脏数据），此时无法逐包恢复，直接 `Disconnect()`。这是"TCP 流式协议里解析失败不可恢复"的正确处理，面试常考。

### 2.2 客户端网络管理器（ClientNetworkManager.cs）

- **单例 + 跨场景**：`[RuntimeInitializeOnLoadMethod(BeforeSceneLoad)] Bootstrap()` 自建 GameObject + `DontDestroyOnLoad`。登录成功从 login 场景跳 `zhuye` 主界面时，连接、`MyPlayerId`、全部事件订阅不丢失——这就是"Play 即登录、登录后跳主界面"的机制底座。
- **收发线程模型**：后台线程 `ReceiveLoop` 只拆帧入 `ConcurrentQueue<byte[]>`；主线程 `Update()` 每帧最多取 **64 包**做 `HandlePacket`（一个按 MessageID 的大 switch，`XXX.Parser.ParseFrom(body)` 解析后触发对应 C# event，全工程约 40 个事件）。限 64 包是**帧预算思想**：防止某帧收到洪峰推送把主线程卡成一帧一 GC 尖刺。
- 状态文本走独立 `statusQueue`、连接事件走 `mainThreadActions` Action 队列，保证所有 UI 回调在主线程。
- **断线重连**：`ReconnectLoopAsync` 指数退避（基数 1000ms，`1<<attempt`，封顶 15000ms，最多 10 次）；重连成功后若内存里缓存了 `cachedAccount/cachedPassword` 则自动 `SendLogin` **静默恢复会话**。凭据仅内存驻留，不落盘。

> 注意：README 里提到的 `CompeteLoginUI.cs` 是早期版本，现已拆分为 `LoginSceneController.cs`（登录：非空校验→未连则 `ConnectAsync(127.0.0.1:8888)`→`SendLogin`→成功跳 zhuye）与 `SignupController.cs`（注册：两次密码一致校验、账号重名提示，面板与登录面板互斥切换）。面试讲架构演进时用得上一句："登录 UI 从运行时纯代码创建演进为场景内 Controller，网络层保持不变。"

### 2.3 服务端 TCP 模型（SocketServer / ClientSession / SessionManager）

- **纯异步、无独立线程池**：`TcpListener.AcceptTcpClientAsync` 的 Accept 循环（`Lazy<T>` 单例），每连接设 `NoDelay=true`（游戏协议小包多，Nagle 必关）→ `new ClientSession` → `SessionManager.TryAdd`（**MaxSessions=100 超限直接拒绝**，容量护栏）→ `session.Start()` 起一条 async 接收 Task。整个进程 = 1 个 Accept 循环 + N 个会话异步 Task。
- **消息分发**：`MessageHandler.Handle(session, messageId, body)` 大 switch。登录/注册留在本类，其余路由到 `FriendHandler / ChatHandler / LeaderboardHandler / QuestHandler / MailHandler / NarrativeQuestHandler / DungeonHandler / ActivityHandler` —— 一个类只当路由器，业务各自内聚，符合"开闭原则的最小实践"。
- **异常熔断**：接收循环连续错误 10 次才退出，避免偶发异常杀死会话服务。
- `ClientSession.Close()` 用 `Interlocked.Exchange(ref closed, 1)` 保证**幂等关闭**（超时、断线、踢线多路径都会调 Close，只生效一次），关闭时从 SessionManager 移除并 `PlayerManager.RemovePlayer`。

### 2.4 心跳设计（3001/3002）

```protobuf
PingRequest  { int64 client_ms }               // UTC 毫秒
PongResponse { int64 client_ms; int64 server_ms } // 原样回带 + 服务端时钟
```

- 客户端每 **15s** 发 Ping；`ReceiveTimeoutSeconds=45`（≈容忍两次心跳丢失+往返），超时视为断线走重连。
- `client_ms` 原样回带可算 **RTT**；`server_ms` 可校准服务端时钟——**副本掉落过期、活动倒计时、任务限时全用服务端 UTC 毫秒**，客户端本地时钟一律不可信，这是防"改本地时间刷活动"的第一道闸。
- 服务端**不主动踢人**，而是惰性超时：`recvCts.CancelAfter(60s)`，每收到完整帧 `TryReset`。客户端 15s 心跳保证 60s 内必有帧，僵尸连接超时后 `ReadAsync` 抛 `OperationCanceledException` → Close。
- **面试深挖点**：为什么服务端不自己发心跳？——服务端主动 ping 需要每会话定时器；CancellationTokenSource 重置方案零定时器、代码最简，靠"客户端必然周期性有包"的契约实现同等效果。真实项目还会讨论：心跳带序号做应用层保活 vs TCP keepalive（OS 级、默认 2 小时、不可靠）、以及"心跳风暴"问题（万人服每 15s 全量 ping 的 QPS）。

### 2.5 登录鉴权与存储

- `AccountRepository.Login`：参数化 SQL `SELECT Id FROM accounts WHERE Account=@Account AND Password=@Password`，失败统一回"账号或密码错误"（不区分"用户不存在/密码错"，防账号枚举）。
- 注册：先查重（"该账号已被注册"）再 INSERT，靠 `UNIQUE KEY UQ_Account` 兜底并发双注册——**查重是体验，唯一索引才是正确性**。
- 连接参数全走环境变量 `CS_DB_HOST/PORT/NAME/USER/PASSWORD`，凭据不落代码。
- ⚠️ **密码目前是明文比对**（代码注释自认学习项目取舍），改进方案见[第 14 章]，面试被问到要主动承认并给出 PBKDF2/bcrypt/argon2 + 恒定时间比较的答案。

### 2.6 TestClient（控制台假客户端）
与双端同一帧格式的顶级语句程序：后台 ReceiveLoop 大 switch 打印回执、15s 心跳 Task、命令行开关驱动协议（`--register / --chat / --friend-add / --mail / --dungeon-kill / --gacha / --activity-rotate / --listen / --autoreply`）。价值：**不依赖 Unity 即可端到端验证服务端协议与 60s 空闲回收**，`--autoreply` 让两个 TestClient 互发消息形成闭环测试。面试可引申："这就是最朴素的机器人/压测客户端雏形，扩展成多连接并发即负载测试。"

## 3. 背包系统

### 3.1 协议（2401–2412）

- `BagSlotInfo{slot_index, item_id, count}`、`ItemConfigInfo{item_id, name, item_type, rarity, icon_key, desc, max_stack}`
- 请求族：`BagList / Use(slot_index,count) / Discard / Tidy / Swap(from,to) / Grant(item_id,count)` 各带 Response。

### 3.2 核心设计：服务端权威 + 快照整表替换

**服务端只下发非空槽、任何写操作的回执都带操作后的完整槽位快照；客户端整表替换、不做本地预测。**

- 客户端 `BagManager`（单例，`[RuntimeInitializeOnLoadMethod]` 自举 + DontDestroyOnLoad）持两份缓存：定长 `slots[Capacity]`（**数组下标即槽位号**，天然对齐服务端 slot_index）与 `configs`（itemId→配置的字典）；对外只有 `BagUpdated / StatusChanged` 两个事件。
- `OnLoginResponse` 时先**清空缓存**（防上一账号数据串到当前账号），登录即 `RequestBag()`。

> **面试权衡题：为什么整表快照而不做增量 diff？** 500 格非空槽 protobuf 序列化也就 KB 级，带宽换的是：① 正确性——永远不可能出现"客户端预测与服务端裁决不一致"这种最难查的 bug；② 代码量——客户端没有任何预测/回滚/对账逻辑。真实大厂项目格子多到几万（如存储盒）才会考虑增量 + 版本号。**能说出"我知道什么时候该换增量"比"我会增量"更加分。**

### 3.3 服务端并发控制（本系统最硬核的部分）

`BagRepository`（711 行，`player_items` 表主键 `(player_id, slot_index)`）：

**所有写操作 = 每玩家写锁 + 单事务：**

```
PlayerWriteLock.Acquire(playerId)          // 进程内同玩家写串行化
  BEGIN TRANSACTION
    LockPlayerRow(accounts 主行 FOR UPDATE) // 玩家级"意图锁"
    LoadSlotsForUpdate()                    // SELECT ... FOR UPDATE 锁全部槽位行
    内存修改（Use 扣减 / Swap 交换 / Tidy 压缩 / Grant 堆叠+找空槽）
    SaveSlots()                             // 整表 DELETE + INSERT 回写
  COMMIT
```

- 为什么用 `PlayerWriteLock`（应用层锁）还要 `FOR UPDATE`（数据库锁）？——应用层锁让**同进程的并发写**直接排队、快且省事务冲突；FOR UPDATE 兜住**多进程/多实例部署**时的跨进程竞争，还保证同一事务里"读到的就是要改的"。两层各司其职，不是重复。
- "整表 DELETE+INSERT 回写"看似粗暴，实际在玩家行锁内是**最简单且不易错**的全量落账方式；行级量小（≤500），面试可顺带讨论 UPSERT/差量更新的替代与权衡。

### 3.4 与任务/邮件的联动（事件漏斗）

Use/Discard 成功后调 `QuestHandler.RaiseItemChanged(playerId, itemId)` → 收集类任务进度按**实时持有量**重算（用掉物品进度会回退）；Grant 成功调 `RaiseItemGained`（累加生涯计数 + 推任务进度通知）。**背包是任务系统的数据源**，这个联动在 7.3 详细讲。

### 3.5 客户端 UI（BagUIController，750 行只管渲染）

- 500 格 = 84 行 × 6 列，用 `VirtualScrollList` 行池虚拟化，`BindSlotRow` 换绑——**只渲染视口行**，这是 UI 列表性能的标准答案。
- 拖拽换位：拖影 `dragGhost` + `EventSystem.RaycastAll` 找落点；空槽上的拖拽**重定向给 ScrollRect**（`RedirectDragToScroll`），解决"UGUI 里 RaycastTarget 挡住父级滚动"的经典冲突。
- 池化点击一律"索引反查"（字典记录行→数据下标），闭包不捕获数据——防池化复用后旧闭包读到过期数据。

## 4. 邮件系统

### 4.1 协议（2601–2615）

`MailInfo{mail_id, title, body, sender_name, create_time_ms, expire_time_ms, read, claimed, items}`；操作族 List/Read/Claim/Delete/Grant + `MailReceiveNotify(2611 在线推送)` + `MailPublicGrant/Revoke(2612–2615 运营邮件)`。**所有时间戳都是服务端 UTC 毫秒。**

### 4.2 领取附件 = 教科书级事务（防重放 + 原子性）

`MailRepository.Claim` 单事务：

```
FOR UPDATE 锁邮件行
→ 校验链：已删除? → 已过期? → 公共邮件已撤回? → 无附件? → item_mask != 0(已领过)?
→ 内存模拟背包发放：整个背包一起放得下吗？
     放不下 → 整单拒绝（绝不部分发放）
     放得下 → item_mask = (1<<n)-1，state |= 已读 → COMMIT
→ 成功后逐物品 RaiseItemGained 联动任务
```

- **`item_mask` 位掩码防重放**：领取状态直接编码在邮件行上，重复领取在锁内被 `item_mask != 0` 挡掉——幂等性靠数据库状态而不是客户端自觉。
- **"整单要么全给要么不给"**：避免"发了 3 件里 2 件、第 3 件丢失"的半成功态，放不下的走溢出邮件（见 12.4 统一模式）。

### 4.3 公共邮件的"延迟创建 / 读时裂变"（最值得面试深挖的设计）

运营要给全服发一封带附件的邮件，朴素做法是全服 INSERT N 行（百万玩家 = 百万行写放大 + 撤回要扫全表）。本项目做法：

- `public_mails` 全局表只存**一封**；`player_public_mail` 去重表记录谁已实例化。
- 玩家**拉列表时** `SyncPublicMails(playerId)`：按"有效 + 未过期 + 未实例化 + 注册时间窗口(min/max_register_ms)"把公共邮件**裂变**进个人邮箱（个人箱满则留到下次）。
- 撤回 = 按 tag 软标记 `state=2`；未领附件的已实例化邮件在**读/领取路径**被拒绝。
- `min/max_register_ms` 窗口让运营能给"某时间段注册的玩家"定向发（新服补偿邮件的标准需求）。

> **面试话术**："这是把'写扩散'改成'读扩散+惰性物化'：成本从 O(全服人数) 的一次性写，摊成 O(活跃玩家) 的按需写；可撤回性靠发件方状态 + 领取路径二次校验。代价是领取时要多查一次公共表状态——用可控的读放大换写放大和撤回能力。"

### 4.4 客户端与红点

`MailManager` 缓存 `mails + mailsById`；`NotifyMailsChanged()` 是唯一出口（刷红点 + 广播）。红点写**叶子** `MailSystem(Key8)`，由红点树自动汇总到邮箱入口 Key5。登录成功即 `RequestMails()`——**面板没开角标也亮**（微信式未读）。点开邮件立即发 MarkRead（服务端幂等），红点即时灭；领取成功**静默 `BagManager.RequestBag()`** 重拉背包保证两处口径一致。

## 5. 聊天系统

### 5.1 协议（2201–2205）与两个字段设计决策

`ChatMessageItem{message_id(string), sender_id, receiver_id, content, sent_at_ms, read, content_type}`

- **message_id 是 string**：消息落 MongoDB，`ObjectId` 是 12 字节，塞不进 int64——类型被存储选型倒逼，面试讲得出这个因果就是真实经验。
- **content_type**：0=文本 1=表情。选 0 做默认值是 proto3 语义红利——老数据没有该字段，反序列化天然为 0（文本），**向后兼容零迁移**。表情消息 content 只存"贴纸键"不存图，客户端本地资源表解析。
- `ChatSendRequest{target_id, content, content_type}` 无 sender_id（结构性防伪造，见 1.3）。

### 5.2 服务端：隐私分层 + 敏感词 + 转发模型

`ChatHandler.HandleChatSend` 三层递进：

1. 会话身份推导发送者；
2. `FriendRepository.AreFriends` 好友准入（非好友不能发）；
3. `ChatRepository` 内部 `BuildConversationId` 把两 ID **归一化为 "小_大"**，方法签名不暴露 conversationId——调用方永远拼不出别人的会话键，隐私边界在类型系统层面。

- **敏感词** `BannedWordFilter`：干扰字符归一化 + 位置映射后打码，**打码不改长度**——这样打码前的长度校验对打码后依然成立（否则"插入 * 撑爆长度"是漏洞）。词库热加载自 `Config/banned_words.json`。
- **转发 ≠ 广播频道**：回执 Echo 给发送方自己；`SessionManager.GetSessionByPlayerId(targetId)` 命中在线收件人则推 `ChatReceiveNotify`，**离线只落库**，等对方拉历史。这是 1v1 私聊模型（好友聊天），不是世界频道。
- **拉历史即已读**：`MarkConversationRead` 一次 UpdateMany；倒序 limit 取最新再 Reverse 正序下发（利用索引取最近 N 条）。
- **Mongo 熔断不静默丢消息**：`SaveMessage` 失败返回 null → 回执失败 → 客户端**回滚乐观消息**。宁可让用户看到发送失败，不可假装成功。

### 5.3 客户端乐观发送（全工程唯一一处本地预测）

聊天对延迟最敏感，是全项目唯一破例做乐观 UI 的地方：

```
发送 → 立即以 pending_N 临时ID上屏（气泡秒出）→ inflight FIFO 队列登记
     → 回执按发送顺序到达（TCP 有序 + 服务端按会话串行处理）
     → Echo 到达：与队头配对，原位替换（校准真实 message_id/时间戳，不闪烁）
     → 失败：移除气泡 + SendFailed 事件
断线 OnConnectionBroken：全量回滚在途 pending（防永久卡"发送中" + 防队列错位）
```

> **面试深挖**："为什么 FIFO 配对是安全的？"——依赖两个前提：**TCP 保证同一连接字节有序**，**服务端每会话一条接收 Task 串行处理**（不存在会话内两包并发乱序回执）。若哪天改成多路复用/QUIC/服务端并发处理，这个配对立刻失效，要换成客户端携带 client_msg_id 显式配对。能主动说出前提和失效条件，就是分布式基本功。

### 5.4 表情（贴纸）系统

- `StickerCatalog`：**约定式扫描** `Resources/biaoq` 目录——丢一张图进目录就多一个表情，零代码注册；`键_NNN` 正则归帧（序列帧），`sticker.txt` 声明 fps。
- `StickerAnimation`：池化气泡、显式 Play/Stop、用 `unscaledDeltaTime` 计时（暂停面板不影响表情），**掉帧对齐不补播**（动画落后太多直接跳最新帧，不疯狂快进）。

## 6. 好友系统

### 6.1 协议（2103–2112，定义在 LoginPacket.proto）

`FriendList`（响应含 `online` + `unread_count`）、`QueryPlayer(2105)`、`FriendAdd(2107)`、`FriendRespond(2109, from_player_id + accept)`、`FriendRequests(2111)`。

### 6.2 服务端：双向两行 + N+1 压缩

`friendships` 表**双向两行方案**：A→B、B→A 各存一行，`UNIQUE KEY(OwnerId, FriendId)` 防重复申请，`Status 0=待同意 / 1=已同意`。

- 同意 = 申请行置 1 + **事务内补插反向行**；拒绝 = 删行。
- 对比"单行 + 方向字段"方案：两行方案查询永远是 `WHERE OwnerId=我`，**索引友好、无 OR 条件**，读多写少的关系数据这正是对的取舍（写时多插一行、事务内完成保证原子）。
- 同意后对**双方** `RaiseGameEvent(GoalTypeAddFriend)`——离线方也推进任务进度（服务端事件落库不依赖在线）。

`HandleFriendList` 两个性能点：

1. **在线状态查内存** `PlayerManager`（会话即在线，不查库）；
2. **未读数一次聚合**：`ChatRepository.CountUnreadBatch` 用一次 Mongo Aggregate 把 N 个好友的未读全部算出——**消灭 N+1 往返**（逐个好友查未读 = 打开面板打 N 次数据库）。

### 6.3 客户端：动态红点叶子（微信式未读角标）

- 好友未读红点用**运行时动态叶子**：`FriendKey(id) = (ERedDotKeyType)(100000 + id)` 挂到好友入口 Key14 下面。`100000+id` 的编码让动态键永不与配置表静态键冲突。
- 正在查看的会话不计数；打开会话即清零；**登录时 `RemoveChildNode` 摘掉旧账号的动态节点**防串号。
- 批量写红点用 `BeginBatch/EndBatch` 包裹（try/finally 配对）——批量模式下父节点只在 End 时统一重算一次，既防红点闪烁又防中途异常导致批量模式卡死、父节点永久停更（陈旧红点 bug 的根源与修法，面试好素材）。
- UI：`FriendUIController`（1409 行）好友+聊天一体，三页左栏 + 右栏聊天；聊天虚拟列表**变高行、按我方/对方双池**（`GetPoolKey = IsFromMe`），气泡高度用隐藏 `measureText` ForceMeshUpdate 测量并按 MessageId 缓存（测一次终身复用）。QQ 式细节：输入框自动增高（40–220 clamp）且消息区底边联动让位、光标跟随只在 caret 变化时滚（用户手动上翻不被弹回）。

## 7. 任务系统（服务端权威 25xx）

项目里有**两套并行任务体系**，这是面试讲"架构分层"的绝佳案例：25xx 是服务端权威的"玩法任务"，27xx 是叙事框架的任务，权威模型、协议段、存储表完全独立（见第 8 章）。

### 7.1 数据结构与状态机

```
PlayerQuestInfo{quest_id, state, progress}
state: 0 未接取 → 1 进行中 → 2 已完成待提交 → 3 已提交
goal_type: 1 挑战分数 / 2 收集物品 / 3 加好友 / 4 发消息 / 5 章节 / 6 生涯统计
```

- `QuestCfgInfo` 带 `prev_quest_id`（前置链）与 `parent_quest_id`（章节归属），服务端 `AppendChapterTree` 让一次推送包含**整棵章节树**，`topLevelOrder / stepsByChapter` 两级索引支撑"章节→步骤"展示。
- 章节 FSM：`AdvanceChapter` 按已提交步骤数推进章节状态、`AcceptNextStep` 自动开启下一步。

### 7.2 客户端：纯镜像层，零预测

`QuestManager`（单例自举）只做两份缓存（configs + quests）+ 事件广播。**Accept/Submit/Abandon/GmComplete 全部只转发网络请求，不做任何本地状态变更**；成功回执整表替换 `ApplyQuests`，失败仅发文案事件。

**红点联动**：`NotifyQuestsChanged()` 唯一出口 → `RefreshRedDot()`：`RedDotKeys.QuestEntry(Key16) = Set(可接取数 + 可提交数, Number)`。红点树自动把它汇总到更上层入口。提交成功后还会静默 `BagManager.RequestBag()`——背包变化又经服务端 `RaiseItemChanged` 反推收集任务进度，**闭环**。

`QuestUIController` 是标准 View：订阅事件、`VirtualScrollList` 变高行三段分类渲染，`RankOf()` 排序"可提交→进行中→可接取→未解锁→已完成"。

### 7.3 服务端：防作弊的进度裁决（本章核心）

`QuestHandler` 对全玩法开放**事件漏斗**——背包使用/发放、聊天发消息、好友添加、排行榜挑战、副本掉落、邮件领附件，全部汇进这几个入口：

```
RaiseGameEvent / RaiseItemChanged / RaiseChallengeScore /
RaiseMessageSent / RaiseItemGained / RaiseCareerDelta / RaiseCareerMax
```

**收集类任务的进度根本不存"累计值"，而是提交时实时算**：

- `LoadItemTotals` 直接聚合 `player_items` 当前持有量 → **玩家用掉/丢弃交付物，任务会从"可提交"回退**。进度不是计数器而是谓词，改不了。
- `HandleQuestSubmit` 全流程在一个事务内（复用 3.3 的背包锁机制）：`FOR UPDATE` 锁任务行 + `LockPlayerRow` + 锁内重读实时持有量校验 + 扣交付物 + `GrantIntoSlots` 发奖 + **守卫式 UPDATE**（`SET state=3 WHERE state <> 3` 且核对受影响行数，0 行整单回滚）→ 杜绝并发双重发奖。
- **奖励背包放不下 → 同事务 `MailRepository.InsertOverflowMail` 转邮件**，和抽卡溢出共用一个模式（注释里写着"DNF 云幂罐子教训"——奖励丢失是玩家可感知的最高优先级事故）。
- 成就类（career）进度实时读 `career_scores` 表，**只增不减、最高分取 max**；"提交任务数/获得物品数"的统计写在 Repository 层，保证手动提交/自动提交两条路径口径一致。
- 配置缓存：`quest_config` 带 10 秒 TTL 的不可变快照，`Interlocked` 原子发布——改配置 10 秒内生效，不用重启。

> **面试话术**："任务系统我没有让客户端上报'进度+1'，而是客户端只上报'我做了接取/提交这个动作'，进度由服务端从自己的数据（背包、生涯表）推导。这样玩家开修改器改客户端数字毫无意义，因为那个数字只是镜像。"

## 8. 叙事任务系统（事件上报 27xx）

### 8.1 与 25xx 的分工（两套体系并存的合理性）

| | 25xx 玩法任务 | 27xx 叙事任务 |
|---|---|---|
| 权威 | 服务端裁决进度/状态 | "客户端报事、服务端裁决"，进度在叙事引擎 |
| 目标类型 | 物品/社交/挑战等数值谓词 | 杀敌/拾取/进区域/对话事件（graph+eventKey 匹配） |
| 存储 | player_quests（state+progress） | mm_player_quests（**progress_json 全量快照** + expire_time_ms） |
| 载体 | 任务面板 | Mm-DialogSystem 对话框架（鸣潮式分工） |

### 8.2 事件桥：只转发、不推进

`MmQuestServerSync`（挂在框架 QuestManager 同物体即自动启用权威模式）：

- 订阅 `NarrativeEventBus.NarrytiveBus` 上的 `EnemyKilled / ItemCollected / ZoneEntered / DialogueTriggered` 四类事件 → 每个只转成 2705 `NarrativeQuestEventReport{event_type, target_key, count, graph_name, event_key}` 上报，**本地绝不推进任务**。
- 框架核心 `OnEnable` 检测到桥存在就不 `ListenGameEvents()`——本地推进逻辑只留给离线 Demo，同一套代码双模式。
- 登录/进场景发 2701 拉快照；所有回执/推送（2702/2707/2709/2710）统一 `ApplySnapshot()` → `QuestManager.ApplyServerSave(QuestSaveFile)` **整表镜像**：清空活跃列表、停全部限时计时、逐条 `ApplySaveData` 回填、执行中任务按服务端下发的 `remain_seconds` 重启倒计时。客户端若篡改本地镜像，下一次 2710 全量推送直接覆盖——**推送即纠偏**。
- 护栏：`MaxQuestRows=256 / MaxGoalCount=16 / MaxEventCount=1000`、事件 Key 截断 128 字符（防恶意包撑爆内存/存储）。
- 限时任务**惰性判定**：`SweepExpired` 在读取时判断 `expire_time_ms`，不起后台计时器；过期时间由服务端接取瞬间计算，权威且免运维。

### 8.3 Facts 黑板：玩法 → 叙事条件的解耦

`BagFactsBinder`：场景加载后订阅 `BagManager.BagUpdated`，把每个物品的持有总量写成全局事实 `DialogueFacts.SetIntFact("item_{itemId}_count", n)`（消失的写 0）。

- `DialogueFacts` 是**全局事实黑板**（MVVM 的 Model 侧）；对话开始时 `SeedInto()` 只把"对话图里声明且类型一致"的变量播种进本次对话作用域——条件节点（IntGreater/IntEquals）**零改动**复用。
- 效果：背包里有没有 1012 号物品 → `item_1012_count` 事实 → 对话选项自动隐藏/显示分支。依赖方向永远是 gameplay → facts → dialogue，对话系统不 import 背包一行代码。
- `ItemConditionDemoUI` 同时是 `IView` 实现（绑定 DialogueViewModel 的 NodeChanged/OptionsChanged/DialogEnded），MVVM 落地示例。

**配置管线**：`Editor\MmQuestConfigExporter`（菜单 Tools/Mm叙事任务/导出配置到服务器）扫描 QuestData 资产 → 导出 `Server/Config/mm_quest_config.json`（对话目标以 graph 资产名+eventKey 为匹配键）。策划改任务 → 一键导出 → 服务端重启加载，**配置双端同源**。

## 9. 副本系统

### 9.1 设计原则与流程闭环

**客户端只上报"杀了哪一类敌人"，掉什么、掉多少、能不能捡，100% 服务端按规则表裁决。** 2801–2804 四条消息构成闭环：

```
进场景(fuben) → 刷怪/战斗/击杀(纯客户端表现)
  → 2801 KillReport{enemy_type}
  → 2802 KillReportResponse{success, message, drops[]}
       A型(拾金鼠): drops 即"已入包" → 拾取横幅 + 静默刷背包
       B型(藏宝龟): drops 带 drop_token+expire_ms → 尸体处生成世界掉落物
  → 2803 Pickup{drop_token} → 2804 PickupResponse{item} → 入包
联动: 每次实入包 QuestHandler.RaiseItemGained → 收集任务/生涯/2511推送
```

- 服务端限频：`MinKillIntervalMs=200` 每玩家击杀频率闸门（压脚本刷）；类型合法性校验；B 型令牌账本 `TokenTtlMs=60s / MaxPendingPerPlayer=16 / MaxDropsPerKill=3`。
- 令牌 = `Guid.NewGuid("N")`；`TryPickup` 用 `ConcurrentDictionary.TryRemove` 保证**同令牌只消费一次**（原子认领）；"令牌不存在"与"归属不符"返回**同一文案**（防探测别人的 token）。
- 掉落规则表 `dungeon_drop_rule`（MySQL，10s TTL 缓存，`Random.Shared` 按 chance 独立 roll min~max），A 型直发 `BagRepository.Grant`（满包转邮件，结果写进 message）。
- **回执配对机制**：为什么客户端能用 `pendingKillTypes`/`awaitingPickups` 这种 FIFO 队列区分每个回执属于哪次击杀？——同 5.3 的论证：TCP 有序 + 服务端会话串行。断线时清空全部在途队列并把世界掉落复位为可重试。
- 服务端**无房间/副本会话管理器**：这是"无房间状态的掉落记账系统"，令牌账本纯内存、重启清空，客户端凭 expire_ms 先行隐藏兜底。面试被问"为什么不做真实副本同步"——答：本副本是单机体验+联网结算，跨端权威在"物品结算"而非"实时位置"，房间同步属于另一量级设计（帧同步/状态同步那一套），按需求裁剪。

### 9.2 万级掉落渲染：instanced + 数据驱动

没有用传统 GameObject 对象池，三层下沉：

- `DungeonDrop` 是**纯数据类**（无 MonoBehaviour）：`HandleDropsTick` 唯一逐帧逻辑——倒序清扫过期/消散条目、半径 1.3m 内自动发 Pickup，全程零 GameObject Instantiate/Destroy。
- `DungeonDropRenderer`：`Graphics.DrawMeshInstanced` 每批 1023（API 硬上限），图标/光晕/地环三材质各 **1 次 draw call**；浮动、脉动、billboard、距离淡出全在顶点着色器，CPU 只打包矩阵数组 + `MaterialPropertyBlock`。
- `DungeonIconAtlas`：懒烘焙 1024×1024 图集（128px×8×8），因源图标未开 Read/Write 走 GPU `Blit → ReadPixels` 拷格——**一张图集使所有掉落共享材质，合批/instancing 的前提**。
- `DungeonDropLabels`：一画布 + 12 个池化 TMP，每 0.1s 把视口内最近掉落 `WorldToScreenPoint` 投影显名（Diablo 按住 Alt 同思路），取代"每掉落挂一个 3D TMP"（几百个 TMP 网格重建是灾难）。

### 9.3 GPU 小地图（技术含量最高，30 分钟能讲秃面试官的部分）

三张图共存、同一份"世界契约"（底图 256m、+Z 北、4px/m）：左上纯地形导航图、右上 uGUI 雷达图（池化标记+0.1s 节流+最近优先有界插入+rim-clamp 边缘指方向）、右下 **GPU 实时图**，外加全屏大地图；`DungeonMapZoom` 7 档缩放三图共享一份状态防漂移，`1-exp(-12·dt)` 帧率无关平滑。

GPU 图复刻腾讯《基于 Compute Shader 的实时小地图》思路——**不用额外相机，Compute 逐像素光栅化 2D 图元**：

- **3-Kernel 管线**：`DrawMarkers`（标记+目标脉动金环）→ `DrawRoute`（金色指引折线，转角缩短+圆角衔接）→ `Composite`（Porter-Duff 合成地形+线+标记+箭头）。全程**预乘 alpha**：`src-over = s + d(1-s.a)`，目标"挖洞"用 `dst-out = d(1-s.a)`，输出时转回直 alpha 交给 RawImage。
- **Tiled 分块装箱**是万级标记的关键：`BuildTileBins` 两遍法（计数→前缀和→游标填表）把标记按 AABB 装进 32px 网格；每像素只遍历自己 tile 的标记引用区间，成本从 **O(全标记) → O(本 tile 密度)**，MaxMarkers 从 200 提到 12000。
- 绕障寻路：2D slab 法判线段与障碍盒相交，被挡则绕四角两两组合取最短合法路径；障碍盒复用场景 `DungeonMinimapLandmark` 的包围盒。
- 两个**反直觉坑**（面试杀手锏，证明你真做过）：
  1. Compute UAV 写的 RenderTexture 行 y=0 在底部 → 显示层 `uvRect=(0,1,1,-1)` 翻转修复；
  2. D3D11 下 RT 与 UAV 绑定互斥，外部做过 `ReadPixels` 后 kernel 绑定**静默失效** → 每帧显式 `BindResources()` 重绑。
- **降级不连坐**：平台不支持 Compute 时只 Destroy 这一张，两张 uGUI 图照常工作。
- 圆形裁剪下沉到 `MinimapMap.shader` 的 UV 空间 alpha 裁剪——用 Mask 组件会引入模板 pass 破坏合批（draw call 实测 24→8）。
- 运行时地形补丁 `DungeonTerrainPatchService`：底图可写副本 + 脏区重绘（还原暗角→按 SDF 重画 runtimeOnly 地块→压回暗角），门开/可破坏物由 Landmark 的 OnEnable/OnDisable 自动标脏，**零侵入**。"地图跟着地形变"。

### 9.4 全屏大地图的坐标数学

`DungeonBigMap` 核心是维护 `panCenter`（视口中心对应的世界 XZ）与一对互逆映射 `ViewportLocalToWorld / WorldToViewportLocal`；单击落点→"传送到此处"两段式确认。两个引擎级坑：CharacterController 禁用时改 position 会被内部缓存覆盖（`enabled=false → 改 → true` 的顺序处理）；传送后 Cinemachine 相机会"自转头"追人（用 `OnTargetObjectWarped` 声明位移跳变）。

### 10.3 LuaEnv 延迟销毁——原生崩溃实战（必讲）

`TearDown 顺序即正确性`：ClosePanel 通常在 **Lua 回调栈内**被触发，若此刻 `lua_close`，回调返回时 LuaVM 已销毁 → 踩已释放的 lua_State → **SIGSEGV 直接崩进程**（不是 C# 异常，try-catch 拦不住）。解法：

```
立即拆 UI 树 + 摘掉所有 Lua 引用
LuaEnv.Dispose 推迟到下一帧执行
Dispose 被拒（仍有 C# 侧回调引用）→ 补一次 GC 重试
两次失败 → 保留旧 VM 复用并告警（宁可泄漏一个 VM，不可崩玩家）
```

### 10.4 协议与服务端抽卡（2901–2914）

- `ActivityInfo{activity_id, type, banner_id, content_key, content_version, ...start/end_at_ms}`；列表响应**附带 `server_now_ms`**，倒计时 = `end_ms - server_now_ms`，本地改时钟无效。
- **抽卡响应一次带全**：`results + pity5_count/threshold + 操作后背包快照(slots+configs)`，客户端免二次拉取（一次 RTT 完成"抽奖动画 + 保底显示 + 背包同步"）。
- `GachaRepository.Draw()` 复用背包的并发模板：**PlayerWriteLock + 单事务**：锁主行 → FOR UPDATE 读背包校验消耗品 → 纯内存 `RollBatch`（**5★ 计数保底 pity5_threshold=30 + 10 连必出 4★ 替换式双保底**）→ 扣媒介 → 逐件入包（满包同事务 `InsertOverflowMail`）→ 批量 INSERT `gacha_records`（`draw_seq = total+1..+n`，**流水即保底计数的唯一依据**——保底不从"计数器字段"读，从流水算，计数器被改也不会错；失败整单回滚防计数漂移）→ 提交。
- 卡池 `banner_config.pool_json` 权重池纯数据驱动，换池零代码；`activity_config` 排期表按时间窗 `GetActiveActivities(now)` 生效。
- `ActivityGmRotate(2913)`：UPDATE 把当前活动 end_at 提前、目标活动 start 提前，成功后直接拼 `[4字节2911+pb体]` 走 `SessionManager.Broadcast` **全服广播**——运营换活动 1 秒全端感知。

## 11. 排行榜系统（MySQL + Valkey 双层）

### 11.1 双层存储模型

```
写路径（SubmitScore）:
  ① MySQL: INSERT ... ON DUPLICATE KEY UPDATE score = GREATEST(score, new)   ← 落袋为安
  ② Valkey: ZADD GT compete:lb:{challengeId} score memberId                  ← 实时层，与①同语义
  ③ ZREVRANK 回实时名次
读路径（GetLeaderboard, TopN≤100）:
  优先 ZREVRANGE → key 缺失先用 MySQL 重建一次(TryRebuild) → Valkey 不可用则直查 MySQL idx_score 索引
```

- **双保险语义一致**："只保留最高分"这条业务规则同时由 `GREATEST`（SQL）和 `ZADD GT`（Redis 6.2+，只在分数更大时更新）表达，任何一层失败都不破坏另一层的正确性。
- **降级不中断**：Valkey 挂了成绩照样进 MySQL、rank 返回 0 并在 message 说明原因；`ValkeyManager` 全 API 容错返回 false + **30s 熔断冷却**（挂了就不反复敲门）。Valkey 是 Redis 兼容发行版，用 StackExchange.Redis 驱动。
- 名字补齐：`GetNamesByIds` 一次 IN 查询拿全榜玩家名——又一次 N+1 消除。
- 身份仍是 `session.PlayerId`，客户端无法替他人刷分；但成绩本身由客户端上报（5 秒狂点挑战）——反作弊短板见 14 章。

### 11.2 客户端

`ChallengeUIController`：玩法结束 `SendScoreSubmit(1, clickCount)`；排行榜独立面板 `VirtualScrollList` 渲染 Top100 + 我的排名行，`PlayerId == MyPlayerId` 的行标"（我）"，整表替换。

## 12. 贯穿性专题

### 12.1 两种同步范式的刻意选择：快照权威 vs 乐观预测

| | 快照权威（Bag/Mail/Quest/Activity/Narrative） | 乐观预测（仅 Chat） |
|---|---|---|
| 客户端动作 | 只发请求，回执整表替换 | 先上屏，回执配对替换/失败回滚 |
| 适用判断 | 正确性敏感（涉及物品/数值） | 延迟敏感（消息气泡等 100ms 体验差） |
| 代价 | 每次操作一个 RTT，带宽略高 | FIFO 配对前提、断线全量回滚的复杂度 |

> 面试话术："我不是不会做预测，而是**按系统对'错误'和'延迟'各自的敏感度分别选型**，并且全项目只在一个地方引入预测这种复杂机制——复杂机制的引入次数越少，系统越可靠。"

### 12.2 并发控制三板斧（背包/任务提交/抽卡/邮件领取同一套）

```
① PlayerWriteLock.Acquire(playerId)   应用层每玩家串行（同进程快路径）
② SELECT ... FOR UPDATE               数据库行锁（跨进程兜底 + 读即所改）
③ 守卫式 UPDATE + 核对受影响行数        WHERE 带旧状态，0 行 = 冲突 → 整单回滚
```

再加两条业务护栏：**幂等标记**（邮件 `item_mask`、令牌 `TryRemove`）让"重复请求"与"并发请求"同样安全；**流水即真相**（gacha_records 的 draw_seq 推导保底计数）。

### 12.3 防作弊分层清单

| 层 | 手段 | 出处 |
|---|---|---|
| 协议面 | 身份由会话推导，请求无 player_id | 全局 |
| 裁决面 | 客户端只报"动作/事实"，结果服务端算 | 副本掉落、任务进度 |
| 数据面 | 进度 = 背包实时聚合，非累计计数器 | 收集任务 |
| 时钟面 | 过期/倒计时全用服务端 UTC ms | 邮件、副本令牌、活动 |
| 频率面 | 击杀 200ms 闸门、TopN≤100、MaxSessions=100 | 副本/排行/网关 |
| 包面 | 帧长 ≤1MB、MaxQuestRows=256 等护栏、事件 Key 截断 | 全局/叙事 |
| 探测面 | 不存在与无权同文案 | 副本令牌 |
| 镜像面 | 篡改客户端状态会被下一次全量推送覆盖 | 叙事任务 |

### 12.4 溢出邮件：全项目统一的"发奖必达"模式

任务奖励、抽卡产物、（可扩展到一切发放）遇到满包：同事务 `MailRepository.InsertOverflowMail` 转邮件。**发放语义 = 背包 ∪ 邮箱**，绝不出现"钱花了东西没了"的半成功。代码注释引"DNF 云幂罐子教训"——事故案例驱动的设计，面试讲故事专用。

### 12.5 防串号（账号切换脏数据）清单

登录成功时系统性清场：`QuestManager` 清任务缓存、`BagManager` 清槽位与配置、`MailManager` 清邮件、叙事 `ResetForAccountSwitch`、聊天 `RemoveChildNode` 摘旧账号动态红点叶子。**"每个带缓存的 Manager 都必须实现登录清场"作为约定执行**——串号 bug（A 退出 B 登录看到 A 的背包/红点）是这类客户端最常见的低级严重 bug，清单化是工程答案。

### 12.6 红点树与各系统联动（本项目的"消息总线"）

- 树结构：`RedDotNode` 纯内存节点，`rdCounts: Dictionary<RedDotFlags,int>`、多父 `parents`；Set 后沿父链 `CheckRedDotCount` 逐层汇总（**父 = 子之和**）。`RedDotFlags [Flags]` 五种类型同节点按位或、取最高位定样式；Number 显数字、0 自动移除。
- **三条铁律**：只写叶子不写父（父自动聚合）；业务写红点走 Manager 的"唯一出口"方法；动态业务（好友未读）用 `CreateChildNode` 运行时挂叶子，账号切换时摘除。
- 各系统写入口一览：Mail→Key8、Chat/Friends→动态 FriendKey→Key14/15、Quest→Key16=`可接取+可提交`、Bag→Key4（预留）。
- `BeginBatch/EndBatch` 批量传播 + try/finally 配对（见 6.3）。

## 13. 面试问答 40 题

> 按主题分组；每题给"回答脚本要点"，标注【加分点】。

### A. 网络与连接（Q1–Q8）

**Q1. TCP 粘包/半包怎么解决的？**
答：4 字节小端长度前缀 + 两段式精确读取（先读满长度头，校验上界，再按长度读满整帧）；发送侧 SemaphoreSlim 串行写防止并发交错。【加分】说出"长度头不含自身"的歧义处理、1MB 上界同时是攻击护栏。

**Q2. 为什么解析失败要直接断线而不是跳过该包？**
答：TCP 是字节流，一旦帧边界失步，后续字节归属不可知，跳过只会让错误扩大；断线→重连→重新握手是最干净的恢复路径。

**Q3. 服务端 TCP 模型是什么？一连接一线程吗？**
答：不是。Accept 循环用 `AcceptTcpClientAsync`，每连接一条 async 接收 Task（IOCP/Socket Task 模式），无每连接线程。会话上限 MaxSessions=100。【加分】NoDelay=true 的必要性（游戏小包 + Nagle 交互延迟）。

**Q4. 心跳怎么设计的？为什么不及时怎么办？**
答：客户端 15s Ping、45s 未收到任何包判失联重连；服务端不主动踢，用 `CancelAfter(60s)` + 每收帧 reset 的惰性超时。Pong 回带 client_ms（算 RTT）+ server_ms（时钟校准源）。【加分】说出服务端主动踢 vs 惰性超时定时器成本对比；提到心跳风暴与随机 jitter。

**Q5. 断线重连怎么做？重连后登录态怎么恢复？**
答：指数退避（1s 基数、×2、封顶 15s、10 次）；成功后用内存缓存的凭据静默重登恢复会话。凭据不落盘。【加分】讨论会话恢复（session token 续期）与重登的区别——本项目用重登，大厂项目会用 token 避免密码二次暴露。

**Q6. 单点登录怎么实现？**
答：`SessionManager.TryBindPlayer`：同 playerId 已有在线会话 → 拒绝后登者"该账号已经在线"。【加分】可改进为"后登踢前登 + 通知旧端"，讲出踢线时序与旧端状态清理。

**Q7. 客户端主线程怎么处理收到的包？**
答：接收线程只入队，主线程 Update 每帧限量 64 包分发到 C# 事件。【加分】帧预算思想：防洪峰卡帧。

**Q8. protobuf 在这个协议里扮演什么角色？为什么 MessageID 单独一个 proto 包？**
答：帧 = 长度+ID+pb 体；ID 决定 ParseFrom 哪个类型。MessageID 枚举与同名 message 类型在同一命名空间会冲突（C++ 作用域规则），单独 package 隔离。【加分】ID 放帧头不用 parse 就能路由，省一次反序列化。

### B. 服务端正确性（Q9–Q18）

**Q9. 怎么防止客户端伪造身份？**
答：所有 Request 无 player_id 字段，身份由登录绑定到 TCP 会话的 session.PlayerId 推导——协议面上表达不出"我是别人"。

**Q10. 背包并发扣加怎么保证不超发/不丢物品？**
答：三板斧——每玩家应用层写锁 + 事务内 FOR UPDATE + 守卫式 UPDATE 核对行数，0 行整单回滚。【加分】讲两层锁各自存在的理由（同进程排队 vs 跨进程兜底）。

**Q11. 邮件领取重复点/并发领怎么防？**
答：FOR UPDATE 锁邮件行 + `item_mask != 0` 即已领拒绝；claim 与置 mask 同事务——幂等落在数据库状态上。

**Q12. 任务收集进度为什么不存计数器？**
答：提交时实时聚合 player_items 持有量。计数器会被"用掉物品"污染，谓词永远反映真相，还能让状态从可提交回退。【加分】对比两种方案的 bug 面。

**Q13. 奖励发不出去怎么办？**
答：发放语义 = 背包 ∪ 邮箱：同事务算整体容量，放不下转溢出邮件，绝不部分发放。抽卡、任务、副本统一走 `InsertOverflowMail`。

**Q14. 抽卡保底计数怎么防篡改/防漂移？**
答：保底从 `gacha_records` 流水（draw_seq）推导而非计数字段；roll、扣费、入包、写流水同事务，失败整体回滚——保底与流水永远一致。

**Q15. 配置改了服务端要重启吗？**
答：任务/掉落/物品配置用 10s TTL 不可变快照缓存（Interlocked 原子发布），改库 10s 内生效；叙事任务配置走编辑器导出 JSON 管线。【加分】不可变快照 + 原子换引用 = 无锁读。

**Q16. 排行榜为什么用两个存储？一致性怎么保？**
答：MySQL 真相 + Valkey 实时。写双保险（GREATEST 与 ZADD GT 同语义），读优先 Valkey、缺失 MySQL 重建、宕机直查索引，降级时成绩照样入账。

**Q17. 限时任务/掉落过期要不要定时器？**
答：不要，惰性判定：expire_time_ms 读取时比较（叙事 SweepExpired、副本令牌）。在线玩家不需要秒级到点的清扫，省一套定时器基建。【加分】说出何时必须用定时器：需要离线推送/邮件到点触达时。

**Q18. 聊天为什么在 Mongo 而好友在 MySQL？**
答：消息是高频写、量大、schema 松的文档型负载；关系是强一致多表事务负载。存储按数据形态分而治之。【加分】Mongo 故障时聊天回执失败让客户端回滚，"绝不静默丢消息"。

### C. 客户端架构（Q19–Q28）

**Q19. 客户端怎么管理服务器推送与 UI 的关系？**
答：Manager 单例（DDOL 自举）做数据镜像 + C# 事件，UI Controller 订阅渲染；跨场景靠 DontDestroyOnLoad 单例保连接。【加分】与 MiMie MVVM 结合的例子：DialogueViewModel + IView。

**Q20. 聊天乐观发送怎么保证回执配对正确？**
答：TCP 有序 + 服务端会话串行 → 回执到达序 = 发送序，inflight FIFO 即可；断线全量回滚在途。【加分】说出这个方案的两个前提与失效条件（换传输层需 client_msg_id 显式配对）。

**Q21. 500 格背包 UI 怎么不卡？**
答：VirtualScrollList 行池虚拟化（84 行×6 列），BindSlotRow 换绑；点击索引反查不用闭包捕获数据。【加分】拖拽重定向给 ScrollRect 的 UGUI 冲突处理。

**Q22. 红点系统怎么设计的？**
答：纯内存多父树 + [Flags] 五类型，写叶子、父自动聚合求和，Set 0 自动灭，Number 才显数字；批量刷新 BeginBatch/EndBatch。【加分】动态叶子挂好友未读 + 切号摘除。

**Q23. 账号切换的脏数据怎么系统性防？**
答：约定"每个 Manager 必须在 OnLoginResponse 清缓存/摘动态节点"，清单执行（背包/任务/邮件/叙事/红点）。

**Q24. 副本万级掉落怎么渲染？**
答：数据类掉落 + DrawMeshInstanced（每批 1023 上限，三材质各一 draw）+ 单图集共享材质 + 屏幕空间池化标签 0.1s 节流显名。动效全部下沉顶点着色器。

**Q25. GPU 小地图原理？成本优化在哪？**
答：Compute 逐像素光栅化 2D 图元，3 kernel（标记→路径→合成），预乘 alpha + Porter-Duff。关键优化 tiled 分块装箱：每像素只遍历本 tile 标记，O(全标记)→O(本 tile 密度)，上限 200→12000。【加分】讲 UAV y=0 翻转与 D3D11 RT/UAV 互斥重绑两个坑。

**Q26. Lua 热更的 VM 生命周期怎么管理？**
答：每活动独立 LuaEnv（隔离全局污染与崩溃半径）；ClosePanel 常在 Lua 回调栈内，栈内 lua_close 会 SIGSEGV → UI 树立即拆、Dispose 推迟下一帧、被拒补 GC 重试、两次失败保留旧 VM 复用并告警。

**Q27. 活动"改了不发版"怎么做到？**
答：壳(C# 固定)+桥(稳定 API 面)+内容(Lua+prefab 走 YooAsset 包)三层；就绪判定不信 InitializeStatus，自建清单校验；登录后预热包。

**Q28. 对话系统怎么感知背包物品控制选项？**
答：BagFactsBinder 把持有量写成 DialogueFacts 全局事实黑板（item_{id}_count），对话开始 SeedInto 按图声明播种，条件节点零改动。依赖方向单向：gameplay→facts→dialogue。

### D. 综合与权衡（Q29–Q40）

**Q29. 你这个项目服务端权威做到什么程度？哪里破了例？为什么？**
答：玩法数值 100% 权威（快照替换）；唯一破例是聊天气泡乐观上屏——延迟敏感且错误代价仅为 UI 重画。按敏感度选型。

**Q30. 副本有没有做房间同步/多人？为什么这么取舍？**
答：没有，是"单机体验 + 联网结算"：权威边界放在物品结算而非实时位置。真实多人需要帧同步/状态同步 + 服务端 AI/碰撞，是另一个量级；当前需求下按最小正确性裁剪。

**Q31. 哪些设计是"多实例部署"时扛不住的？**
答：PlayerWriteLock 与叙事任务内存缓存、副本令牌账本、SessionManager 都是进程内状态。多实例需：玩家操作路由到同一实例（一致性哈希/gate 分片）或下沉分布式锁/Redis 账本 + 令牌进 Redis（带 TTL）。能主动说出边界最加分。

**Q32. 协议演进（加字段/加消息）怎么做？**
答：只改 .proto 跑 build_proto 三处同步；proto3 加字段向后兼容（默认值语义）；content_type 用 0 作默认使老数据零迁移；消息号段位化永不冲突。【加分】提到删字段要 reserved、复用号段是事故源。

**Q33. 服务端如何广播全服消息？在线才推怎么表达？**
答：`SessionManager.Broadcast` 直接拼二进制帧推在线会话（活动变更 2911）；离线不补推，靠客户端下次 List 拉快照对齐——"推送是加速，快照是真相"。

**Q34. 未读消息数怎么做到打开好友列表一次拿全？**
答：FriendList 响应直接带每好友 unread_count，服务端一次 Mongo Aggregate（$group by 会话）批量算出。对比逐个查询省 N-1 次往返。

**Q35. 邮件的"运营全服邮件"你怎么设计？（白板题）**
答：现场推导 6.3 方案：写扩散痛点 → 全局表 + 读时惰性裂变 + 去重表 + 注册窗口定向 + 撤回靠领取路径二次校验。

**Q36. 时间相关的坑踩过哪些？**
答：① 本地时钟不可信 → 全链路服务端 UTC ms + Pong 带 server_ms；② 限时任务 remain_seconds 由服务端算、客户端只做倒计时显示；③ unscaledDeltaTime 与暂停面板的交互。

**Q37. 这个服务端和 MySQL 怎么管的连接？**
答：MySqlConnector 池（MaximumPoolSize=50），短连接 using 归还，启动 SELECT 1 健康检查，凭据环境变量。【加分】讨论连接池大小 vs 会话数、事务持锁时间与池耗尽。

**Q38. 如果让你给这套协议加密/防重放，怎么做？**
答：握手协商会话密钥（ECDHE），后续帧加 MAC（HMAC/AEAD）、带序号+时间窗防重放；登录密码走 hash+salt（甚至 SRP/OPAQUE）。诚实说明当前全明文 + 无 TLS 是学习项目缺口，列改进优先级。

**Q39. GM 指令（Grant/Rotate/GmComplete）怎么防越权？**
答：当前只验登录不验权限位——已知 P1 风险（代码注释自认）。方案：accounts 加 role 位 + Handler 入口权限检查，GM 协议移出玩家可达端口或独立内网。主动讲 = 风险意识加分。

**Q40. 用一句话总结这个项目的架构风格。**
答："**小团队的大厂姿势裁剪版**：协议同源、段位化消息号、服务端权威 + 快照、事务三板斧、降级与熔断、按敏感度分配复杂度——每一处机制都能对应到一个真实故障模式，不是为设计而设计。"

## 14. 已知短板与改进方向

> 面试被问"这个项目有什么不足"时的诚实清单（主动讲出来是加分，藏着被揪出来是减分）。按优先级排：

1. **密码明文存储/比对** → PBKDF2/bcrypt/argon2 加盐哈希 + 恒定时间比较；登录失败锁定 + 验证码。
2. **GM/运营协议无权限位**（BagGrant/MailGrant/ActivityGmRotate/QuestGm 只验登录）→ role 字段 + Handler 入口鉴权。
3. **传输层全明文**，无 TLS/加密/防重放 → 至少握手 ECDHE + 帧 MAC。
4. **排行榜成绩客户端上报** → 服务端回放校验/行为特征检测（5 秒 80 次点击的合法上限、人机曲线）。
5. **进程内状态**（写锁、叙事缓存、令牌账本、会话表）限制水平扩展 → 玩家路由分片或状态下沉 Redis。
6. **快照全量替换**在数据量大时的带宽成本 → 版本号 + 增量差量协议。
7. **无优雅停机**（重启丢副本在途令牌、Valkey 未回写的 rank）→ 令牌账本落 Redis、drain 会话。
8. **心跳/重连无 jitter**：大服重启后全量客户端同间隔重连惊群 → 随机退避。
9. TestClient 是手工开关驱动 → 演化为自动化回归（协议全链路冒烟 CI）。
10. README 与代码轻微漂移（CompeteLoginUI 已拆为 LoginSceneController/SignupController）→ 文档随代码走。
