# 任务系统与大世界整合设计方案

> 状态：**已实施**（2026-10-29；实测结论见文末 §11）
> 需求来源：「我想把我的任务的系统的ui做成这样 然后将我的任务系统和大世界结合 比如任务是和人物对话 然后地图上是可以显示这个人物的位置的 就是可以帮助我找到这个人的位置 然后任务结束这个标记就消失 你可以用 Assets/Content/Resource/renwu 这里面的任务做任务对象 就是你仿照鸣潮式任务去做」
> 参考素材：鸣潮任务界面截图（2026-10-29）

---

## 0. 需求拆解

| # | 需求 | 落地目标 |
|---|---|---|
| 1 | 任务 UI 做成参考图那样 | 全屏任务界面重做：左侧竖排导航 / 中间分组任务列表 / 右侧任务详情（标题、描述、目标胶囊、步骤、奖励图标+数量、追踪按钮） |
| 2 | 任务系统与大世界结合 | 任务目标直接落在 dashijie 世界里：找 NPC 对话推进任务，不再是脱离场景的"计时/打点"任务 |
| 3 | 地图显示该人物的位置，帮助找到他 | 追踪中的任务在大地图与小地图上显示目标 NPC 标记；未追踪、已完成、已结束的标记不显示 |
| 4 | 任务结束标记消失 | 标记可见性由服务端任务快照实时驱动：对话目标达标、任务提交、任务放弃 → 下一帧标记消失 |
| 5 | 用 renwu 目录里的角色做任务对象 | 场景内 NPC 使用 `Assets/Content/Resource/renwu` 下的 daniya(545) 与 流萤 两个模型 |
| 6 | 仿鸣潮式任务 | 任务由服务端权威裁决；客户端只上报"发生了什么"（对话事件），不本地推进 |

### 已确认的关键取舍

| 取舍 | 决定 | 理由 |
|---|---|---|
| 任务底座 | **两套合一** → 只保留叙事任务（Mm 框架 + 服务端 27xx），删除旧任务（25xx 客户端 QuestManager + QuestView） | 叙事任务的目标类型（对话/击杀/收集/到达）正是鸣潮式任务需要的；旧任务是"累计打点"型，撑不起"找 NPC 对话" |
| 合并方向 | 旧任务的**能力**并入叙事任务，而不是两个体系互相翻译 | 双体系翻译会长期维护两套状态机、两套红点、两套推送；合并后只有一份真相 |
| 生涯/成就 | 成就系统早已独立（`AchievementRepository` + 34xx），**生涯数据保留**，只去掉旧任务的 `RaiseGameEvent` 打点 | 生涯统计是成就系统的事实源，删除会连带破坏成就 |
| 地图指引程度 | **只显示标记**：小地图方向图标 + 大地图图标 | 用户明确选择"只显示地图标记"，不做距离数值、不做屏幕外指示箭头 |
| 奖励 | 任务配置新增奖励字段，提交时**同一事务发奖**，背包满转邮件 | 与旧任务提交同规则（旧 `QuestRepository.Submit` 已有成熟实现可参照） |
| NPC 模型 | daniya(545) + 流萤 各一个 NPC | 用户确认 |
| 对话系统 | 复用 Mm DialogueSystem（`DialogueRunner` + `DialogueView`）。**但每次交互必须新建一个 `DialogueRunner`**，不能用场景里常驻的那一个 | 选项事件确实由 `DialogueViewModel.SelectOption` 发出；而"整图结束"信号 `GraphFinished` 是由 `DialogueRunner` 在 `Start()` 里 `autoStart` 自动跑到结尾时发出的——常驻 Runner 在场景加载时就把图播完了，之后 `PlayGraph` 再播不会再触发同一 `eventKey`（同一次 ViewModel 生命周期内 `firedEventKeys` 会抑制重复发布）。新建 Runner 即得到全新的 ViewModel，结束信号照常发出 |
| 追踪语义 | 单任务追踪：HUD 任务卡、地图标记都只对"当前追踪的 1 个任务"生效；默认自动追踪第一个进行中任务 | 与参考图的「追踪」按钮一致；单标记没有歧义 |
| 任务步骤 | 任务内多目标按顺序展示；当前追踪目标 = 第一个未达标目标 | 参考图「当前目标」胶囊 + 目标列表就是这样 |
| 服务端→客户端配置下发 | **本轮不新增下发协议**；客户端配置以 `QuestData` SO 为准（`Assets/Game/Resources/Quest` 由 `Resources.LoadAll` 加载） | 服务端配置与客户端配置来自同一次导出（`mm_quest_config.json`），单机联调不会出现偏差。代价：SO 变更后必须导出 + 重启服务端，否则两边不一致。后续若要上多人环境，再补一个"配置下发"协议即可，不影响本方案其它部分 |

## 1. 现状分析

### 1.1 两套任务系统

| | 旧任务（25xx） | 叙事任务（27xx + Mm 框架） |
|---|---|---|
| 客户端数据层 | `Assets/Game/Scripts/Quest/QuestManager.cs`（自举单例，服务端快照镜像 + 红点） | `Assets/Game/Narrative/QuestSystem/**`（`Miemie.DialogSystem.Quest.QuestManager`，镜像 + `MmQuestServerSync` 桥） |
| 客户端 UI | `Assets/Game/Scripts/Quest/QuestView.cs`（扁平 HUD 列表面板） | 无任务 UI（只有编辑器窗口 `QuestEditorWindow`） |
| 任务配置来源 | MySQL `quest_config` + `quest_reward`（服务端硬编码种子 8 条） | Unity `QuestData` SO → `Tools/Mm叙事任务/导出配置到服务器` → `competeserves/Server/Config/mm_quest_config.json` → 启动时种子入库 |
| 目标类型 | 挑战成绩 / 收集物品（交付）/ 加好友 / 发消息 / 章节 / 生涯 | 对话 / 击杀 / 收集 / 到达 |
| 状态 | 未接取 0 / 进行中 1 / 已完成可提交 2 / 已提交 3 | 未激活 0 / 可用 1 / 执行中 2 / 提交 3 / 失败 4 |
| 推进方式 | 服务端业务事件 `QuestHandler.RaiseGameEvent(...)` 直接推进 | 客户端上报 2705 事件 → 服务端引擎匹配 → 2710 推全量快照 |
| 奖励 | `quest_reward`，提交单事务发奖、满包转邮件 | **无** |
| 红点 | `RedDotKeys.QuestEntry`（Key16，Number 类型） | 无 |

**关键结论**：叙事任务的功能骨架（服务端权威、前置链、快照推送、对话事件匹配）已经完整且经过联调；它缺的正是旧任务有的东西——**UI、红点、奖励、业务事件入口**。所以合并方向是"拿叙事任务的骨架 + 把旧任务的这四件补上去"，然后删除旧体系。

### 1.2 叙事任务当前是"接通协议但没人触发"的状态

- `MmQuestServerSync`（`Assets/Game/Scripts/Narrative/MmQuestServerSync.cs`）与 `QuestManager`（Mm）都**没有挂在任何场景里**（`Assets/**/*.unity` 里搜不到 `MmQuestServerSync`），也就是说 Mm 任务系统客户端目前完全没运行。
- 它订阅的 `DialogueTriggered` 事件，只有 `DialogueViewModel.SelectOption` 与 `EndDialog` 会发布——这条链路是通的，缺的是"由谁把任务接到对话上"。
- 服务端 `mm_quest_config.json` 只有 2 条 Demo 任务（1001 击杀 demo_enemy、1002 对话图 SimpleDemoGraph），没有真实内容任务。

### 1.3 服务端叙事任务引擎的几个缺口（本次必须补）

| 缺口 | 表现 | 影响 |
|---|---|---|
| 提交不发奖励 | `NarrativeQuestRepository.Submit` 只改状态 | 参考图奖励区无内容可放，任务没有实际产出 |
| 提交不做幂等/加锁 | 校验与落库在内存锁内，没有 `PlayerWriteLock` / 事务 / `FOR UPDATE` | 并发重复提交会重复发奖（补奖励后风险放大到实际物品） |
| 状态 `可用1` 永不出现 | `GetEntry` 加载出的行是基线 `未激活0`，引擎里没有任何地方把 `未激活` 置为 `可用`；客户端 Mm `QuestManager.RefreshAvailable` 因而永远不把这些任务算作可接取 | 面板上所有任务都显示"未解锁"，且系统派发逻辑（`AcceptSystemQuests`）一个都接不到 |
| 不推送其他在线端 | 变化只推给"发起操作的那个 session" | 同账号另一端的任务卡不刷新（单端场景无影响，补推送成本很低） |
| 目标不可自动推进到"可提交" | 本次沿用"目标全达标后玩家点提交"的语义（旧任务也是这个语义） | 与参考图「追踪」+ HUD 任务卡一致，不需要额外设计 |

### 1.4 现有可复用能力

- **对话**：`DialogueRunner`（`PlayGraph(graph)` / `PlayGraphFrom`）、`DialogueView`（UIType 23，已注册）、`GenshinDialogDirector`（`Assets/Game/Demo`）已经实现"靠近 → 面对面 → 打开对话面板 → 摄像机正反打 → 结束后关面板"的完整流程，可直接复用逻辑（不去改 Demo 脚本，而是在大世界里做一个专用组件）。
- **地图**：`DashijieMinimap` 世界契约（中心 0,0、384m、4px/m、1536²）、`DashijieMapView`（全屏地图，内容矩形 `mapContent` 下挂标记）、`DashijieHudView` 小地图（RawImage `uvRect` 采样窗口 + `minimapArrow`）。
- **输入门禁**：`PlayerInputGate.Source.Dialogue` 已经预留（注释写着"本轮预留给对话接入时使用"）。
- **发奖与满包转邮件**：`BagRepository.LockPlayerRow / LoadSlotsForUpdate / SaveSlots / GrantIntoSlots`（internal）+ `MailRepository.InsertOverflowMail`。
- **提示条**：`AchievementToast`（成就解锁提示）可直接复用来做"任务完成/可提交"提示。

```
                    ┌──────────────────────── 客户端 ────────────────────────┐
  QuestData SO ──导出──▶ competeserves/Server/Config/mm_quest_config.json
                    └──────────────────────────────────────────────────────┘
                                          │ 服务端启动种子
                                          ▼
   ┌────────────────────────────── competeserves ─────────────────────────────┐
   │ NarrativeQuestRepository（唯一任务引擎）                                   │
   │   · 静态规则 mm_quest_config（含新增 rewards_json）                        │
   │   · 玩家态 mm_player_quests（进程缓存 + 写穿 MySQL）                       │
   │   · Submit：写锁 + 事务 + 行锁 + 发奖 + 满包转邮件                         │
   │ NarrativeQuestHandler：2701/2706/2707/2708/2709/2710                       │
   │   + 新增 2711 放弃                                                         │
   └───────────────────────────────────────────────────────────────────────────┘
                                          ▲ 2705 事件上报 / 2710 快照推送
   ┌────────────────────────── 客户端（Unity）────────────────────────────────┐
   │ MmQuestRuntime（自举）：挂 QuestManager + MmQuestServerSync（并接管收发包）│
   │   ├─ 镜像：状态 / 进度 / 追踪任务 / 红点                                    │
   │   ├─ 对话事件：WorldDialogueNpc → 对话结束/选项 → DialogueTriggered → 2705  │
   │   └─ 奖励展示：任务配置里的 reward 列表（物品图标+数量）                    │
   │                                                                             │
   │ QuestView（重做，UIType.QuestView 不变）：导航 / 分组列表 / 详情 / 追踪     │
   │ DashijieHudView：任务卡（显示追踪目标）+「有已完成任务」角标                │
   │ DashijieHudView 小地图 + DashijieMapView 大地图：任务目标 NPC 标记          │

   └───────────────────────────────────────────────────────────────────────────┘
```

## 3. 数据与协议

### 3.1 任务配置（`QuestData` SO）

新增两个字段：

| 字段 | 类型 | 用途 |
|---|---|---|
| `rewardList` | `List<QuestReward>`（`itemId` + `count`） | 提交奖励，UI 奖励区与提交发奖共用 |
| `npcKey` | `string`（可选） | 任务区域/目标 NPC 标识。为空表示任务没有地图标记（例如纯累计类任务） |

> `npcKey` 不用来匹配目标，**匹配仍走 `targetKey` / `graphName+eventKey`**；它只解决"这个任务该在地图上标谁"。

### 3.2 服务端表（迁移 `020_AddMmQuestRewards.sql`）

- `mm_quest_config` 新增 `rewards_json TEXT NOT NULL DEFAULT '[]'`（`[{ "ItemId":1001, "Count":5 }]`）。
- 无需动 `mm_player_quests`。

### 3.3 协议

| 消息 | 变化 |
|---|---|
| 2701/2702 同步、2706/2707 接取、2708/2709 提交 | 不变 |
| 2705 事件上报、2710 状态推送 | 不变 |
| **2711 `NarrativeQuestAbandonRequest` / 2712 `NarrativeQuestAbandonResponse`** | 新增：状态回到 `未激活`、进度清零（鸣潮里有"放弃追踪"，这里做成任务级放弃） |
| **2713 `NarrativeQuestToastNotify`** | 新增：提交成功后的提示（"任务【xx】完成，获得 xx×N"），客户端交给 `AchievementToast` 展示 |

奖励不进入协议：客户端从自己的 `QuestData` 读，服务端发奖只认配置；两边配置来自同一次导出，不存在"客户端显示与实发不一致"。

## 4. 服务端设计

### 4.1 `NarrativeQuestRepository.Submit` 改造（幂等 + 发奖）

参照旧 `QuestRepository.Submit` 的成熟实现：

1. `PlayerWriteLock.Acquire(playerId)`；
2. 打开连接 + 事务 + `BagRepository.LockPlayerRow`；
3. `SELECT state, progress_json FROM mm_player_quests WHERE player_id=@p AND quest_id=@q FOR UPDATE`；
4. 校验：`state == 执行中`、`AllDone(progress)`、未过期；
5. 读背包快照 `LoadSlotsForUpdate`；
6. 按 `rewards_json` 逐项 `GrantIntoSlots`（装备走实例），放不下的进 `overflow`；
7. `SaveSlots`；
8. `UPDATE mm_player_quests SET state=提交 WHERE ... AND state=执行中`，受影响行数为 0 则整单回滚；
9. `overflow` 非空 → `MailRepository.InsertOverflowMail(connection, transaction, …)`（同一事务）；
10. `transaction.Commit()`，同时更新进程缓存行。

返回结构扩展为 `(Success, Message, Snapshot, Granted)`，`Granted` 供 2713 提示使用。

### 4.2 任务可用性：`未激活 → 可用`

在 `GetEntry` 装载/`GetSnapshot` 前做一次 `RefreshAvailable(rows)`：对每条 `未激活` 行，若配置存在且全部前置任务已提交 → 置 `可用`，变更写库与推送。这样客户端看到的 `可用1` 是有意义的"可接取"。

### 4.3 与旧任务合并后的服务端清理

| 改动 | 说明 |
|---|---|
| 移除 `MessageHandler` 中 2501/2502/2503/2504/2507/2508 路由 | 旧任务协议下线 |
| 删除 `QuestRepository` 的任务部分（配置/进度/章节/放弃/GM/`OnGameEvent`） | 成就、生涯用到 `GetConfigMap` 的地方改走新引擎或直接删（成就本就独立） |
| 保留 `CareerRepository` 与 `AchievementRepository` | 生涯统计与成就来自真实业务（挑战成绩、聊天、好友、物品），不属于任务 |
| `QuestHandler` 只保留 `RaiseCareer*`、`RaiseChallengeScore`、`RaiseMessageSent`、`RaiseItemGained` 的生涯/成就部分 | 删掉其中调用 `RaiseGameEvent` 的任务打点 |
| `InternalAgentApiServer` 里读 `QuestRepository` 的接口 | 改为读新引擎快照或下线该字段 |
| `Program.cs` | 不再 `SeedQuestConfigs`；保留 `NarrativeQuestRepository.EnsureTable + LoadAndSeedConfigs` |
| 不再建 `quest_config` / `quest_reward` / `player_quests` | 老表数据保留不动（不 DROP，避免不可逆），仅停止读写 |

> 一次迁移动作：旧库里已有的任务进度直接丢弃（旧任务与新的叙事任务语义不同，没有可平移的对应关系）。若需要保留，可在文档回填阶段补一条"旧任务进度 → 叙事任务"的映射表，但当前设计不迁移。

### 4.4 客户端清理

| 删除 | 说明 |
|---|---|
| `Assets/Game/Scripts/Quest/QuestManager.cs`、`Assets/Game/Scripts/Quest/Editor/QuestViewBuilder.cs` | 旧任务数据层与旧构建器（`QuestView.cs` 保留文件名与 `UIType.QuestView` 注册，内容整体重写） |
| `ClientNetworkManager` 中 25xx 收发与事件 | 旧任务网络层 |

## 5. 客户端设计

### 5.1 任务运行时常驻：`MmQuestRuntime`

`Assets/Game/Scripts/Narrative/MmQuestRuntime.cs`，`[RuntimeInitializeOnLoadMethod(BeforeSceneLoad)]` 自举一个 `DontDestroyOnLoad` 物体，挂：

- `Miemie.DialogSystem.Quest.QuestManager`（`questList` 是**私有** `[SerializeField] List<QuestData>`，运行时无法从外部赋值——自举脚本用反射写入该字段，数据来自 `Resources.LoadAll<QuestData>("Quest")`。任务配置 SO 从 `Assets/Game/Narrative/QuestSystem/QuestSo` 移到 `Assets/Game/Resources/Quest/`，导出工具按类型扫描不受目录影响）；
- `MmQuestServerSync`（原有桥，负责 2701/2705/2706/2708 与镜像）。

对外提供（UI 只读这一层）：

| 成员 | 说明 |
|---|---|
| `QuestsUpdated` 事件 | 任意快照/操作完成后触发 |
| `TopLevelQuests` / `StepsOf` | 按分类（主线/支线）分组的任务与步骤 |
| `StateOf` / `ProgressOf` | 镜像状态与进度（方案 7 状态量语义） |
| `TrackedQuestId` / `Track` | 追踪任务（可空；默认自动追踪第一个进行中任务） |
| `CurrentGoal(questId)` | 当前目标 = 第一个未达标目标 |
| `Accept / Abandon / Submit` | 转发桥（服务端权威） |
| `RefreshRedDot()` | 待办数写 `RedDotKeys.QuestEntry`（Number）：可接取 + 可提交 |

### 5.2 大世界接入：`WorldQuestDirector`

`Assets/Game/Scripts/World/Quest/WorldQuestDirector.cs`，挂在 dashijie 场景的 `DashijieSceneBootstrap` 物体上：

1. **系统派发**：登录后快照到达 → 对 `AcceptMode=系统派发` 且状态 `可用` 的任务调 `Accept`（原桥已有该逻辑，保留）。
2. **NPC 注册**：收集场景内全部 `WorldDialogueNpc`，建立 `npcKey → NPC` 映射（供地图标记查询位置）。
3. **对话事件**：由 `DialogueViewModel` 发布到 `NarrativeEventBus`，`MmQuestServerSync` 转发 2705，本组件不重复转发；对话被提前关闭（Esc 走的是 `EndDialog`）同样会发 `GraphFinished`，按"对话结束即算完成"处理。
4. **任务完成提示**：监听 2713，交给 `AchievementToast` 展示。
5. **地图标记数据源**：`GetMarkerOf(trackedQuestId)` → 返回当前目标的 NPC 世界坐标与图标类型（见 5.5）。

### 5.3 场景 NPC：`WorldDialogueNpc`

`Assets/Game/Scripts/World/Quest/WorldDialogueNpc.cs`，挂在每个 NPC 根节点：

| 序列化字段 | 说明 |
|---|---|
| `npcKey` | 与任务 `npcKey` 对应的唯一标识（`daniya` / `firefly`） |
| `displayName` | 头顶名字 |
| `dialogueGraph` | 交互时播放的对话图 |
| `interactRange` | 交互距离（默认 3m） |
| `faceRotation` | 初始朝向 |

职责（复用 Demo 导演已验证的流程，不复用其脚本本身）：

- `Update` 里量到"当前大世界 Player"的距离，进入范围显示头顶「F 交谈」提示；

### 5.5 地图标记

**数据**：`WorldQuestDirector.GetTrackedMarker()` 返回 `(worldPosition, iconType, visible)`：

- `visible = 追踪任务存在 && 状态 == 执行中 && 当前目标未达标 && 任务配置有 npcKey`；
- `worldPosition` = 该 `npcKey` 对应 NPC 的世界坐标；
- 提交任务 / 对话目标达标 / 放弃 / 取消追踪 → `visible` 立即变 false。

**小地图（HUD）**：在 `DashijieHudView` 的小地图窗口里加一个 `questMarker` 子节点（金色菱形图标 `dashijie_quest_mark.png`）。位置换算与玩家箭头同一套：

```
窗口内相对位置(px) = (markerPixel - playerPixel) × (PixelsPerMeter × MinimapZoom)
```

`MinimapZoom = 0.55`，超出小地图窗口半径时**贴边夹取**在窗口圆周上（方向仍正确），避免"标记飞出窗口"后彻底找不到。

**大地图（`DashijieMapView`）**：在 `mapContent` 下预置一个 `questMarker` 子节点，与玩家标记同一坐标系：

```
anchoredPosition = (markerPixel - 中心) × fitScale × zoom
```

随内容一起缩放/平移；始终显示（即使当前视野外，拖过去就能看到）。

**图标与美术**：`Assets/Game/UI/Dashijie/Icons/dashijie_quest_mark.png`（金色四角菱形 + 细描边，256²，由构建器程序化绘制）；大地图与 UI 内其余新图（导航图标、罗盘、单选、勾选、奖励框、卡片底、分组条、按钮底）统一由 `Assets/Game/UI/Quest/Editor/QuestViewSkinBuilder.cs` 生成，菜单 **Tools/UI/重建任务界面**。

### 5.6 HUD 任务卡

`DashijieHudView` 现有任务卡的结构不变，数据源改为 `MmQuestRuntime`：

- 标题：追踪任务名（无追踪 → "暂无追踪任务"）；
- 目标行：当前目标描述；
- 进度行：`目标进度/需求`；
- 目标全达标时标题行右侧加金色「可提交」标记，点击任务卡仍打开任务面板。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 删 25xx 会丢老玩家的任务进度记录 | 旧任务记录失效，任务红点归零 | 老数据留在 `player_quests` 不删表；新系统红点重算；上线前告知 |
| Mm QuestData GUID 是伪造值（`f8e3c1a2…`） | 运行时脚本引用可能解析失败，任务配置读不出来 | 实施第一步在编辑器里确认类型；必要时重挂脚本并重新导出资产 |
| Mm QuestManager 客户端从未实例化 | 事件与状态镜像全链路不通 | 新增 `MmQuestRuntime` 在 `BeforeSceneLoad` 自举（§5.1），并补一次 2701 拉取 |
| 服务端配置改动需重启 | 导出后不重启会"改了没用" | 在导出菜单与文档里写明；E2E 一律先重启服务端 |
| NPC 模型无动画、比例未知 | 站立时 T-pose 或过高过矮 | 复用现有模型的默认姿态；用胶囊碰撞体兜底；不做动画闭环 |
| 玩家提前退出时传送到 NPC 旁 | 相机瞬移、角色悬空 | 传送后调 `KinematicCharacterMotor.SetPositionAndRotation(pos, rot, true)` 并清空驱动残留根运动（踩过的坑） |
| 地图标记与烘焙底图错位 | 找不到人 | 标记坐标一律走 `DashijieMinimap.WorldToMap`，不另写换算 |
| 全屏面板残留 | 场景变暗被误判为 bug | 任务面板走 `DashijieHudView` 已有的面板管理（暂停栈 + HUD 显隐），不另做全屏遮罩层 |

### 11.2 与设计稿的差异（以实现为准）

1. **没有引入服务端"可用性刷新"**：可用性由客户端 `QuestManager.RefreshAvailable` 按前置链自行推导（`ApplyServerSave` 后自动重算），服务端 `Accept` 只校验前置，链路已完整。省掉了每玩家一次多余写库。
2. **对话中途关闭（Esc）不算完成**：`DialogueView` 没有 Esc 收尾逻辑，外部关闭不会发 `GraphFinished`；`WorldDialogueNpc` 检测面板被关掉后只做收尾（解绑、销毁 Runner、放开门禁、锁回光标），不伪造完成事件。要"中途关闭也算完成"需要再改 `DialogueView.OnCancel`。
3. **左侧导航只做任务页**：成就/地图/角色/设置是视觉占位，点击提示"该页签暂未开放"——从任务面板直接开别的全屏面板会绕开 HUD 的暂停栈记账。
4. **任务配置不走上行下发**：客户端读 `Resources/Quest` 的 SO，服务端读同一次导出的 JSON；改任务需「导出 → 重启服务端」。
5. **演示任务不进运行时**：`QuestSo` 目录里的 1001/1002/Empty 模板已移出 `Resources`（否则会出现在任务面板），仅作为导出工具的存量数据。
