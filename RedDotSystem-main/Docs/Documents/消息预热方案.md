# 聊天消息预热方案（好友私聊 + 世界频道）

> 目标读者：后续维护聊天 / 好友 UI / 网络层的同学。
> 本文是施工蓝图；代码落地后请在各节追加「实测结论」，避免文档与实现漂移。

---

## 0. 一句话方案

登录进主界面后，由常驻数据层**在后台安静地预读**最近一批聊天：

- **世界频道**：主页 UI 就绪后拉首页历史（50 条），打开面板即秒开。
- **好友私聊**：只挑**确实有历史**的会话（服务端好友列表下发 `last_message_at_ms`），按「有未读优先 → 最后消息时间最新优先」选最多 8 个，用**新增的 `peek` 预读模式**拉最近 50 条；`peek` 只读不写，**不触发服务端"拉历史即已读"**，未读红点与角标语义完全不变。
- **启动时机**：等主页 UI（HomeView）就绪后再开始，避免与登录转场、主页自身请求抢同一条会话队列。

用户点开好友或世界聊天时，数据已在内存，**不再出现"正在加载…"**；只有从未预热到的新会话才走原来的按需拉取。

## 1. 背景与现状

### 1.1 现在的链路

| 入口 | 首次打开的行为 | 代码位置 |
| --- | --- | --- |
| 好友私聊 | `SelectChat` → `ChatManager.OpenConversation` → 本地无缓存则发 `ChatHistoryRequest` 并显示「正在加载与 X 的聊天记录...」 | `Assets/Game/Scripts/Friends/FriendUIController.cs:727`、`Assets/Game/Scripts/Chat/ChatManager.cs:150` |
| 世界频道 | `WorldChatView.OnOpen` → `WorldChatManager.Open` → 未 Loaded 才拉首页 50 条；加载期间列表为空、无任何提示 | `Assets/Game/Scripts/Chat/WorldChatView.cs`、`WorldChatManager.cs:186` |

结论：**所有聊天数据都是"用户点开才请求"**，一次 TCP 往返 + Mongo 查询的耗时直接暴露在 UI 上。账号好友越多、服务器越远，体感越差。

### 1.2 服务端的硬约束（本次设计的核心）

`competeserves/Server/Handler/ChatHandler.cs` 的 `HandleChatHistory` 里无条件执行：

```csharp
// 拉历史即已读：把对方发我的未读消息置 Read=true
repository.MarkConversationRead(session.PlayerId, request.TargetId);
```

也就是说：**如果登录后直接预读所有好友的历史，会把所有未读一次性标成已读**，好友列表的未读角标（红点 Key14/动态好友叶子）全部熄灭。这是绝对不能接受的回归。

世界频道没有未读概念，预读天然安全。

### 1.3 已有的可复用能力

- `ChatManager` 是常驻单例（DDOL），已经订阅好友列表响应（用于红点种子），**登录后一定拿得到好友列表与未读数**。
- `ChatHistoryResponse` 自带 `TargetId`，多个会话并发预读不会串会话。
- `ChatManager` 的会话槽是「每人一个 List」，推送到达即归位；预读填充后，在线期间的新消息由 `ChatReceiveNotify` 继续追加，缓存天然保鲜。
- 服务端 `GetHistory` 已支持 `before_ms` 与 `limit`（默认 50、上限 200）。

## 2. 目标与非目标

### 2.1 目标

1. 登录进主界面后，**不点击任何聊天入口**，后台完成最近消息预读。
2. 点击已有历史的好友 / 打开世界频道：**立即看到消息，不再显示加载态**。
3. 未读红点语义**零变化**：预读不清未读，真正打开会话才清。
4. 预读失败/超时**不打扰用户**（不弹错误、不卡加载态），点开时自动回退到按需拉取。
5. 不引入登录时的请求风暴：延迟启动 + 串行节流 + 数量上限。

### 2.2 明确不做（本期）

- 不做「最近会话摘要」新协议（按最后消息时间排序的会话列表）——列为 P2 可选增强。
- 不做私聊"上拉加载更早历史"（当前也没有）。
- 不做本地磁盘缓存/跨会话持久化（内存缓存足够覆盖本次在线）。
- 不做服务端主动推送"离线期间的消息打包"（当前靠拉取补齐）。

## 3. 方案对比

### 方案 A：纯客户端，跳过有未读的会话

- 只预读 `UnreadCount == 0` 的好友会话；有未读的仍按需拉取。
- 优点：零协议、零服务端改动。
- 缺点：**最想看的（有未读）恰好没预热**，用户感知解决不彻底。仅作为临时兜底，不推荐单独采用。

### 方案 B（推荐）：`peek` 预读模式 + 全量预读

- `ChatHistoryRequest` 增加 `bool peek`；`peek=true` 时服务端**只读不写**（跳过 `MarkConversationRead`）。
- 客户端登录后对有未读 / 最近好友的会话发 `peek` 预读。
- 用户真正点开有未读的会话时，仍发一次普通请求（`peek=false`）完成"置已读"，但此时内容已在屏幕上，用户无感。
- 优点：语义完整、改动小、协议向后兼容（老客户端不传 `peek`，默认 false，行为不变）。
- 缺点：需要 proto 重新生成 + 服务端重启部署一次。

### 方案 C：新增「最近会话摘要」接口

- 服务端聚合返回「每个会话最后一条消息 + 时间 + 未读数」，客户端据此排序再定向预读。
- 优点：预读优先级最准、带宽最省。
- 缺点：新协议 + Mongo 聚合查询 + 服务端实现，工作量约为 B 的 2~3 倍；当前好友规模（个位数）收益不明显。

**结论：本期采用 B；C 作为 P2 增强（等好友数上来或需要"最近会话"排序时再做）。**

## 4. 详细设计（方案 B）

### 4.1 协议改动

`frined/protobuf/protos/ChatPacket.proto`：

```proto
message ChatHistoryRequest {
  int32 target_id = 1;
  int64 before_ms = 2;
  int32 limit = 3;

  // 预读模式：true = 只读不写，不把对方发我的消息置为已读（登录后的消息预热用）
  // false（默认值）= 保持原有"拉历史即已读"语义；老客户端不传该字段行为完全不变
  bool peek = 4;
}
```

生成：在 `frined/protobuf` 下执行 `build_proto.bat`，同时更新：

- 客户端 `Assets/Game/Scripts/Generated/ChatPacket.cs`
- 服务端 `competeserves/Server/Generated/ChatPacket.cs`

### 4.2 服务端改动

`competeserves/Server/Handler/ChatHandler.cs` 的 `HandleChatHistory`：

```csharp
if (!request.Peek)
{
    // 拉历史即已读：仅普通拉取；预读（peek）只读不写，保护未读红点
    repository.MarkConversationRead(session.PlayerId, request.TargetId);
}
```

其余逻辑（登录校验、会话身份推导、limit 截断、正序下发）一律不动。

> 安全口径：`peek` 只影响"是否置已读"，不改变任何可见性。不同会话键仍由 `session.PlayerId + targetId` 推导，客户端无法越权。

### 4.3 客户端网络层

`Assets/Game/Scripts/Network/ClientNetworkManager.cs`：

```csharp
public Task SendChatHistory(int targetId, long beforeMs = 0, int limit = 0, bool peek = false)
{
    return SendAsync(MessageID.ChatHistoryRequest, new ChatHistoryRequest
    {
        TargetId = targetId,
        BeforeMs = beforeMs,
        Limit = limit,
        Peek = peek,
    });
}
```

默认参数保证所有既有调用点行为不变。

### 4.4 `ChatManager`：会话加载状态机 + 预读队列

#### 4.4.1 为什么需要状态机

当前 `OpenConversation` 用「字典里有没有槽」判断有没有缓存。预读会**先建空槽再发请求**，如果请求失败或尚未返回，用户点开时会被误判为"有缓存"，于是看到空列表且**永远不会再拉取**。因此必须区分三种状态：

```csharp
private enum ConversationLoadState { None, Loading, Loaded }
private readonly Dictionary<int, ConversationLoadState> loadStates = new();
```

| 状态 | 含义 | `OpenConversation` 的行为 |
| --- | --- | --- |
| `None` | 从未请求过 | 发普通请求（`peek=false`），置 `Loading`，返回空列表 + UI 显示加载态 |
| `Loading` | 预读/拉取在途 | 直接返回现有缓存（可能为空），**不重复发请求**；响应到达后 `ConversationUpdated` 触发渲染 |
| `Loaded` | 已成功拿到过历史 | 直接返回缓存；仅当本次打开时服务端未读 > 0，补发一次普通请求置已读 |

补充规则：

- `OnChatHistoryResponse`：置 `Loaded`，按现有逻辑覆盖缓存（保留本地 pending 项）。
- 超时保护：发出请求后 8 秒仍未响应且状态仍为 `Loading`，回退为 `None`（用户点开可重试）；不弹任何 UI。
- `OnLoginResponse`（换号/重登）：连同会话缓存一起清空 `loadStates`。
- `OnConnectionBroken`：把 `Loading` 全部回退为 `None`。

#### 4.4.2 预读触发与优先级

触发点：登录成功并拿到好友列表后，**等主页 UI 就绪**（`HomeViewLauncher.IsReady`，超时 10s 兜底）再启动。

候选排序（只统计有历史的会话）：

1. `UnreadCount > 0` 的好友，未读数降序（最可能有内容要看）；
2. 其余按 `LastMessageAtMs` 倒序（最近聊过的优先）；
3. `LastMessageAtMs == 0`（从未聊过）的会话**不预热**——预热它们只会白跑一次 Mongo 查询；
4. 跳过自己、跳过已 `Loaded` 的会话。

`LastMessageAtMs` 由服务端好友列表下发：`ChatRepository.GetLastMessageTimes` 用一次 Mongo 聚合取回（与未读数聚合并列，好友列表总共仍是 2 次 Mongo 查询，不随好友数增长）。

数量与节奏（字段可调，默认值）：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `prewarmEnabled` | `true` | 总开关（出问题可一键关） |
| `prewarmHomeReadyTimeout` | `10s` | 等主页 UI 就绪的上限，超时仍开始（非 zhuye 入口登录兜底） |
| `prewarmInitialDelay` | `0.3s` | 主页就绪后再等 0.3 秒，让主页自身请求先走完 |
| `prewarmMaxConversations` | `8` | 单次登录最多预读的会话数（只含有历史的会话） |
| `prewarmInterval` | `0.08s` | 相邻两个请求的间隔（串行，防突发） |
| `prewarmLimit` | `50` | 每个会话预读条数，与服务端默认开箱条数一致（避免"预读后比原来少"） |
| `prewarmTimeout` | `8s` | 单会话在途超时回退 |

链式实现建议：用协程（`ChatManager` 是 MonoBehaviour）而不是 `UniTask` 循环，便于"登录→好友列表→延迟→逐个发"的时序；`prewarmInterval` 用 `WaitForSecondsRealtime`，避免受 `timeScale` 影响。

请求统一走 `SendChatHistory(friendId, 0, prewarmLimit, peek: true)`。

#### 4.4.3 用户点开有未读会话时的时序

```
登录 → 预读(peek) 填充缓存，未读角标保持 N
用户点好友 → OpenConversation:
    state=Loaded，未读 N>0
    → 立即用缓存渲染（无等待）
    → 同时补发普通请求（peek=false）→ 服务端置已读
    → 客户端立即清本地未读角标
    → 响应到达后再覆盖一次缓存（内容一致，无闪烁）
```

这条链路完全复用现有 `OpenConversation` 的"有未读则补拉置已读"分支，只需允许它在 `Loaded` 状态下照常发请求。

#### 4.4.4 预读与实时推送的配合

- 预读回来的是"截至请求时刻"的快照；之后在线期间的新消息由 `ChatReceiveNotify` 追加。
- 服务端对同一会话的消息处理是串行的，响应顺序与请求顺序一致，不存在"旧快照覆盖新推送"的风险。
- 预读期间收到的推送会先落进同一个槽，历史响应覆盖时按现有逻辑保留本地 pending（乐观发送项），不会丢。

### 4.5 `WorldChatManager`：登录预读

- 新增 `Prewarm()`：
  - 若 `Loaded` 或已有首页请求在途，直接返回；
  - 发 `SendWorldChatHistory(0, HistoryPageSize)`（**必须用整页 50**，否则 `HasMoreHistory` 的"不足一页=没有更早"判断会误判）；
  - 响应走现有 `OnWorldChatHistoryResponse`，置 `Loaded = true`。
- 触发：`OnLoginResponse` 成功后排队，**等主页 UI 就绪**（超时 10s 兜底）再延迟 0.5 秒发起。
- `Open()` 增加在途判断：首页请求在途时不再重复发，直接复用即将到达的数据。
- 失败/超时：登录后 10 秒仍未 `Loaded` 则静默复位（下次打开面板会重新拉）；断线由 `OnConnectionBroken` 现有逻辑复位。
- 不设置 `IsOpen`，不影响未读/面板语义。

### 4.6 UI 侧收尾

`FriendUIController`

1. `OnConversationUpdated` 在渲染当前会话后清除"正在加载…"状态文案（目前该文案发出后没有任何地方清除，历史到达后仍会残留）。
2. `SelectChat` 的加载文案条件保持"缓存为空才提示"：预热过的会话天然不显示。
3. 不改气泡/虚拟列表/输入框任何逻辑。

`WorldChatView`

1. 打开时若有缓存直接渲染（现有逻辑已满足）。
2. 若首页仍在途（例如登录 1 秒内就点开），状态行显示一次「正在加载频道消息…」，到达后清除；避免"空白面板"的错觉。

## 5. 时序图（文本）

```
登录成功
  ├─ ChatManager: 清缓存 / 清状态机
  ├─ 请求好友列表（现有，含 unread_count + last_message_at_ms）
  ├─ 请求待处理申请（现有）
  └─ 等主页 UI 就绪（HomeView 打开）→ 再等 0.3s / 0.5s 开始预热

好友列表响应
  └─ ChatManager: 等主页就绪 → 只取有历史的会话 → 按未读/最近活跃排序 → 串行(每 80ms)
        → ChatHistoryRequest(target, limit=50, peek=true)
        → 响应: 填充会话缓存, state=Loaded, 触发 ConversationUpdated
        → 未读红点保持不变

主页就绪
  └─ 世界频道: +0.5s → WorldChatHistory(limit=50) → Loaded=true

用户点好友
  ├─ 已预读 → 立即渲染（0 等待）
  └─ 有未读 → 补发 peek=false → 服务端置已读 → 客户端清角标 → 再覆盖一次缓存

用户打开世界频道
  └─ Loaded=true → 直接渲染 50 条（0 等待）
```

## 7. 测试计划（E2E 验收）

### 7.1 协议级

1. `peek=true` 拉历史：返回条数正确，且服务端未把对方发我的消息置为已读（对比拉取前后好友未读数）。
2. `peek=false`（或不传）：仍置已读（回归）。
3. `peek=true` 不影响好友准入、limit 截断、正序下发。

### 7.2 客户端（Play 模式，数据断言优先）

1. 登录后等待预热窗口，**不点任何入口**：`ChatManager` 中目标会话 `Loaded=true` 且消息数 > 0；世界频道 `Loaded=true`。
2. 点开已预热的**无未读**会话：无历史请求发出（服务端日志 / 请求计数为 0），列表立即有内容，无加载文案。
3. 点开已预热的**有未读**会话：内容立即出现；随后发出 1 次普通请求；本地角标清零；服务端未读数归零。
4. 未预热到的新会话：仍能正常按需拉取（回归）。
5. 世界频道：登录后预读完成再打开 → 0 加载；登录后立刻打开 → 只发 1 次首页请求（在途去重）；`HasMoreHistory` 判断不变（满 50 条时仍可上拉）。
6. 好友数 > 8：只预读 8 个，且"有未读 / 最近活跃"优先；从未聊过的会话不预读。
7. 断线重连 / 换账号：缓存与状态机全部复位，不串号、不显示上个账号消息。
8. 预读请求无响应（模拟断网）：8 秒后状态回退，用户点开能重新拉取，UI 无报错弹窗。

### 7.3 视觉门禁

一次录屏：登录 → 直接点好友（已有历史）→ 立即出消息；再打开世界频道 → 立即出内容。VLM 只验形态与中文渲染，时序以运行时断言为准。
