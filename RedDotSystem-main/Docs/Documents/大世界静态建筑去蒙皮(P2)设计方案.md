# 大世界静态建筑去蒙皮（P2）设计方案

## 一、现状与问题

`dashijie.scene` 的城市实例 `未命名 (1)` 下共有 **240 个渲染器**，其中 **239 个是 `SkinnedMeshRenderer`（SMR），只有 1 个是 `MeshRenderer`**。

这些建筑**没有任何动画**：祖先链上没有 `Animator`，没有 `AnimatorController`，骨骼全部处于绑定姿态（239/239，偏离 0 个），每个网格只挂 1 根骨骼。它们是导出工具产出的伪蒙皮网格，运行时每帧仍要走一遍蒙皮矩阵计算。

由此产生两个后果：

1. **性能浪费**：1,206,565 个三角面每帧走蒙皮路径，GPU 与 CPU 都在为不存在的形变付出成本。
2. **遮挡剔除不可用**：Umbra 只收录 `MeshRenderer` 的静态几何，蒙皮网格不参与烘焙。P0 遮挡剔除因此永远产出空数据（实测 `umbraDataSize=0`，烘焙只生成 288 字节的空 `OcclusionCullingData.asset`）。

## 三、方案

**做「渲染器类型替换」，不做「网格烘焙」。**

因为 `SMR.sharedMesh` 本身就是 FBX 里那个可复用的 `Mesh` 资产，且骨骼处于绑定姿态、无 BlendShape，直接改为 `MeshFilter + MeshRenderer` 引用同一网格即可，外观逐像素一致，无需 `BakeMesh`、不产生新网格资产、不增加包体。

转换规则：

- 对每个 SMR 物体：`AddComponent<MeshFilter>().sharedMesh = smr.sharedMesh`，`AddComponent<MeshRenderer>()` 并复制 `sharedMaterials`、`shadowCastingMode`、`receiveShadows`、`lightProbeUsage`、`reflectionProbeUsage`、`probeAnchor`、`renderingLayerMask`。
- 删除 `SkinnedMeshRenderer`。
- 骨骼子物体（每块网格下的那 1 根骨骼）**保留**：它们是层级的一部分，删除可能影响其它物体位置；若确认无引用再单独清理。
- 缩放保持原样（`localScale=100` 不动），不做烘进顶点处理。

做成编辑器工具（菜单 `Tools/大世界/静态建筑去蒙皮（P2）`），幂等：只处理仍为 `SkinnedMeshRenderer` 且无 Animator、骨骼处于绑定姿态的物体；已转换的跳过。

## 四、影响面

| 文件 | 影响 |
|---|---|
| `Assets/Game/Scenes/dashijie.scene` | 239 个物体的组件替换（场景文件会变化） |
| `未命名.fbx` | **不改动**（继续被引用） |
| 新工具脚本 | `Assets/Game/Scripts/World/Editor/DashijieDemorphSkinned.cs` |

## 五、验收项

1. 场景中城市渲染器：`SkinnedMeshRenderer = 0`，`MeshRenderer = 240`。
2. 抽检 10 个物体的 `bounds` 与转换前一致（误差 < 0.01）。
3. Play 进入 `dashijie`，出生点可见渲染器数量与转换前一致（转换不应改变可见性）。
4. 截图对比：转换前后同一机位画面一致。
5. 重新烘焙遮挡剔除：`umbraDataSize > 0`，出生点可见渲染器数量下降。

## 六、风险与回退

| 风险 | 应对 |
|---|---|
| 转换后外观不一致 | 方案基于「绑定姿态 + 同一网格资产」，理论上零差异；用第 4 项截图逐机位比对 |
| 骨骼子物体删除导致位置错乱 | 本方案不删骨骼，规避该风险 |
| 场景文件体积变化 | 组件数增加（MeshFilter+MeshRenderer 替代 SMR），属预期 |
| 转换不可逆 | 场景在 git 中，转换前提交一次基线，失败直接 `git checkout` 回退 |

## 七、未包含

- 其它场景的同类处理（只做 `dashijie`）。
