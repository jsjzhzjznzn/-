# 战斗三系统对齐与技能冷却框架设计方案

> 状态：设计定稿（2026-10-27）。本文只描述采用的一版设计。Buff 部分独立成文，见《Buff系统设计方案.md》。

## 1. 结论

1. **伤害与 Buff 的骨架已经对齐三份讲解的核心原则**：请求对象、攻守分段的阶段化计算、阶段快照、配置与运行实例分离、容器统一管理、属性加成走来源账本、表现层通过事件解耦。
2. **需要改的地方集中在三处**：
   - 技能与冷却：目前只有事件枚举占位，没有任何冷却记录、充能、公共冷却或释放门禁。本期新建一套以角色为归属的冷却框架。
   - 技能命中：`PlayerSkillState` 只播动画，不注册打击帧、不结算伤害；技能要真正可用必须补上这条链。
   - Buff：叠加规则、来源归属、控制生效与单一时钟按《Buff系统设计方案.md》落地，本文不重复。
3. **伤害公式本期不改**。护盾、元素/伤害类型、反伤、攻击标识、服务端重算出手伤害都按玩法出现再插入，插入点在第 6 节写清楚，避免现在加空字段。
4. **不引入 GAS 替换现有实现**。`Assets/ThirdParty/GAS` 目前只有 1 个文件在项目内使用，现有轻量实现已覆盖当前需求，双轨会带来属性/效果两套真相。

## 2. 现状（以仓库当前代码为准）

### 2.1 伤害结算

| 环节 | 现状 | 位置 |
| --- | --- | --- |
| 命中判定 | 打击帧动画事件 `ATK()` → 前方球形检测，同一打击帧用 `HashSet<GameObject>` 去重 | `Battle/Core/StateMachine/Combo/CharacterCombo.cs` |
| 请求对象 | `DamageRequest { damage, isCritical, sourceId, isDoT }`，可作为 ServerRpc 单参数，字段只能追加 | `Battle/Core/Combat/Damage/DamageRequest.cs` |
| 攻方段 | 攻击力 × 招式倍率 → ×(1+DamageUp) → 暴击掷骰，只读攻方属性，产出"出手伤害" | `DamageCalculator.CalculateOutgoing` |
| 受方段 | 防御减免 `DEF/(DEF+100)` → 减伤（clamp 90%）→ 保底 1，只读受方属性 | `DamageCalculator.CalculateIncoming` |
| 结果对象 | `DamageResult` 结构体，逐阶段字段 `stageBase…stageFinal`，零分配 | `Battle/Core/Combat/Damage/DamageResult.cs` |
| 提交 | 计算完立即 `TakeDamage` 扣血；血量只在服务器（或单机）结算，再 ClientRpc 广播表现事件 | `Battle/Core/Combat/Health/HealthModel.cs` |
| 死亡 | 服务器 `_isDead` 锁，保证死亡事件只派发一次 | 同上 |
| 表现 | `E_OnDamage` / `E_DamageBlocked` / `E_OnDeath` 事件，血条、飘字、受击、震屏各自订阅 | `Battle/Core/Events/EventCenter.cs` |
| 权威 | 出手伤害由攻方算出后随请求传给受方，服务端只做受方段，不重算、不做上限校验（代码注释已声明为设计取舍） | `DamageRequest.cs` / `HealthModel.RequestDamageServerRpc` |

已知的两处口径不齐：

- 敌人伤害直接把 `AttackDef.damage` 当出手伤害传入，没有走攻方段。敌人身上的攻击力/增伤 Buff 不会影响伤害。位置：`Battle/AI/Core/EnemyBrain.ResolveAttackHit`、`Challenge/ChallengeMonster.DealDamage`。
- 一次"攻击"的去重边界是一次 `ATK()` 调用；多段技能、跨帧多判定、重发的 RPC 没有统一攻击标识。

### 2.2 Buff 与属性

| 环节 | 现状 | 位置 |
| --- | --- | --- |
| 配置 | `BuffData`：buffId、时长、最大层数、效果策略资产 | `Buff/BuffData.cs` |
| 运行实例 | `BuffInstance`：owner、source、stacks、remainTime、tickTimer | `Buff/BuffInstance.cs` |
| 容器 | `BuffComponent`：Add / Remove / RemoveAll / tick / 死亡清空 / NetworkList 镜像 | `Buff/BuffComponent.cs` |
| 效果 | 策略资产 `BuffEffect`，钩子 `OnApply / OnStackChanged / OnTick / OnRemove / OnExpire`；具体有属性加成、DoT、HoT、眩晕、沉默、无敌 | `Buff/BuffEffect.cs`、`BuffEffects.cs`、`BuffBehaviorEffects.cs` |
| 属性 | `AttributeComponent` + `MutableAttribute` + `AttributeModifier(source)`：白值 `(Base+ΣAdd)×ΠMul`，系数 `(1+ΣAdd)×ΠMul-1`，脏标记延迟重算 | `Buff/AttributeComponent.cs`、`MutableAttribute.cs` |
| 控制 | `CharacterState` 三个引用计数（眩晕/沉默/无敌）+ 网络镜像整份赋值 | `Buff/CharacterState.cs` |
| 网络 | 服务端权威；`NetworkList<BuffNetState>` 传 buffIdHash / 层数 / endServerTime / 控制位；客户端重建只读镜像，不跑效果 | `Buff/BuffComponent.cs`、`BuffNetState.cs` |

实际存在的语义缺口：

1. **叠加规则不可配**：同一 buffId 一律"层数累加（上限 maxStack）+ 时长刷新"，没有"只刷新不叠层 / 替换 / 独立多实例"的选择。
2. **来源归属模糊**：叠层时不更新 `source`，两个来源叠加后 DoT 击杀仍记给首个施加者。
3. **没有刷新钩子**：时长被刷新时效果策略收不到通知。
4. **控制未接入拦截**：`CharacterState` 只维护计数，眩晕/沉默没有在任何输入或状态切换处读取（文件注释已标注"尚未接入"）。
5. **时间源混用**：服务端 buff 计时用 `Time.deltaTime`（受顿帧/暂停影响），网络字段 `endServerTime` 用 NGO `ServerTime`（不受 timeScale 影响），客户端镜像先按 `ServerTime` 折算再用 `deltaTime` 递减。

### 2.3 技能与冷却

| 项 | 现状 |
| --- | --- |
| 输入 | `player.skill` 输入动作存在，只在 `PlayerNullState.OnSkillInput` 里使用 |
| 技能数据 | 复用 `PlayerComboSOData.skillCombo`（单个 `ComboData`），没有技能 ID、图标、冷却、充能、分组 |
| 技能状态 | `PlayerSkillState` 播放 `skill.attackClip`，播完回待机；**没有注册打击帧、没有伤害结算** |
| 冷却 | 无。`E_SkillCooldownStart/End`、`E_SkillCast` 只有枚举和 `SkillData` 结构体，无任何派发点 |
| 现存的冷却 | 三套互不相通：闪避（`Player.dodgeCooldownRemain`，本地 `deltaTime`）、敌人出招（`EnemyBrain.attackCooldowns` + `globalCooldown`，`Time.time`）、世界聊天（服务端限速 + 客户端 `unscaledTime` 节流） |
| 冷却缩减属性 | `AttrType` 没有对应项 |
| 已有但未使用 | `ComboData.comboColdTime` 与 `ComboContainerData.GetComboColdTime()` 当前没有调用点 |

### 2.4 时钟

- `Time.time` / `Time.deltaTime` 受 `timeScale` 影响。重击顿帧由 `Player.HitStop → PauseManager` 压低 `timeScale`，暂停菜单把 `timeScale` 置 0。
- `NetworkManager.ServerTime.Time` 不受 `timeScale` 影响。
- 现状结论：动画、Buff tick、闪避冷却走缩放时间；网络 Buff 到期时刻走真实时间。技能冷却必须只选一种。

## 4. 技能与冷却框架

### 4.1 分层与归属

```
配置层   SkillDefinition(SO) + SkillDatabase(SO, Resources)
           └─ 规则：标识、动画、冷却、充能、分组、挂什么 Buff
运行层   SkillCooldownRecord（纯数据，按角色一份）
容器层   SkillComponent（MonoBehaviour + NetworkBehaviour，挂角色根）
表现层   动画/UI/音效：只读状态，订阅事件
```

- 冷却状态属于角色，切换快捷栏、关闭界面、销毁 UI 都不影响。
- 只有 `SkillComponent` 修改冷却记录；其他系统通过 `TryCast` / 查询 API 交互。

### 4.2 配置

新增 `SkillDefinition : ScriptableObject`（`Battle/Core/Combat/Skill/`）：

| 字段 | 说明 |
| --- | --- |
| `_skillId` (string) | 叠加/网络判定键，`Animator.StringToHash` 预计算；为空回退资产名，与 `BuffData` 同口径 |
| `_displayName` / `_icon` | UI 与调试用 |
| `_combo` (ComboData) | 复用现有招式资产：动画、倍率、暴击、打击帧、命中 Buff、判定范围 |
| `_cooldown` (float) | 秒；`<=0` 时回落到 `_combo.comboColdTime`（该字段目前无调用点，正好复用） |
| `_maxCharges` (int) | 1 = 普通冷却；>1 = 充能型 |
| `_chargeRecoverSeconds` (float) | 每次充能恢复间隔；`<=0` 时用 `_cooldown` |
| `_cooldownGroupId` (string) | 空 = 不参与公共冷却；同组技能配置相同 GCD |
| `_gcdSeconds` (float) | 本技能触发的公共冷却秒数；`<=0` = 不触发 |

公共冷却不另建资产：分组键与 GCD 都写在技能自身配置上，释放时按该技能的 `gcdSeconds` 写入分组记录。同组技能的 GCD 应保持一致，这是一条配置约定。

`SkillDatabase : ScriptableObject` 放 `Resources/SkillDatabase.asset`，提供 `ResolveSkill(int skillIdHash)`。与 `BuffDatabase` 同构：RPC 只传 hash，两端各自还原配置。

> 命名说明：`EventCenter.cs` 已有 `SkillData` 结构体（事件参数），配置类必须叫 `SkillDefinition`，避免全局类型冲突。

### 4.3 运行时记录与统一算法

一条记录同时覆盖普通冷却与充能，避免两套代码：

```csharp
public class SkillCooldownRecord {
    public int skillIdHash;
    public int charges;          // 当前可用次数
    public float nextRecoverAt;  // 下一次恢复时刻（Time.time 口径）；满充能时为 0
}
```

- 释放：`charges--`；若从"满"变为"未满"且 `nextRecoverAt == 0`，置 `nextRecoverAt = now + recoverSeconds`。
- 每帧恢复（仅服务端/单机）：
  ```
  while (charges < maxCharges && now >= nextRecoverAt) {
      charges++;
      nextRecoverAt = now + recoverSeconds;
  }
  if (charges >= maxCharges) nextRecoverAt = 0;
  ```
  先补一次再把 `now` 作为起点，能避免掉帧/长帧后一次性补满；也天然支持"逐次恢复"。
- 剩余时间：`charges > 0 ? 0 : max(0, nextRecoverAt - now)`。
- `maxCharges == 1` 时该模型等价于普通冷却，不需要分支。
- 冷却缩减：`effective = baseCooldown × (1 - clamp(CooldownRate, 0, 0.8))`，在**开始冷却那一刻**快照，Buff 中途到期不会改变本次已开始的冷却。

公共冷却单独一张表：

```csharp
class CooldownGroupRecord { public int groupIdHash; public float endAt; }
```

查询时组合：`技能自身可放 && 分组 endAt <= now`。两者共用同一时钟和同一套变化通知，但不合并成一个数。

### 4.4 释放流程与门禁

```
玩家按键（仅拥有者）
  → SkillComponent.RequestCast(skillId)
      校验：存活 → 未沉默 → 技能存在 → 自身次数/冷却 → 公共冷却
  → 单机：本地提交，返回成功；直接开始冷却
  → 联机：本地先按快照做一次预校验（只用于手感提示），发 CastSkillServerRpc
            服务端再校验一次 → 提交 → 开始冷却 → 广播状态
            客户端收到状态后以服务端为准校正；被拒绝则回滚本地表现
  → 成功后由技能状态播放动画
```

- 死亡时 `ResetAll()` 清空全部技能记录与分组记录。
- 沉默读 `CharacterState.IsSilence`；眩晕同样禁止释放技能。移动/攻击/闪避的眩晕拦截按《Buff系统设计方案.md》实施，技能容器只负责拒绝释放。
- 没有技能配置时 `TryCast` 返回 `NotFound` 并只打一次警告，不进入冷却、不报错。

对外 API：

```csharp
SkillCastResult TryCast(int skillIdHash);
bool CanCast(int skillIdHash, out SkillCastResult reason);
float GetRemaining(int skillIdHash);
int GetCharges(int skillIdHash);   // 返回 -1 表示未初始化
```

### 4.5 打击帧与伤害接入

现状是技能只播动画。需要三步最小改动：

1. `PlayerSkillState.Enter` 在播放动画后注册 Animancer 事件 `state.Events.Add(skill.hitFrameTime, ...)`，与 `PlayerComboState.PlayAttackClip` 同口径；远程端不注册（防重复伤害）。
2. `CharacterCombo` 增加一个 `AttackTrigger(ComboData data)` 重载，把现有 `AttackTrigger()` 的判定/结算主体按传入招式执行；`ATK()` 用当前连招段调用，技能用技能招式调用。这是方法提取，不改变轻击行为。
3. 技能数据随状态传递：`PlayerComboReusableData.currentSkill` 由 `ComboData` 改为 `SkillDefinition`，技能状态从配置取动画与打击帧。

### 4.6 网络同步（仅 multiplecompete）

- `SkillComponent` 服务端（房主）权威：校验、扣次数、登记冷却、恢复计时只在服务端执行。
- 同步结构 `SkillNetState`（NetworkList 元素）：
  - `kind`：技能记录 / 公共冷却分组记录（两者共用一张表，避免再维护第二条列表）
  - `idHash`：`skillIdHash` 或 `cooldownGroupIdHash`
  - `charges`：技能当前充能（分组记录为 0）
  - `remainSeconds`：服务端算好的剩余秒数；客户端收到后用本地 `Time.time + remainSeconds` 重建
- 用 `NetworkList<SkillNetState>`，与 `BuffComponent` 同构：服务端 `Sync`，客户端整表重建只读镜像，不跑恢复计时。
- 传"剩余秒数"而不是"绝对时刻"，客户端与服务端各自用本地缩放时钟，避免 `ServerTime` 与 `timeScale` 混用。
- 冷却按全员可读同步，观战/队友 HUD 与迟到加入者都能看到正确剩余时间。
- 迟到加入/重连：`OnNetworkSpawn` 时服务端全量推一次。

### 4.7 事件与 UI 契约

复用已定义枚举，新增派发点（不为 UI 建视图）：

- `E_SkillCast`（`SkillData { skillId, cooldown }`）：提交成功后派发。
- `E_SkillCooldownStart` / `E_SkillCooldownEnd`：进入冷却、恢复可用时派发；UI 用 `GetRemaining` 每帧渲染，不要求管理器每帧广播整表。
- 事件只在"变化"时发；倒计时进度由 UI 自己按 `SkillComponent` 的查询结果算。

## 5. Buff 系统

Buff 的叠加规则、来源归属、统一退出、控制生效与网络时钟统一独立成文，见 `Docs/Documents/Buff系统设计方案.md`。本文只保留与本方案共用的一条接口约定：

- 技能释放门禁读取 `CharacterState.IsStun / IsSilence`；Buff 负责维护计数，技能容器负责拒绝释放。
- DoT 走 `HealthModel.TakeDamage(..., isDoT: true)`，与技能伤害共用受方段结算与表现事件。

## 8. E2E 验收项

单机（tiaozhan / fuben）：

1. 未配技能资产时按技能键：不报错、不进入冷却、只打一次缺失警告。
2. 配一个 3 秒冷却、1 充能的测试技能：释放后进入冷却；冷却中连按无效；3 秒后可再放。
3. 暂停菜单打开：倒计时冻结；关闭后从剩余时间继续。
4. 轻击命中的顿帧期间：倒计时按缩放时钟变慢（与动画一致），不出现跳变。
5. 3 充能技能：连放 3 次各消耗一层；之后按恢复间隔逐层回满；不满层时剩余显示正确。
6. 两个技能共用 1 秒公共冷却：A 释放后 B 立即被拒，1 秒后可放；A 自身冷却时长不受公共冷却影响。
7. 冷却缩减 Buff：实际冷却缩短；Buff 在冷却途中到期，本次冷却不变；BUFF 移除后新释放恢复原时长。
8. 沉默 Buff 生效时不能释放技能；结束后恢复。眩晕同上。
9. 死亡后冷却清空，复活可立即释放。
10. 技能打击帧造成伤害：掉血、飘字、暴击、命中附带 Buff 均与轻击一致；一次技能只结算一次。

联机（multiplecompete）：

11. 主机与客户端看到同一冷却与充能；客户端连点两次只成功一次。
12. 客户端本地改倒计时（暂停本地时钟/改内存）后，服务端仍拒绝释放，客户端收到状态后校正显示。
13. 迟到加入/重连的客户端能立即看到正确剩余时间与充能。

## 9. 风险

1. **时钟口径**：用 `Time.time` 意味着顿帧和暂停都会让冷却变慢。顿帧通常 0.03~0.3 秒，单次影响小，但连续命中会累积。若产品要求"冷却只走真实时间"，需要所有技能改用 `unscaledTime`，并接受暂停时冷却继续减少。
2. **乐观播放被拒绝**：客户端先播动画、服务端再拒绝，会出现"动作放出去但没进冷却/没伤害"。需要短 RTT 与明确的拒绝反馈；若观感不可接受，改为等待服务端确认后再播。
3. **技能打击帧复用轻击判定**：提取 `AttackTrigger(ComboData)` 时若改动到连招去重与顿帧条件，会回归到轻击手感。验收必须包含轻击连招、弹刀、粘刀三项。
4. **网络改动范围**：只在 multiplecompete 生效；挑战/副本单机路径不受影响，但仍要做一遍单机回归。
5. **命名冲突**：配置类必须叫 `SkillDefinition`，不要占用已有的 `SkillData`。
6. **不要双轨**：现有 `AttributeComponent` 是唯一属性账本；GAS 不作为第二套属性/效果系统引入。

## 10. 已确认的设计决策

1. 实施范围为完整版：技能冷却框架 + Buff 按《Buff系统设计方案.md》收敛 + 技能打击帧伤害接入。
2. 冷却时钟用 `Time.time`：暂停时停表，顿帧时与动画同步变慢。
3. 联机（multiplecompete）采用服务端权威冷却 + 客户端乐观播放，服务端状态到达后校正。
4. 充能次数、公共冷却、冷却缩减属性一并落地；记录模型一次成型，后续新增技能只加配置。

## 11. 实测结论（2026-10-27）

逻辑 E2E（程序化对象 + 读取 SkillDatabase 测试资产）：

- 3 秒冷却：1 秒后剩余 2.00 秒；3.2 秒后恢复可用。
- 3 充能 / 1 秒恢复：连放 3 次后进入冷却；1 秒回 1 层；再 2 秒回满 3 层。
- 公共冷却：同组第二次释放立即被拒；1 秒后可放。
- 冷却缩减 50%：2 秒冷却变为 1.00 秒。
- 眩晕/沉默：释放被拒（Stunned / Silenced）。
- 死亡：冷却记录清空（GetCharges = -1）。

挑战场景实机：

- 技能打击帧命中假目标：HP 1000 → 984，一次技能只结算一次。
- 技能输入走 PlayerNullState：校验通过进入 PlayerSkillState；冷却中再按留在 PlayerNullState。

未实测：联机服务端权威冷却与迟到加入（需两客户端）、远程端按 netSkillIdHash 还原技能动画。
