# 大世界技术选型评估（dashijie）

> 判断对象：九宫格 tile 加载、子场景流式（World Streamer 2 一类）、GPU Driven 渲染、双精度坐标与原点重定位、地形四叉树 / CDLOD、八叉树空间索引、六边形分块。
> 本文所有数字来自 2026-10-29 编辑器实测（`AssetDatabase`、`Renderer` 几何统计、`ProfilerRecorder`），不是估算。

---

## 0. 结论

**这些技术现在都不需要。** 它们只解决两个问题：世界装不进内存（流式加载）、世界坐标超出 float 精度（双精度 / 原点重定位）。dashijie 的可玩街区是 384 m 见方，全部静态美术放在一个 0.59 MB 的场景里加载，坐标最大 3.9 km —— 距离 float 开始失真的 10 km 还有 2.5 倍余量，距离"内容装不进内存"更远。

现在真正的浪费在渲染侧，按性价比排序三件事：

1. **遮挡剔除没有烘焙**：城市是强遮挡场景，出生点却要提交 174 个渲染器，城市几何全量进管线。
2. **3.9 km 天际线全精度渲染**：没有 LODGroup，也没有距离剔除，远处建筑与眼前建筑同样精度。
3. **239 个静态建筑是 SkinnedMeshRenderer**：这批网格带骨骼但不播放任何动画，每帧照付蒙皮与包围盒更新。

## 1. 现状实测

### 1.1 世界尺度

| 项 | 实测值 |
|---|---|
| 可玩街区 | 384 m 见方（`DashijieMinimap.WorldSize = 384`，1 m 射线烘焙可达格 55,656） |
| 城市模型包围盒 | size (3862.7, 764.9, 4201.5)，center (-283.3, 222.9, 252.4) |
| 玩家 / NPC 世界坐标 | 出生点 (6.8, -0.1, -16.2)，NPC 分别在 (8, -0.07, -18) 与 (-20, 0.04, -30)，活动范围都在 ±40 m 内 |

### 1.3 渲染与场景设置

| 项 | 现状 |
|---|---|
| 静态标记 | 全场景 0 个物体标记 BatchingStatic / Occluder / Occludee |
| 遮挡剔除 | 未烘焙（无 `OcclusionCullingData`，`m_OcclusionEnabled = 0`） |
| LODGroup | 0 个 |
| SRP Batcher | 开，spawn 点 setPass 50 / batches 485 |
| 阴影距离 | 50 m（`URP-PipelineAsset_High`） |
| 相机 | `Camera` + `thirdcamera`（第三人称跟随），主光源 1 盏直射 + 补光 |
| 加载方式 | 单场景直载，场景切换走既有 LoadingScreen 统一入口 |

### 1.4 运行时基线（编辑器 Play，仅供参考）

出生点静止、相机朝向街区：batches 485、setPass 50、提交三角面 3.27 M、顶点 4.87 M、可见渲染器 174/309、平均 20.6 fps（RTX 5070 Laptop）。

**这组帧数不能作为性能结论**：编辑器 Play 的 Main Thread 包含 EditorLoop，且提交三角面含 Scene View 与阴影 pass 的重复提交（3.27 M ≈ 场景几何 1.38 M 的 2.4 倍）。真实开销以打包后的 PlayerLoop 为准。可视作结论的只有两条：**视锥剔除在工作（174/309）**，**遮挡剔除没工作（没有数据可剔）**。

## 2. 逐项判定

| 技术 | 解决的问题 | 本项目数据 | 判定 | 触发阈值 |
|---|---|---|---|---|
| 九宫格 tile 加载 | 固定视角、瓦片化地图资源 | 无 tile 资源，单个手工城市场景，第三人称自由视角 | 不需要 | 玩法改成瓦片地图 |
| 子场景流式加载 | 内容总量超出内存 / 加载时长 | 单场景 0.59 MB + 57 MB 模型，一次加载完成 | 不需要 | 常驻 >1.5 GB 或 加载 >3 s 或 可玩面积 >2 km 见方 |
| World Streamer 2 的增量加载 | 大地图按玩家位置装卸 tile | 同上，没有可拆的 tile 划分 | 不需要 | 同上 |
| GPU Driven 渲染 | 万级渲染器、draw call 爆炸 | 309 个渲染器 / 485 batches | 不需要 | draw call >2000 或 同屏渲染器 >5000 |
| 双精度坐标 + 原点重定位 | float 在超大坐标下精度不足 | 最大坐标 4.2 km | 不需要 | 世界跨度 >10 km 必须上，>5 km 开始评估 |
| 双精度物理参考点 / 活动场景 | PhysX 在超大坐标下抖动、漏判 | 物理只在 384 m 街区内 | 不需要 | 同坐标系阈值 |
| 地形四叉树 / CDLOD / GeoMipMap | 超大程序化地形按屏幕误差细分 | 没有 Terrain，城市是静态网格 | 不需要 | 出现 >1 km² 的可走 Terrain |
| Hi-Z 深度剔除 | GPU 侧遮挡剔除，适合动态海量物体 | 静态城市，Umbra 烘焙遮挡即可覆盖 | 不需要 | 完全动态的万级物体 |
| 八叉树 / 空间索引 | 半径查询、碰撞 broadphase、AI 感知 | 动态实体 <10（2 个 NPC + 玩家） | 不需要 | 动态实体 >1000 且需要半径查询 |
| 六边形 / 立方体分块 | 立体空间世界的分块几何选型 | 单场景，无分块 | 不需要 | 真做分块后按视距收益再选 |

### 2.1 为什么 float 精度现在完全不是问题

单精度 24 位尾数。坐标 4,096 处相邻可表示值间距约 0.0005 m，16,384 处约 0.002 m，100 km 处约 0.008 m，1,600 万处才是 1 m。

- 当前最大坐标 4,201（城市包围盒 z 轴），间距 0.0005 m —— 比角色脚趾缝还细，物理与渲染都不会有可见误差。
- 经验分界线是 10 km 起需要关注、50 km 起严重。**3.9 km 距离门槛还有 2.5 倍。**
- 属于此类的抖动 / 贴图撕裂 / 物理穿透在本工程没有出现过，也不是当前任何已知视觉问题的成因。

### 2.2 为什么流式加载现在不划算

流式解决的是"内容 > 内存"和"加载时间 > 玩家耐心"。当前全部城市内容 1.2 M 三角面、578 张贴图，单场景加载一次完成，进入后步行 4 秒即可横穿可视街区 —— 玩家根本走不出已加载区域，拆块只会换来 seam、跨块寻路、跨块光照、跨块存档四类新问题。

拆场景真正开始划算的条件是：玩家能走到当前场景之外，或者单场景加载超过 3 秒。

### 2.3 为什么 GPU Driven 现在没有收益

URP 14 没有 GPU Resident Drawer（Unity 6 才提供），自建 GPU Driven 管线要重写剔除、LOD、材质属性绑定。当前 485 batches / 50 setpass 在桌面端远未成为瓶颈，投入产出为负。

## 3. 现在值得做的三件事

### P0 烘焙遮挡剔除

- **现状**：城市建筑互相遮挡极强，但场景没有任何遮挡数据，出生点 174 个渲染器全部提交。
- **做法**：给城市实例（`未命名 (1)`）与 NPC 容器标记 `OccluderStatic` / `OccludeeStatic` / `BatchingStatic`，在 `dashijie.scene` 烘焙 Occlusion Culling（默认参数先跑一版），确认剔除效果后再考虑调 `smallest occluder`。
- **收益**：街区里街对面的建筑与后街会被整体剔掉；依据 174/309 的可见比例，预期城市提交面数下降 25%~45%（以烘焙后实测为准，不预设数字）。
- **代价**：场景文件增大、烘焙耗时（分钟级）；几何改动后需重烘。

### P1 远景距离剔除

- **现状**：城市包围盒 3.9 km，天际线远景与眼前建筑同精度提交，没有 LODGroup。
- **做法**：新增 `Assets/Game/Scripts/World/DashijieFarCull.cs`，用 `CullingGroup` 对城市渲染器做距离分带（近带全显，远带关闭），半径取 350 m 起步；配合现有雾效隐藏切换。先按渲染器包围盒中心距离分带，不需要重做美术资产。
- **收益**：远景天际线（包围盒内的远处塔楼）不再进管线，视锥外的 500 m 外集群直接归零。
- **代价**：远带关闭处的 pop-in，需要用雾 / 地平线遮挡；超过 350 m 的建筑不再投影（阴影距离只有 50 m，无实际影响）。

### P2 静态建筑去蒙皮

- **现状**：239 个城市网格是 SkinnedMeshRenderer，239/239 带 bones，但没有任何动画。
- **做法**：用 FBX 内的 240 个 Mesh 重建一个纯静态 prefab（MeshFilter + MeshRenderer），原 FBX 保持不动，`dashijie.scene` 用新 prefab 替换实例，再按原位置重建 240 个 MeshCollider。
- **收益**：省掉 239 个蒙皮矩阵上传与 185 万顶点/帧的蒙皮指令，以及每个 SMR 的包围盒更新。桌面独显上收益小，移动端明显。
- **代价**：240 个 MeshCollider 是 prefab override，替换实例会全部丢失，需要脚本迁移；角色与 NPC 保持 SMR 不动。

排序理由：P0 风险最低、收益上限最高；P1 不碰资产即可见效；P2 收益依赖目标平台且迁移成本最高，放在前两项实测之后再决定。

## 4. 升级触发器

| 条件（任一满足） | 届时做什么 |
|---|---|
| 可玩面积超过 2 km 见方，或玩家能走出当前场景 | 拆子场景 + 按玩家位置流式装卸，加载半径 > 可视距离、卸载带缓冲 |
| 单场景加载超过 3 s，或常驻内存超过 1.5 GB | 同上，并加异步预加载与 loading 兜底 |
| 世界坐标跨度超过 5 km | 评估原点重定位：定期把世界平移回原点附近，存档坐标用 double |
| 世界跨度超过 10 km 且有 cm 级交互 | 双精度全局坐标 + 相机相对渲染 + 物理参考点 |
| 同屏渲染器超过 5000 或 draw call 超过 2000 | 评估 GPU Driven（需迁到支持 GPU Resident Drawer 的版本） |
| 出现 >1 km² 的可走地形 | 地形 LOD（四叉树 / CDLOD）与地形分块 |
| 动态实体超过 1000 且需要半径查询 | 引入空间索引（八叉树选型按查询形态定） |

## 6. 验证口径

1. **取数环境**：关闭 Scene View、清空 Selection（选中带 `UIControlData` 的对象会让编辑器帧严重失真），Play 模式在同一机位（出生点与街区中段各一处）采样 batches / 提交三角面 / 可见渲染器数。
2. **遮挡剔除**：对比烘焙前后同一机位的可见渲染器数与提交面数；贴墙与开阔地各测一次，确认开阔地不被误剔。
3. **距离剔除**：从街区走向远景边界，录 `record_game_view` 慢放核对切换处是否出现明显 pop-in；同时确认 350 m 外的建筑消失不影响画面主体。
4. **去蒙皮**：替换实例后核对 240 个 MeshCollider 的 `sharedMesh` 非空、玩家可正常站立与碰撞；对比替换前后同一机位的提交面数与 PlayerLoop 耗时。
5. **回归**：小地图 / 大地图标记坐标不变（`DashijieMinimap` 世界契约未改），存档传送落位一致。

## 7. 风险

| 风险 | 说明 |
|---|---|
| 遮挡剔除误剔 | 烘焙参数过激会在门口 / 天井剔除本应可见的物体；用默认参数起步，逐场景核对 |
| 标记静态的副作用 | 静态标记会禁止运行时移动这些物体；NPC 容器与可交互物件不能标 |
| 距离剔除 pop-in | 远带切换依赖远景遮挡与雾，空旷地形上最容易露馅 |
| 去蒙皮迁移丢碰撞 | 240 个 MeshCollider 是场景实例上的 override，替换 prefab 实例会全部丢失，须脚本重建并逐个校验 |
| 编辑器数据误读 | 编辑器 Play 的面数含 Scene View 与阴影 pass 重复提交，帧率含 EditorLoop，不能直接当验收依据 |
