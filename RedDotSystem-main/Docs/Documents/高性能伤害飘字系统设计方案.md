# 高性能伤害飘字系统设计方案（1000 同屏）

## 1. 目标与范围

`tiaozhan` 场景里每次有效命中在受击点飘出一条伤害数字，风格对标绝区零：数字弹入、随机倾斜、上浮渐隐，暴击有专属字号与金橙色表现，同一目标短时间内的连续命中合并成一条累加数字。

性能目标按**同屏 1000 条**设计：1000 条同时存活时，飘字只占 **1 个 DrawCall、0 B 托管分配/帧、CPU 增量 ≤1ms**。挑战场景的实际峰值远低于此（单 BOSS、每秒 10 次左右命中），这套实现为后续割草/AOE 玩法预留容量，不需要再换实现。

不做的事：不做 `TextMeshProUGUI` 逐条渲染；不做 ECS/DOTS；不改伤害结算、服务端与协议。飘字只显示数字与少量符号，不显示中文文案（中文提示走 HUD 文本）。

## 2. 现状分析

### 2.1 触发链路（保持不变）

```
攻击命中 → HealthModel.TakeDamage → EventCenter.Dispatch(E_OnDamage, DamageData)
        → DamageTextManager.OnDamage（订阅方）→ 世界坐标投屏幕 → 写入飘字数据
```

`DamageData` 提供 `target / source / amount / isCritical / isDoT / canTriggerDodge`，没有命中点字段，位置由受击者自身推算。闪避无敌被拦下的伤害走 `E_DamageBlocked`、不派发 `E_OnDamage`，天然不会飘字。

### 2.2 TMP/UGUI 路线在 1000 条时的硬上限

现有实现是「每条飘字一个 UGUI 对象 + 一个 `TextMeshProUGUI` + 一个 DOTween 序列」。在这个规模下有四类成本无法通过打补丁消除：

- **元素数量**：1000 条就是 1000 个 `CanvasRenderer` 与 1000 份文本网格，Canvas 的 BuildBatch 开销随元素数线性上升。
- **生成即全画布重建**：任何一条文本变化触发 `Canvas.SendWillRenderCanvases`，该层 Canvas 全部元素重排/重批；1000 元素下单次重建就是毫秒级。
- **激活与父级变化**：`SetActive(true)` 会把整个 Canvas 的元素标记 SyncTransform，1000 条规模下这一下最贵。
- **每条一个补间**：DOTween 的每个 tween 都有托管对象与每帧调度成本，1000 条就是 1000 份调度。

结论：1000 条不能走「一条 = 一个 UGUI 元素」的路，必须把渲染降到一次批量提交。

### 2.3 现有代码的事实

- `DamageTextManager` 由 `Singleton<T>.MainInstance` **自举**创建，`tiaozhan` 没有实例化 `DamageTextManager.prefab`，所以挑战场景用的是脚本字段默认值；预制体只作用于 `multiplecompete`。
- 每次命中产生 `amount.ToString()`、`() => Recycle(text)`、`DOTween.Sequence()` 三笔托管分配，`SetActive` 两次。
- 画布条件已经合适：`UILayer.DamageLayer = 3500`、Overlay、`pixelPerfect = false`。飘字不进主 UI 层，命中不会导致主界面重建。

## 3. 设计

### 3.1 总体结构

三部分，全部围绕「一条飘字 = 一个实例」：

| 部分 | 职责 |
|---|---|
| `DamageTextManager` | 订阅伤害、投屏、合并、限流、维护 `FloatingText[]` 数据数组、每帧推进动画 |
| `DamageTextRenderer` | 把数据数组打包成实例参数，`Graphics.DrawMeshInstanced` 提交；每帧只写数组，不建 GameObject |
| `DamageText.shader` | 顶点着色器按实例参数完成数字排版、倾斜、缩放、定位；片元着色器采样字形图集输出颜色 |

**一条飘字 = 1 个实例，不是 1 个字符 1 个实例。** 实例网格固定为 6 个四边形（最多 6 位数字，含符号），未使用的位在着色器里缩到 0 面积丢弃。1000 条 × 24 顶点 = 24000 顶点，`DrawMeshInstanced` 上限 1023 实例/批，因此 1000 条**恰好 1 批 1 个 DrawCall**。

### 3.2 数据层：结构体数组 + swap-back

```csharp
struct FloatingText {
    float3 origin;      // 屏幕坐标（像素）
    float  age, life;   // 动画进度
    int    value;       // 数值
    int    targetId;    // 目标实例 ID（合并用）
    float  rot, scaleMul;
    float  seed;        // 随机相位
    byte   flags;       // 暴击 / 治疗 / 合并中
}

FloatingText[] _texts = new FloatingText[1024];
int _count;
```

回收用 swap-back：末尾元素覆盖被删除位，`_count--`，O(1) 且活跃数据连续。数组一次性分配，运行期不扩容、不 new、不装箱。

### 3.3 每帧 CPU 工作量

| 步骤 | 复杂度 |
|---|---|
| 遍历活跃数组算 t、位置、缩放、alpha、旋转 | O(1000)，纯浮点运算 |
| 屏幕外剔除（屏幕矩形判定） | 同行一次比较 |
| 写实例参数数组 | O(1000) 次写入，每条约 12 个 float |
| 提交 | 1~2 次 `DrawMeshInstanced` |

没有协程、没有补间、没有字符串、没有 GameObject 增删。1000 条时的 CPU 侧预期在 0.3~0.8ms 之间。

### 3.4 实例参数表

`MaterialPropertyBlock` 按实例下标写入连续数组（每批 1023）：

| 数组 | 内容 |
|---|---|
| `_Origin` (float4) | 屏幕像素坐标 + 起始时间 |
| `_Params` (float4) | 缩放、旋转（弧度）、alpha、标志位 |
| `_Digits` (float4) | 6 位数字打成 2 个 uint（每 4 bit 一位），低 8 bit 存有效位数 |
| `_Color` (float4) | 颜色（普通暖白 / 暴击金橙） |

顶点着色器由 `unity_InstanceID`（或 instancing buffer 索引）取本实例参数，逐顶点算出「第几位、哪个角」，再取字形 UV 与 advance。

### 3.5 顶点着色器排版

1. 由 `vertexID / 4` 得到位数槽 `slot ∈ [0, 5]`，`slot >= digitCount` 时把四边形缩为 0 丢弃。
2. 从 `_Digits` 解出该位数字，查表得字形 UV 矩形与 advance。
3. 数字总宽度 = 各有效位 advance 之和（等宽排版时可退化为 `digitCount × advance`）；当前槽的横向偏移 = 前面各位 advance 之和。
4. 四边形四角在字形矩形内归一化到 `[0,1]`，乘字号得到局部坐标。
5. 叠加整体缩放与旋转（绕本条飘字中心），平移到 `_Origin`。
6. Billboard：在视空间构造四边形，保证始终正对相机。

排版的全部算术都在 GPU 上，CPU 每帧只更新原点/缩放/alpha，不参与字形布局。

### 3.6 字形图集

直接复用工程现有的 `TMP_FontAsset`：从 `atlasTexture` 取纹理，从 `characterLookupTable` 读 `0-9`、`-`、`+`、`!` 的 `glyphRect` 与 `horizontalAdvance`，归一化成 UV 后写进材质常量（10~13 个 `float4` + advance 数组）。

好处是零新增美术资产、字形与 HUD 文本完全同风格；片元按 SDF 采样（`alpha = smoothstep`）并支持描边宽度，暴击用同一张图集只换 tint。

字体缺字时该位退化为空白并记一次警告，不崩。

### 3.7 动画（t 的纯函数，CPU 侧计算）

四段曲线沿用前一版的判定，只是把结果写进实例参数：

| 段 | 曲线 | 参数 |
|---|---|---|
| 弹入（0~0.14s） | 缩放 `0.55 → 1.0`，`EaseOutBack` 过冲到约 1.12 | `scaleFrom = 0.55` |
| 上浮（0~0.55s） | `EaseOutQuad` 抬升 | `floatHeight = 86px` |
| 微坠（0.55s~结束） | 二次曲线回落 | `settleDrop = 12px` |
| 渐隐（45%~结束） | alpha `1 → 0` | `fadeStart = 0.45` |

随机量在生成时定死：旋转 `±8°`、水平偏移 `±20px`、垂直偏移 `±10px`。暴击额外叠加前 0.18s 的 ±3° 衰减抖动，并把整体缩放乘 1.25。

### 3.8 渲染顺序与混合

- 队列：`Queue = Overlay`（4000），在 3D 不透明与半透明之后、UI 相机之前绘制 —— 飘字压在场景上、位于 HUD 之下。
- 状态：`ZTest Always`、`ZWrite Off`、`Cull Off`、`Blend SrcAlpha OneMinusSrcAlpha`。
- 同批实例按实例下标顺序混合，后生成的字在上层；不做逐条深度排序。

### 3.9 坐标

- 世界点：受击者渲染器包围盒的上半段（`center.y + extents.y * 0.35`），失败退回 `position + up * headOffsetY`。取上半身而非包围盒顶，是因为 BOSS 体型大时顶部会投影到屏幕之外。
- 投影：`Camera.main`（战斗里两套座位相机同名标签，绑座后只有本机在用），取不到退「任意启用的 Game 相机并排除 UI 相机」；`screenPos.z < 0` 丢弃。
- 屏幕像素 → 世界：在相机前方固定距离 `d = 1` 处放四边形，像素尺度 `k = 2·d·tan(FOV/2)/Screen.height`，于是字号以像素为单位恒定，不受距离影响。
- 着色器直接写裁剪空间，因此必须乘 `_ProjectionParams.x`（D3D / 渲染到纹理时投影是翻转的）；漏掉会让飘字的落点与字形一起上下颠倒。
- 屏幕坐标最终夹进可视区（边距 48px），保证飘字不会跑到视野外。

### 3.10 合并、限流、容量

- **合并**：键为 `target.GetInstanceID()`，窗口 `mergeWindow = 0.25s`；命中则累加数值、重置年龄重新弹入，不新增实例。
- **自适应窗口**：活跃条数 > 700 时窗口自动放大到 0.45s，让连击在高压下更快收拢。
- **限流**：每帧最多新建 32 条，超出按合并规则处理。
- **容量**：1024 条。满了以后新伤害优先合并到同目标，无同目标则顶替年龄最大的一条，不扩容。

## 7. E2E 验收项

1. **单 DrawCall**：Frame Debugger 里 1000 条飘字只有一次 instanced draw，材质与图集唯一。
2. **零分配**：1000 条生成与播放期间 `GC Allocated In Frame` 为 0 B。
3. **帧预算**：1000 条同屏时 `CPU Main Thread Frame Time` 相比空闲基线增量 ≤1ms，`GPU Frame Time` 增量 ≤1ms。
4. **无尖峰**：一次 AOE 触发 500 条，最差单帧 ≤33ms。
5. **合并生效**：同目标 0.25s 内 3 次命中只留 1 条，数值为三次之和。
6. **排版正确**：1~6 位数与负数、暴击字号、描边、倾斜方向均正确；字距无重叠、图集无串字。
7. **遮挡关系**：飘字压在角色与场景上，被 HUD 覆盖；目标在相机背后不出现。
8. **生命周期**：目标死亡、切场景回主页后无残留实例、无空引用、无材质泄漏。

## 8. 风险与约束

- **渲染路径已验证**：`DrawMeshInstanced` + `MaterialPropertyBlock` 数组 + 自定义实例化 shader 在本工程（URP 14.2.0-t1 分叉）跑通，1000 条实例一次提交，字形 UV 与排版正确。
- **着色器写裁剪空间必须处理投影翻转**：顶点着色器直接输出 NDC 时，Y 要乘 `_ProjectionParams.x`。漏掉的表现是整条飘字上下颠倒且落点镜像，容易被误判成图集 UV 错。
- **Tuanjie shader 解析限制**：属性块禁止带空格的中文 `[Header]` 与中文 `[Tooltip]`，注释用 ASCII，否则整个 shader 变 unsupported。
- **图集重建**：TMP 字体补字时会重建图集纹理，渲染器每帧比对图集引用与尺寸，变化时重读字形 UV。
- **SDF 采样**：直接采样 TMP 图集的 alpha 做 SDF，缩放跨度比 TMP 原生渲染窄；暴击字号放大到 1.35 倍时边缘仍清晰。
- **深度与排序**：关闭深度测试与写入，飘字之间按实例顺序混合；极端重叠时可能出现个别穿插，属可接受表现。
- **合并会跳变**：连击累加时数值会跳大，是有意的表现选择；合并保留首次命中的样式，先普通后暴击的连击不会中途变成金色。
- **字体缺字**：数字字符在所有常规字体里都存在；换用裁剪过的图集缺位时该位留空并打一次警告。

## 9. 实测结论

2026-10-29 在 `tiaozhan` 场景实测（同场景内先清空飘字取基线，再一次性灌入 1000 条）：

| 指标 | 基线 | 1000 条 | 增量 |
|---|---|---|---|
| CPU Main Thread Frame Time | 2.51ms | 3.00ms | **+0.49ms** |
| GPU Frame Time | 1.89ms | 2.20ms | **+0.31ms** |
| GC Allocated In Frame | 9534 B | 9579 B | +45 B（噪声级） |
| Batches | 37.1 | 39.0 | +2（其中 setPass +1，即实例化提交本身一次） |

功能项：

- 合并：同一目标连续三次命中 100 / 200 / 300，最终只留 1 条，显示 **600**。
- 事件链路：向 BOSS 派发两次 `E_OnDamage`（128 普通 + 356 暴击），0.25s 内合并为 **484**，落点在 BOSS 上半身并夹进屏幕内。
- 排版：0-9 与多位数逐位正确，字距与居中正常；与同字号 TMP 文本并排对照，字形方向一致。
- 观感：普通暖白、暴击金橙并带更大字号与描边；飘字压在场景之上、HUD 之下。
