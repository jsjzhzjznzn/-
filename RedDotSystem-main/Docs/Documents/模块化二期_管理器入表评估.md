## 0. 结论先行

**不建议全量迁移。** 一期之后 ModuleHub 表内有 3 个管理器（`MonoManager` 1 / `AudioManager` 3 / `InputBuffer3D` 8），表外还有 20 多个单例。逐条核过之后，真正值得入表的只有 **3 个**：

| 结论 | 系统 | 一句话理由 |
|---|---|---|
| ✅ P1 建议做 | 资源层（`ResourceManager` + `YooAssetService`） | 启动时已经在 `ModuleHub.Boot` 里手调初始化，属于"事实上的模块但没入表"，顺序必须第一 |
| ✅ P1 建议做 | `UIManager` | 不自建实例、必须显式 `Initialize()`、依赖资源与相机就绪，现在靠"调用方记得先调"这种隐性约定 |
| ✅ P1 建议做 | `ClientNetworkManager` | 有连接生命周期 + 需要确定性断连 + 二十多个事件订阅，现在只有 `OnDestroy` 才退订 |
| ⚠️ P2 看需求 | `RedDotSingleton` / `ChatManager` / `LuaEnvManager` | 收益中等，且聊天/Lua 都依赖网络模块先入表 |
| ❌ 不做 | `BagManager` / `QuestManager` / `MailManager` / `Friends` / `Challenge` / `Guide` / `Activity` | 常驻但既无顺序依赖、也无关闭需求，迁过去收益为零 |
| ❌ 不做 | 战斗/副本内的 `TimerManager`、`VFXManager`、`DamageTextManager`、`BattleSpawnManager`、`CharacterInputSystem`、`DungeonManager` | **场景级对象**。入表 = 全局单例 = 切场景不释放，反而制造泄漏与脏状态 |
| 🧹 先清理 | `Assets/Game/Scripts/Compete/**`（131 文件 / 15238 行） | 全工程无外部引用，疑似整包死代码，比模块化更值得先处理 |

一句话概括判断依据：**ModuleHub 卖的是"顺序 + 关闭 + 可替换"，不是"少写一个 Instance"。**

## 1. 准入标准：什么才配进 ModuleHub

ModuleHub 提供的四件事（详见一期文档 §5）：构造并按优先级排序、按序 Init、逆序释放、按类型取用。所以一个系统值得入表，至少要命中两条：

| # | 条件 | 反例 |
|---|---|---|
| A1 | **跨场景常驻**，生命周期 = 应用生命周期 | 一局战斗里的 `TimerManager` |
| A2 | **有启动顺序依赖**（必须晚于资源、早于 UI …） | `BagManager`（谁先谁后都对） |
| A3 | **需要确定性关闭**（断连 / flush / 释放句柄 / 停线程） | 纯查询类数据层 |
| A4 | **需要 Inspector 配置或可替换实现**（测试替身） | 纯静态工具类 |

不满足的，现有的 `Singleton<T>` / `SingletonMono<T>` 就够了。**"全项目统一写法"本身不构成收益**，它是重构成本，不是功能。

> `ResourceManager` 与 `YooAssetService` **不是重复**：后者是 YooAsset 的薄封装（`LoadAssetAsync` / `UnloadUnusedAssets`），前者是上层门面（懒初始化、引用计数、对象池、`Recycle`）。两者应作为**一个模块**入表，对外只暴露 `ResourceModule`。

### 2.3 场景级系统（明确不迁）

`TimerManager`、`DamageTextManager`、`VFXManager` + `VFX_PoolManager`、`BattleSpawnManager`、`DungeonManager`、`CharacterInputSystem`、`CameraShakeManager`、`PauseManager`

这些的生命周期跟"一局战斗 / 一个副本"绑定。入 ModuleHub 后会在**启动时构造并 DontDestroyOnLoad 常驻**，切场景不释放：内存里挂着一整局的残留状态（敌人引用、计时器、粒子句柄），下一局开始前还得手动清 —— 比现在更差。

## 4. 反方意见：为什么"全都模块化"是错的目标

1. **收益不在写法**。对没有顺序依赖、没有关闭需求的常驻单例，迁移只是把 `X.Instance` 换成 `GetManager<X>()`：多一层字典查找，少一个编译期可搜索的符号（`Instance` 能被 "Find Usages" 找到，`GetManager<T>` 不能）。
2. **会把懒加载变成启动构造**。`ModuleHub` 的 Boot 是"注册即构造 + 立即 Init"。`LuaEnvManager`、`ChatManager` 现在都是第一次用到才建；入表后开局就建。用启动时间换写法统一，不划算。
3. **会把场景级系统变成全局泄漏**（见 2.3）。
4. **迁移期双实例陷阱**：单例的 `Instance` 和 `managerDict` 会各持一份。必须一次性把 `Instance` 改成转发或删掉，不能"先加进去、旧路径以后再说" —— 那种状态最难查。
5. **ModuleHub 自身也有代价**：`ReadyAsync` 之前的任何 `GetManager<T>()` 都拿不到东西，业务侧必须 `await`。现在很多代码是同步的 `X.Instance.Yyy()`，改造面比看起来大。

## 0.5 ⚠️ 执行前审查修订（2026-10-23，推翻 §0 的三项 P1）

按"执行前必须严格审查、确认是否影响其他功能"的要求，对 §0 的结论逐条查证，结果**三项 P1 全部不成立**，只有 P0 站得住：

| 原结论 | 审查结果 | 证据 |
|---|---|---|
| P1-1 资源层入表 | ❌ **撤回**：收益接近 0 | `ResourceManager.InitializeAsync` 只有一行转发 `YooAssetService.InitializeAsync`（后者自带防重入），`ModuleHub.Boot` 已经在调用它。包成模块只是把 3 行代码换个位置 |
| P1-2 `UIManager` 入表 | ❌ **撤回**：前提全错、风险高 | ① 它用的是 `SkierFramework.SingletonMono`，**不是** `MieMieFrameWork.SingletonMono`——前者 `Instance` 里 `FindAnyObjectByType`，找不到就 `new GameObject + AddComponent + DontDestroyOnLoad`；② 全工程手调 `Initialize()` 只有 **1 处**（`BattleTestBootstrap.cs:38`），不是"多处"；③ 真正干活的是**异步**的 `EnsureInitializedAsync`（YooAsset → 建层/相机 → 读 UIConfig），而 `IManagerBase.Init()` 是**同步**的，接不住；④ `UIManager` 是 `LOGIN.scene` 里的根物体（名字 `SkierFramework.UIManager`），ModuleHub 在 BeforeSceneLoad 构造时它还不存在，只能 new 一个 → **丢掉 Inspector 上的 `width/height/uiBlackType` 配置** |
| P1-3 `ClientNetworkManager` 入表 | ❌ **撤回**：高收益假象 | 它现在靠 `RuntimeInitializeOnLoadMethod(BeforeSceneLoad)` **同步** new 出来，立即可用；ModuleHub 的自举是**异步加载** `Resources/Framework/FrameRoot` 预制体，中间有若干帧 `Instance == null` 的窗口。全工程 **258 处** `ClientNetworkManager.Instance` 调用点，必须全部改成 await 语义 |

追加一条地基级发现（比上面三条更重要）：

> **项目里有 3 套 `SingletonMono` 实现**：`MieMieFrameWork`（不自动创建）、`SkierFramework`（自动创建 + DDOL）、`Compete`（随 Compete 目录一起删）。同一个 `XXX : SingletonMono<XXX>` 在不同命名空间下语义完全不同。**不先统一单例基类，任何"模块化"都是在流沙上盖楼**——因为"实例何时存在"这件事目前没有统一答案。

**修订后的执行计划**：只做 P0（删除 `Compete`），P1 全部搁置；统一单例基类另行立项。
