## 1. 第 1 项：异步模块契约

### 现状

```csharp
// ModuleHub.cs:100
internal void InitManagers()
{
    foreach (var Manager in managerOrderList)
        Manager.Init();          // 同步，没法 await
}
```

`BootAsync` 里 `RegisterAllManagers() → InitManagers() → isReady = true`，整条流水线本身是异步的（`UniTask`），只有 `Init` 这一步是同步的。

### 方案

```csharp
public interface IAsyncManagerBase : IManagerBase
{
    UniTask InitAsync(CancellationToken cancellationToken);
}
```

`InitManagers` → `async UniTask InitManagersAsync(CancellationToken)`：

```csharp
foreach (var Manager in managerOrderList)
{
    if (Manager is IAsyncManagerBase AsyncManager)
        await AsyncManager.InitAsync(cancellationToken);   // 实现异步接口的，只走异步
    else
        Manager.Init();
}
```

- **契约**：实现了 `IAsyncManagerBase` 的管理器，`Init()` 不参与初始化（ModuleHub 不调用它），避免同步/异步两条路径重复初始化。
- 现有 3 个管理器不受影响（都不实现该接口）。
- 失败回滚：`BootAsync` 已有 catch → `readySource.TrySetException`；异步阶段抛异常会走同一条路。

### 收益

以后 `ResourceModule` / `UIModule` 这类**真需要异步**的模块才有资格入表；同步 `Init()` 不再是拦路虎。**但本期不新增任何模块**。

## 2. 第 2 项：单例基类收敛

### 现状盘点（4 套自研 + 1 套第三方）

| # | 基类 | 位置 | 形态 | 语义 | 使用者 |
|---|---|---|---|---|---|
| 1 | `MieMieFrameWork.Singleton<T>` | `Framework/A_Frame/Singleton.cs` | 纯 C# | 懒 `new T()`，无钩子 | **无人使用** |
| 2 | `MieMieFrameWork.SingletonMono<T>` | `Framework/A_Frame/SingletonMono.cs` | MonoBehaviour | **不自动创建**，默认不 DDOL | `ModuleHub` 自身 |
| 3 | `SkierFramework.Singleton<T>` | `UI/Framework/Common/Singleton.cs` | 纯 C# | 双检锁懒建，有 `OnInitialize()` 钩子 | `ResourceManager` / `YooAssetService` / `UIModelManager` |
| 4 | `SkierFramework.SingletonMono<T>` | 同上 | MonoBehaviour | **自动创建 + DDOL** | `UIManager` |
| 5 | `Battle.Core.Singleton<T>` | `Battle/Core/Common/Singleton.cs` | MonoBehaviour | 属性名 **`MainInstance`**，自动创建，重复时 `Destroy(this)` 只删组件 | `CharacterInputSystem`（21 处）/ `TimerManager`（4 处） |
| — | `RootMotion.Singleton<T>` | `Plugins/RootMotion/...` | 第三方 | 不碰 | 插件内部 |

问题不在"套数多"，在于**同名不同义**：一个 `XXX : SingletonMono<XXX>` 到底会不会自动创建、会不会跨场景存活，取决于它在哪个命名空间——这正是 `RoomState.cs:17` 注释在吐槽的东西。

### 方案：显式化 + 收敛，而不是一次性大搬家

新增两个**语义显式**的基类（放 `Framework/A_Frame/Singleton.cs`）：

```csharp
/// 纯 C# 服务单例
public abstract class SingletonService<T> where T : SingletonService<T>, new()
{
    public static T Instance { get; }        // 懒创建
    public static bool IsCreated { get; }
    protected virtual void OnInitialize() { } // 构造后钩子（兼容 SkierFramework 现有用法）
}

/// MonoBehaviour 单例：两个语义开关必须显式声明
public abstract class SingletonBehaviour<T> : MonoBehaviour where T : SingletonBehaviour<T>
{
    protected virtual bool AutoCreate => true;    // 取不到时是否新建
    protected virtual bool Persistent  => true;   // 是否 DontDestroyOnLoad
    public static T Instance { get; }
    public static T MainInstance => Instance;      // 兼容 Battle.Core 的旧属性名
    protected virtual void Awake();   // 首个注册；重复者 Destroy(this)（不毁 GameObject）
    protected virtual void OnDestroy();// 仅当自己是当前实例时置空
}
```

**关键：`AutoCreate` / `Persistent` 从"各基类默认值不同"变成"每个类自己声明"。**

### 迁移清单（调用点改动 = 0）

| 类 | 从 | 到 | 需声明 | 调用点影响 |
|---|---|---|---|---|
| `ResourceManager` | Skier `Singleton<T>` | `SingletonService<T>` | — | 0 |
| `YooAssetService` | Skier `Singleton<T>` | `SingletonService<T>` | — | 0 |
| `UIModelManager` | Skier `Singleton<T>` | `SingletonService<T>` | — | 0 |
| `UIManager` | Skier `SingletonMono<T>` | `SingletonBehaviour<T>` | 默认值即匹配（AutoCreate/Persistent 都 true） | 0（102 处 `.Instance` 不变） |
| `CharacterInputSystem` | Battle `Singleton<T>` | `SingletonBehaviour<T>` | 默认值即匹配 | 0（`MainInstance` 保留为别名） |
| `TimerManager`（Battle/Core） | Battle `Singleton<T>` | `SingletonBehaviour<T>` | 默认值即匹配 | 0 |

旧基类**不删除**，加 `[Obsolete]` 指向新基类，保证任何遗漏的引用仍能编译（并给出警告）。

`ModuleHub` 自身继续用 `SingletonMono`（它是框架根，语义特殊：不自动创建 + 手动 DDOL），标 Obsolete 除外。

### 分步提交（每步单独可回滚）

1. 新增 `SingletonService<T>` / `SingletonBehaviour<T>`（无人引用）
2. 迁移 3 个纯 C# 单例
3. 迁移 `UIManager`
4. 迁移 `CharacterInputSystem` / `TimerManager`
5. 旧基类标 `[Obsolete]`

## 3. 第 3 项：启动编排（改口径）

### 原方案的问题

"Boot 里按序 await 资源 → 配置 → UI 配置 → Lua" 会**提前构造** UI 与 Lua。而：

- `UIManager` 是 `LOGIN.scene` 里的根物体（名字 `SkierFramework.UIManager`），BeforeSceneLoad 阶段它还不存在；此时访问 `.Instance` 会触发 **自动创建空物体**，丢掉 Inspector 上的 `width/height/uiBlackType`
- `LuaEnvManager` 现在 `BeforeSceneLoad` 自建、首次 `Require` 才真正加载业务脚本；预初始化只是把开销挪到启动、没有收益
- 启动时间会变长（当前是懒加载）

### 复检：这条链本来就不存在

| 环节 | 现状 | 是否已有顺序保证 |
|---|---|---|
| 资源 | `ModuleHub.Boot.BootResourceAsync` → `ResourceManager.InitializeAsync` | ✅ 已经是唯一的启动入口 |
| UI 配置 | `UIManager.EnsureInitializedAsync`：**内部**串行 resource → layers/camera → `InitUIConfig` | ✅ 自身已串行，且有 `_isInitializing` 防重入 |
| Lua | `LuaEnvManager` 自举 + 懒加载 | 独立，不依赖前两者 |

也就是说：**"散落在各处的启动顺序"并不存在**，唯一需要集中的（资源）早就集中了。硬要在 Boot 里 await 后面两步，是把"懒"改成"急"，属于负优化——和上一轮否掉 P1-2 是同一个坑。

### 改为：启动阶段可观测

```csharp
public enum BootPhase { Resource, Managers, Ready }

/// 等待某个阶段就绪；已过则该阶段立即返回
public UniTask WaitPhaseAsync(BootPhase phase, CancellationToken cancellationToken = default)
```

- 只提供**观测/等待**能力，**不触发**任何系统的初始化
- 业务侧要"确保 UI 就绪"时，用 `await UIManager.Instance.EnsureReadyAsync()`（把现有 private `EnsureInitializedAsync` 提升为 public + 保留原名的转发），而不是等 ModuleHub
- 收益：启动顺序有唯一真相（谁在哪个阶段就绪），且**零行为改变**

## 4. 明确不做

| 不做 | 原因 |
|---|---|
| 新增任何 `IManagerBase` 模块（资源/UI/网络） | 上一轮已论证：收益 ≤ 0，风险 > 0 |
| 在 Boot 里预初始化 UI / Lua | 见 §3，会丢 Inspector 配置、拉长启动 |
| 删除旧单例基类 | 迁移期要保证任何遗漏引用仍可编译；确认无人引用后再单独删 |
| 动 `RootMotion.Singleton<T>` | 第三方插件内部使用 |
