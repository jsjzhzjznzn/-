# 背包拆分：武器背包 / 道具背包（道具无上限）

> 状态：**已实施**（2026-10-30；实测见 §7）
> 需求来源：「背包搞两个部分，一个武器背包一个道具背包，道具背包无限」
> 已确认：道具无限、武器有上限、同一面板两个页签、武器 = 装备实例（`item_type=3`）

---

## 0. 现状

- 服务端 `BagRepository`：单一槽位空间 `BagCapacity = 500` 定长；`player_items(player_id, slot_index)` 只存非空槽；`LoadSlots` 固定 500 长度数组，读写全部按该长度做边界校验；`GrantIntoSlots` 找不到空槽就返回剩余量（调用方转邮件）。
- 客户端 `BagManager`：`Capacity`（服务端下发）+ 定长 `BagSlotInfo[]`；`ApplySlots` 按 `Capacity` 摊平，越界丢弃。
- 界面 `BagView`：6 列虚拟列表，500 格 = 84 行，一行 6 格；右侧详情、底部「加物品/整理」、容量文案「x/500 格」。
- 物品分型：`item_type=3` 为装备（每件一个 `equipment_instance`，不堆叠、独占一格），其余为可堆叠道具。

---

## 1. 设计（单槽位空间 + 两段分区）

不新增表、不新增列，沿用 `player_items.slot_index` 一个连续索引空间，切成两段：

```
slot 0                499 │ 500                         ∞
├── 武器区（500 格）──────┼── 道具区（无上限）──────────────►
```

| 区 | 范围 | 容量 | 满时行为 |
|---|---|---|---|
| 武器 | `[0, 500)` | 固定 500 | 沿用现状：放不下的转邮件 |
| 道具 | `[500, ∞)` | 动态，基数 120 格、按 60 格步长扩 | 自动扩容，永不"满" |

**动态长度推导**（服务端与客户端同一口径，避免协议改动）：

```
itemCapacity = max(120, 向上取整到 60 的倍数(最高道具槽 - 500 + 1))
数组长度      = 500 + itemCapacity
```

为什么不改协议：快照里已经带了 `slot_index`，客户端用「最大 slot_index + 上面的公式」就能推出长度；只有「一件道具都没有」时才依赖基数常量 120。这样 `BagListResponse.capacity` 继续表示**武器区容量**，字段语义不变，不必重跑 proto 生成。

## 2. 服务端改动（`competeserves`）

| 位置 | 改动 |
|---|---|
| 常量 | `BagCapacity` → `WeaponCapacity = 500`；新增 `ItemRegionStart = 500`、`ItemCapacityFloor = 120`、`ItemCapacityStep = 60` |
| `LoadSlots` / `LoadSlotsForUpdate` | 先读行到列表，算出 `maxIndex`，再按 §1 公式定长；`slot_index < WeaponCapacity` 归武器区，其余归道具区（脏数据防御：负索引忽略） |
| `GrantIntoSlots` | 改为接收 `ref BagSlot[] slots`；道具路径找不到空槽时**扩容**（按步长加长数组并把新槽留给本件），装备路径不变（500 格满 → 剩余转邮件） |
| `SwapSlots` | 两侧必须同区：`(from < 500) == (to < 500)`，否则返回「不能跨背包换位」 |
| `Tidy` | 分区整理：武器区按「稀有度降序 → 物品ID → 实例ID」紧凑排布在 `[0,500)`；道具区按「类型 → 稀有度降序 → 物品ID」堆叠紧凑排布在 `[500, ...)`，排完把道具区收缩到实际需要（不小于基数） |
| `ConsumeItem` / `GetSlotItemId` | 边界校验改为「< 数组长度」；`GetSlotItemId` 单行查询的越界判断同样放宽 |
| `MessageHandler.HandleBagList` | `Capacity` 仍填 `WeaponCapacity`；日志补一行道具区容量 |
| `InternalAgentApiServer` | 同 `MessageHandler`：`capacity = WeaponCapacity`（语义 = 武器上限） |

不变：所有写路径仍是 `PlayerWriteLock + 事务 + accounts 行锁 + FOR UPDATE + 差分回写`；装备实例、满包转邮件、任务/唤取入口全部沿用。

## 3. 客户端改动（`RedDotSystem-main`）

| 位置 | 改动 |
|---|---|
| `BagManager` | `Capacity` 语义固定为武器区容量（默认 500）；新增 `WeaponSlotCount`、`ItemCapacity`（按 §1 公式从快照推导）、`IsWeaponSlot(index)`、`SlotCount`；`ApplySlots` 长度 = `SlotCount`，越界保留防御；登录复位同步清 `ItemCapacity` |

| `BagView.prefab` | 新增 `tabWeaponButton` / `tabItemButton`（含选中态底色与下划线），登记 `UIControlData`；标题右侧容量文案沿用 |
| `BagSlotView` | 无需改动（格子只认槽位下标） |

## 5. 老数据兼容

历史数据里道具也占用 `0~499`，分区后这些槽在"武器区"内。处理方式：**读取时不搬家，靠界面上"归属判定"兜底** —— 判定规则用 `item_type`：

- 武器页签：`slot < 500` 且 `item_type == 3`
- 道具页签：`slot >= 500`，或 `slot < 500` 且 `item_type != 3`（历史遗留）

这样老玩家打开背包不会"丢道具"，新发放的道具一律落在 `>=500`。搬家（一次性 `UPDATE player_items SET slot_index = ...`）留到后续清理，不在本次做（涉及实例引用与事务，风险高收益低）。

---

## 6. 风险

| 风险 | 对策 |
|---|---|
| 服务端扩容与客户端基数不一致 → 快照摊不平 | 两边用同一常量：基数 120、步长 60；客户端长度取 `max(基数, 最大槽+1)`，永不小于服务端 |
| 道具区无限增长导致一次快照过大 | 快照只发非空槽（现状如此）；每格一条，千件级仍是小报文 |
| 分区后 `Tidy` 把历史道具搬进道具区 | 允许：整理本身就是"重排"，道具被搬到 `>=500` 达成自然迁移（验证时确认不丢物品） |
| 跨区 `Swap` 的旧请求 | 服务端显式拒绝并给文案；UI 不会产生这种请求 |

### 7.2 与设计稿的差异（以实现为准）

1. **计数按槽位区间统计**（`UsedWeaponCount` = `[0,500)` 非空数，`UsedItemCount` = `[500,…)` 非空数），不是按 `item_type` 统计——这样文案与页签里看到的格子永远一致；历史数据里放在武器区的道具会先显示在武器页，按一次「整理」后按类型迁到道具区。
2. **`Tidy` 里装备溢出保护**：极端情况（武器 >500 件）不会丢物品，多出来的按顺序追加到数组尾部空槽。
