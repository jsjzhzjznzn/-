# 抽卡系统评估与改造方案

> 评估对象：`competeserves/Server`（服务端）+ `RedDotSystem-main`（客户端活动热更层）
> 参照：B 站《讲解游戏抽卡系统设计逻辑》提出的四条原则（分层随机 / 双保底状态 / 逐抽结算 / 服务端权威 + 重试幂等）
> **状态（2026-10-26）**：已完成实施并提交——Unity `bca3f75`、服务端 `1d29941`；实测结论见 §11。
> 下文 §0–§8 保留改造前的评估原文（便于对照），§9/§10 为落地顺序与证据索引。

---

## 0. 结论摘要（改造前）

当前抽卡系统的基础骨架是对的：**结果由服务端裁决**、**扣媒介 / 发奖 / 写流水 / 更新保底在同一个事务里**、**十连是逐抽循环并逐抽推进 5★ 计数**。这三点比很多 Demo 都扎实。

但对照视频里的四个问题，仍有 3 个半没做到：

| 视频原则 | 当前状态 | 判定 |
|---|---|---|
| 随机分两步：先定星级，再定物品 | 只有一层「整池按物品权重 roll」，星级概率是物品权重的副产物 | ❌ 未做到 |
| 保底要记两件事：5★ 计数 + 下一次 5★ 是否必 UP | 只记了 5★ 计数；没有「大保底」状态 | ❌ 未做到 |
| 十连按顺序逐抽结算，中途出金后续重新累计 | 5★ 计数确实逐抽推进；但「十连必 4★」是整批抽完后回头替换第 10 抽 | ⚠️ 半做到 |
| 结果由服务器决定；断网重试不得重复扣券重抽 | 结果服务端裁决、单事务结算；但**没有请求幂等**，重试必然再扣一次、再抽一次 | ❌ 未做到（最严重） |

另外有一个会直接卡死界面的客户端缺陷：**抽卡请求发出后如果连接断开，待回执的 Lua 回调永远不会被调用**，`state.busy` 永远为 `true`，抽卡按钮从此点不动，只能关面板重开。

风险排序（建议实施顺序）：

1. **P0 幂等**：`request_id` + 结果快照重放。这是「能上线」与「不能上线」的分界线。
2. **P1 大保底**：`guaranteed_up` 状态，配合 UP 概率，才是完整的限定池。
3. **P1 分层随机**：星级权重与星级内物品权重拆开，概率可读、可调、可审计。
4. **P1 十连保底改为顺序结算**：第 10 抽前置判定，不再回头改结果。
5. **P2 保底状态独立成表**：不再用 `COUNT(*)` 从流水推算。
6. **P2 `is_pity` 拆语义**：区分「5★ 计数保底 / 十连 4★ 保底 / 大保底」。
7. **P3 客户端断线/超时重试链路**。

## 2. 逐条对照视频四问

### 2.1 问题一：随机怎么抽？——未做到分层

现状 `RollAll`（`GachaRepository.cs:393`）把整池铺成一根尺子，每个物品占自己权重那一段：

```csharp
int totalWeight = pool.Sum(p => p.Weight);
int roll = Random.Shared.Next(totalWeight);
```

后果：

- **星级概率是隐式的**。想知道「5★ 是多少」必须把同星级物品权重加起来再除以总和；改一个填充物权重，5★ 概率也跟着变。策划无法直接写「5★ 0.6%、4★ 5.1%」。
- **UP 概率也是隐式的**。当前 UP 80% 完全依赖 `800 / (800+100+100)`，改一个歪池物品就会改变 UP 率。
- **无法做「同星级内再来一次 UP 判定」**。大保底、UP 率配置都无处安放。

视频的做法是两步：`先定星级 → 再在该星级里定物品`。这是行业标准做法，也是可配置、可审计的前提。

### 2.2 问题二：保底怎么记？——只记了一半

现状 `QueryPityState`（`GachaRepository.cs:134`）：

```sql
SELECT COUNT(*), COALESCE(MAX(CASE WHEN star = 5 THEN draw_seq END), 0)
FROM gacha_records WHERE player_id = @P AND banner_id = @B
```

只推出一个 `pity5_count`。视频强调要分开记两件事：

1. 距离上次 5★ 抽了多少次 —— ✅ 有。
2. **下一次 5★ 是不是必定当期 UP** —— ❌ 没有。

而且还有两个衍生问题：

- **状态是从流水反推的**：每次查保底都要扫该玩家该池的全部流水。抽数一多就是 O(n)，且无法表达「流水没写成功但保底已推进」这类中间态（现在靠同事务回滚兜住，但代价是整单失败）。
- **保底是「按 banner_id」隔离的**：换池（A→B）保底清零。视频里原神两个角色池共享保底；本项目是鸣潮式武器池，是否共享属于产品选择，但当前连「可配置」都没有。

### 2.3 问题三：十连中途出金怎么算？——5★ 对了，4★ 保底错了

现状 `RollBatch`（`GachaRepository.cs:355`）：

```csharp
for (int i = 0; i < count; i++)
{
    bool forced5 = pity + 1 >= banner.Pity5Threshold;
    entry = forced5 ? RollStar(pool, 5) : RollAll(pool);
    pity = entry.Star == 5 ? 0 : pity + 1;
}
// 十连保底：整批结果都 <4★ 时，把最后一抽替换成 4★
if (count == 10 && results.All(r => r.Rarity < 4))
    results[^1] = fourStar;
```

- 5★ 计数：逐抽推进、中途出金后重置 —— ✅ 与视频一致。
- 十连 4★：**先抽完 10 次，再回头把第 10 抽换掉**。这不是「按顺序结算」，而是「批后修正」。问题：
  - 第 10 抽的原始结果被丢弃，但它已经参与过 `batchSeen` / `isNew` 判定（`GachaRepository.cs:372`），
  - 替换出来的 4★ 没有加入 `batchSeen`，同一批里可能重复，
  - 替换件一律标 `is_pity=true`，与 5★ 保底混在一起，历史里看不出是哪种保底，
  - 如果第 10 抽本来抽到了 5★（`All(<4)` 为假）不会替换 —— 结果对；但语义上仍依赖「事后回看」。

正确写法：**在循环内、第 10 抽 roll 之前**判断「前 9 抽是否已有 4★+」，没有就把本次的星级下限抬到 4。这样每一次抽都是独立、顺序、可解释的。

### 2.4 问题四：结果由谁决定？——服务端权威做到了，重试幂等没做

✅ 已做到：

- 客户端只发「我要抽哪个池、几次」，不带任何结果。
- 服务端在同一事务里完成：校验媒介 → roll → 扣媒介 → 入包（满包转邮件）→ 写流水 → 提交。
- 没有「扣了媒介但没入包」或「入包但没扣媒介」的中间态。

❌ 没做到（P0）：

- **没有请求幂等键**。`GachaDrawRequest` 只有 `banner_id`、`count`。
- 客户端 `RequestDraw` 没有超时。如果响应在网络上丢了：
  - 玩家看到「一直在处理」，
  - 关掉面板重开再点 → 服务端**再扣一次媒介、再 roll 一次**，
  - 服务端其实已经把第一次写进库了 —— 玩家的媒介凭空少了一次机会。
- **断线时更糟**：`ClientNetworkManager.ConnectionBroken` 触发后，`pendingDrawCallback` 不会被调用也不会被释放，Lua 的 `state.busy` 停在 `true`，抽卡按钮永久禁用；下次 `ReleasePendingCallbacks`（关面板/活动轮换）才释放，且释放时没有任何提示。

视频里说的「把原来的结果找回来，而不是再扣一次券再抽一遍」，对应的就是：

```
request_id（客户端生成，重试时复用） → 服务端查已结算记录 → 命中则原样重放
```

## 3. 问题清单（按严重度）

### P0-1 缺少请求幂等（断网/超时重试会重复扣费）

- 证据：`ActivityPacket.proto:77` 的 `GachaDrawRequest` 只有 2 个字段；`ActivityShell.cs:376` 无 requestId、无超时。
- 影响：一次网络抖动可能让玩家损失一次十连；无日志可对账。
- 修复：新增 `request_id`，服务端落 `gacha_requests` 快照并在命中时重放（见 §4.5）。

### P0-2 断线后抽卡回调悬空，界面永久忙碌

- 证据：`ActivityShell.cs:376-390` 只置 `pendingDrawCallback`；`ReleasePendingCallbacks`（`:558`）只在关面板 / 活动轮换时调用；没有订阅 `ConnectionBroken`。
- 影响：Lua `state.busy` 永为 `true`（`activity_main.lua.txt:319`），后续点击只弹「唤取处理中」。
- 修复：订阅 `ConnectionBroken` + 12s 超时，回调一个 `retryable=true` 的失败结果并清 `busy`。

### P1-1 缺少「大保底」（下一次 5★ 必 UP）

- 证据：`GachaRepository` 无任何 `guaranteed_up` 字段或状态；`DrawResultItem` 只有 `IsUp`。
- 影响：限定池只有「80% UP」，没有「歪一次下次必中」的保底，长期体验与商业池不一致。
- 修复：`gacha_pity.guaranteed_up` + `up_rate_5` 配置 + roll 时强制 UP。

### P1-2 随机不分层，概率不可读

- 证据：`GachaRepository.cs:393` `RollAll`；`banner_config` 无星级概率列。
- 影响：策划改一个填充物权重会连带改变 5★ 概率；无法表达「5★ 出率 0.6%」。
- 修复：`star_rates_json` + 星级内 roll。

### P1-3 十连保底是批后回溯替换

- 证据：`GachaRepository.cs:381-386`。
- 影响：结果不可解释；`batchSeen` / `isNew` 有轻微错算；`is_pity` 语义混淆。
- 修复：循环内第 10 抽前判定 `has4Plus`，把星级下限抬到 4。

### P2-1 保底状态不独立，靠扫流水推算

- 证据：`GachaRepository.cs:134`。
- 影响：O(n) 扫描；无法表达与流水无关的状态（大保底）；共享保底无从实现。
- 修复：`gacha_pity` 表，流水只做审计。

### P2-2 `is_pity` 一个布尔承担三种语义

- 证据：`GachaRepository.cs:370`（5★ 计数）、`:384`（十连替换）都写 `IsPity=true`。
- 影响：结果卡/详单只能显示「保底」，玩家分不清是 30 抽保底、十连 4★ 保底还是大保底。
- 修复：新增 `pity_kind`（0 无 / 1 5★计数 / 2 十连4★ / 3 大保底），`is_pity` 保留为 `pity_kind != 0` 的兼容视图。

### P2-3 `total_draws` / 详单口径与共享保底会打架

- 现状 `total_draws` 是「本 banner 累计」，保底若共享，两个数会不同。必须在协议注释与 UI 文案上区分「本池累计」与「保底进度（共享池）」。

### P3-1 其他

- `RollStar` 在目标星级为空时静默回退整池（`GachaRepository.cs:409`），配置写错会悄悄降级，建议打日志。
- `GachaHistoryResponse` 不返回 `guaranteed_up`，客户端首屏无法显示大保底状态。
- `GetTotalDraws` 与 `QueryPityState` 各扫一遍流水，可合并。
- 抽卡成功后 `bag.GetSlots()` 又打开一条新连接重读，事务内已有快照可直接转化（非必须）。

## 4. 改造方案

### 4.1 目标架构

```
客户端
  request_id = GUID（每次点击生成；重试复用）
        │
        ▼
服务端 Handler
  校验登录 / banner / count / request_id 长度
        │
        ▼
GachaRepository.Draw(playerId, bannerId, count, requestId)
  PlayerWriteLock + 单事务 + accounts 行锁
    ① gacha_requests 命中？ → 直接反序列化快照返回（replayed=true，零扣费）
    ② 读背包快照，校验媒介
    ③ 读/初始化 gacha_pity(pity_group)
    ④ 逐抽：
         a. 5★ 计数到阈值？         → 星级=5（pity_kind=1）
         b. 第 10 抽且前 9 抽无 4★+？→ 星级下限=4（pity_kind=2）
         c. 否则按 star_rates 抽星级
         d. 星级内抽物品：
              大保底 && 该星级有 UP → 强制 UP（pity_kind=3）
              否则按 up_rate_{star} 判定是否走 UP 子池
         e. 逐抽更新 pity5_count / guaranteed_up
    ⑤ 扣媒介 → 逐件入包（满包转邮件）
    ⑥ 写 gacha_records（含 pity_kind）+ UPSERT gacha_pity
    ⑦ 写 gacha_requests 快照（同一事务）
  COMMIT
        │
        ▼
响应 results + pity5 + guaranteed_up + replayed + 背包快照
```

### 4.2 数据库变更（Migrations/016_AddGachaPity.sql）

`banner_config` 增列（MySQL 无 `ADD COLUMN IF NOT EXISTS`，用 `information_schema` 幂等判断，照 `QuestRepository.EnsureTable` 的写法）：

| 列 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `pity_group` | INT | 0 | 0 = 本池独立；>0 = 同组共享保底（A/B 都设 1 即共享） |
| `star_rates_json` | TEXT NULL | NULL | `[{"star":5,"weight":60},{"star":4,"weight":510},{"star":3,"weight":9430}]`；空 = 兼容旧整池权重 |
| `up_rate_5` | INT | 50 | 5★ 出 UP 的百分比（0~100），大保底时忽略 |
| `up_rate_4` | INT | 0 | 4★ 出 UP 的百分比；本项目 4★ 无 UP，默认 0 |

新表：

```sql
CREATE TABLE IF NOT EXISTS `gacha_pity` (
  `player_id`      INT     NOT NULL,
  `pity_group`     INT     NOT NULL,
  `pity5_count`    INT     NOT NULL DEFAULT 0 COMMENT '距上次 5★ 的抽数',
  `guaranteed_up`  TINYINT NOT NULL DEFAULT 0 COMMENT '下一次 5★ 是否必 UP（大保底）',
  `total_draws`    INT     NOT NULL DEFAULT 0 COMMENT '该保底组累计抽数（统计用）',
  `updated_at_ms`  BIGINT  NOT NULL,
  PRIMARY KEY (`player_id`, `pity_group`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='抽卡保底状态（唯一真相，流水只做审计）';

CREATE TABLE IF NOT EXISTS `gacha_requests` (
  `player_id`     INT          NOT NULL,
  `request_id`    VARCHAR(64)  NOT NULL,
  `banner_id`     INT          NOT NULL,
  `draw_count`    INT          NOT NULL,
  `response_json` MEDIUMTEXT   NOT NULL COMMENT '首次结算的完整回执快照（含结果/保底/背包槽位）',
  `created_at_ms` BIGINT       NOT NULL,
  PRIMARY KEY (`player_id`, `request_id`),
  KEY `idx_created` (`created_at_ms`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='抽卡幂等表（重试重放，不重复扣费）';
```

`gacha_records` 增列 `pity_kind TINYINT NOT NULL DEFAULT 0`（0 无 / 1 5★计数 / 2 十连4★ / 3 大保底）。

迁移期初始化：`gacha_pity` 无记录时，由 `gacha_records` 首次反推并落行（保证老玩家保底不丢）：

- `pity5_count` = 该保底组内按 `created_at_ms, banner_id, draw_seq` 排序后、最后一条 5★ 之后的记录数；
- `guaranteed_up` = 最后一条 5★ 是否非 UP（用 `banner_config.pool_json` 的 `is_up` 反查）；
- 没有 5★ → `0/false`。

### 4.3 协议变更（ActivityPacket.proto，全部为新增字段，向后兼容）

```proto
message GachaDrawRequest {
  int32  banner_id  = 1;
  int32  count      = 2;
  string request_id = 3;   // 新增：客户端生成的幂等键；空 = 不做幂等（老客户端）
}

message GachaResultItem {
  // ... 1-7 不变
  int32 pity_kind = 8;     // 新增：0 无 1 5★计数 2 十连4★ 3 大保底
}

message GachaDrawResponse {
  // ... 1-8 不变
  int32 guaranteed_up = 9; // 新增：本次抽后，下一次 5★ 是否必 UP
  bool  replayed      = 10;// 新增：true = 这是同一 request_id 的原结果重放（未扣费）
}

message GachaHistoryEntry {
  // ... 1-7 不变
  int32 pity_kind = 8;     // 新增
}

message GachaHistoryResponse {
  // ... 1-5 不变
  int32 guaranteed_up = 6; // 新增：用于首屏显示大保底
}
```

兼容性：

- 老客户端不带 `request_id` → 服务端沿用旧行为（不做幂等），不会报错。
- 新客户端连老服务端 → 新字段被忽略；客户端在缺少 `request_id` 回执时按普通结果处理。
- `build_proto.bat` 三端同步（Server/Generated + Assets/Game/Scripts/Generated）。

### 4.4 服务端算法（关键改动）

```csharp
// ── 星级层 ──
int RollStar(BannerConfig b, int minStar)
{
    var tiers = b.StarRates.Where(t => t.Star >= minStar && t.Weight > 0).ToList();
    if (tiers.Count == 0) return 0;         // 0 = 走旧整池权重
    int total = tiers.Sum(t => t.Weight);
    int r = Random.Shared.Next(total);
    foreach (var t in tiers) { r -= t.Weight; if (r < 0) return t.Star; }
    return tiers[^1].Star;
}

// ── 星级内 ──
(PoolEntry Entry, bool WasUp) RollItem(BannerConfig b, int star, bool forceUp)
{
    var tier = b.Pool.Where(p => p.Star == star).ToList();
    if (tier.Count == 0) { LogWarn($"卡池 {b.BannerId} 缺 {star}★ 条目，回退整池"); tier = b.Pool; }

    var up = tier.Where(p => p.IsUp != 0).ToList();
    var normal = tier.Where(p => p.IsUp == 0).ToList();
    if (up.Count == 0) return (RollAll(tier), false);   // 该星级无 UP

    int rate = star >= 5 ? b.UpRate5 : star == 4 ? b.UpRate4 : 0;
    bool takeUp = forceUp || (rate > 0 && Random.Shared.Next(100) < rate);
    if (takeUp) return (RollAll(up), true);
    if (normal.Count > 0) return (RollAll(normal), false);
    return (RollAll(tier), false);
}
```

逐抽主循环：

```csharp
int pity = state.Pity5Count;
bool guaranteedUp = state.GuaranteedUp;
bool has4Plus = false;

for (int i = 0; i < count; i++)
{
    bool forced5   = pity + 1 >= banner.Pity5Threshold;
    bool tenGuard  = count == 10 && i == 9 && !has4Plus;

    int star;
    if (forced5)       star = 5;
    else if (tenGuard) star = RollStar(banner, minStar: 4);   // 4 或 5，按权重
    else               star = RollStar(banner, minStar: 0);

    // 旧配置兼容：star == 0 时整池 roll，用 entry.Star
    var (entry, wasUp) = star == 0
        ? RollAllLegacy(banner)                                 // 写日志提示配置待迁移
        : RollItem(banner, star, forceUp: star == 5 && guaranteedUp);

    int pityKind = 0;
    if (star == 5 && guaranteedUp && wasUp) pityKind = 3;       // 大保底
    else if (forced5)                       pityKind = 1;
    else if (tenGuard)                      pityKind = 2;

    // 顺序更新状态（这一抽结算完立刻生效，下一抽用它）
    if (entry.Star >= 4) has4Plus = true;
    pity = entry.Star == 5 ? 0 : pity + 1;
    if (entry.Star == 5)
        guaranteedUp = TierHasUp(banner, 5) ? !wasUp : false;
}
```

说明：

- `tenGuard` 在第 10 抽 roll **之前**判定，不再回头替换。
- `pityKind=3` 优先于 `1`：如果这一抽同时是 30 抽保底和必 UP，玩家更关心「大保底生效了」。
- `guaranteed_up` 只在 5★ 时更新；4★ 不影响。
- 若该星级没有 UP 条目（例如 4★），`wasUp=false` 且不清空 5★ 的大保底状态（状态按星级独立理解，实现上只在 5★ 分支写）。

### 4.5 幂等设计

**客户端**

- 每次点击「唤取一次/十次」生成 `request_id = Guid.NewGuid().ToString("N")`。
- 请求在途时再次点击 → 直接拒绝（现有单在途逻辑）。
- 12 秒未回执 / `ConnectionBroken` → 回调 `retryable=true` 的失败结果，保留 `lastDrawRequestId + bannerId + count`。
- 玩家再次点击同一按钮 → 用同一个 `request_id` 重发（不是新 ID）。
- 服务端命中幂等记录 → 返回原结果，`replayed=true`，客户端提示「已恢复上次唤取结果」，不再扣费。

**服务端**

- 事务第一步（背包校验之前）：

```sql
SELECT `response_json` FROM `gacha_requests`
WHERE `player_id`=@P AND `request_id`=@R FOR UPDATE
```

命中 → 反序列化，`replayed=true` 返回；不命中 → 正常结算，最后写入快照。

- `request_id` 为空 → 跳过幂等（老客户端）。
- 长度 > 64 → 直接拒绝（防脏数据）。
- 并发同一 ID：`PlayerWriteLock` 已按玩家串行；`PRIMARY KEY(player_id, request_id)` 兜底，捕获 1062 重复键后重读并重放。
- 快照内容：`message / pity5_count / pity5_threshold / total_draws / guaranteed_up / results[] / slots[]`。
  `configs[]` 不入快照（静态表，重放时按结果 item_id 现查），避免配置改版后回执不一致。
- 保留窗口：默认 7 天，启动时清理 `created_at_ms < now - 7d`；也可在每次 Draw 时以 1% 概率顺带清理（建议后者，避免启动长事务）。
- 流水不重复写：重放路径直接返回，不进入结算段。

**为什么不用「幂等键 = bannerId + drawSeq」**：drawSeq 只有在结算时才知道，无法在请求阶段判重；且玩家正常连抽会得到连续 seq，无法区分「重试」与「新抽」。

## 6. 兼容、迁移与回滚

### 6.1 兼容

- 协议全部是新增字段，老客户端/老服务端都能跑。
- `star_rates_json` 为空时走旧的整池权重 roll（只在日志里提示「该池未配置星级权重」），保证未迁移的池行为不变。
- `guaranteed_up` 在旧池（`up_rate_5` 默认 50）上会开始生效 —— 这是行为变化，需要运营知会。若不想改变现网体验，可把 `up_rate_5` 设为 `100`（等价于当前的 80% 权重效果就不对了）。**建议直接用新配置**：`up_rate_5=80` 复刻当前体感，同时获得大保底。

### 6.2 老数据初始化

- 首次 `Draw` 或 `HandleGachaHistory` 读不到 `gacha_pity` 行时，用 §4.2 的算法从流水反推并落行。
- 反推只发生一次；之后以表为准。
- `gacha_records.pity_kind` 老数据默认 0，历史页对老记录不显示保底标签（可接受）。

### 6.3 回滚

- 服务端：保留旧 `RollAll` 分支；把 `star_rates_json` 置 NULL 即回到旧 roll。
- 幂等：服务端可开关（环境变量 `CS_GACHA_IDEMPOTENCY=0`），关闭后忽略 `request_id`。
- 客户端：`ActivityBridge.RetryDraw` 是新增 API，Lua 旧版本不调用即无影响。

## 8. 风险与待确认决策

### 8.1 需要你拍板的决策

1. **A/B 池是否共享保底？** 建议：共享（`pity_group=1`），符合视频；若希望各池独立，改成 `pity_group=banner_id`，代码不用动。
2. **大保底范围？** 建议：仅 5★（歪一次下一只必 UP）；4★ 不做大保底。是否要 4★ UP 也做？
3. **UP 概率取多少？** 建议：`up_rate_5=80`（复刻当前 80% 体感），正式池可改 50。
4. **演示保底 30 抽是否保留？** 建议保留；`star_rates` 用当前权重（5★≈16%）以免测试节奏变慢。
5. **幂等保留窗口？** 建议 7 天。
6. **客户端超时时长？** 建议 12 秒（服务端单次抽卡实测 < 200ms，12s 足以覆盖抖动）。
7. **是否本期就发新热更包？** Lua 展示改动需要发版（1.2.0）；若想先只上服务端，可以让客户端继续用旧 Lua（会忽略新字段，但不显示大保底）。

### 8.2 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 行为变化 | 引入大保底后，老玩家历史 5★ 若为歪，服务端反推会把 `guaranteed_up` 置 true，下一次 5★ 直接必 UP | 上线前用 SQL 预置/清理；或首版把反推结果统一置 false（更保守） |

| 幂等表膨胀 | 每次抽卡一行（含结果 JSON） | 7 天清理；按 `created_at_ms` 索引删除；单行 < 4KB |
| 热更包版本 | Lua 改了没发版 → 客户端看不到新标签 | 实施时同步 `BuildAndPublish`，并在文档记录版本号 |

- 不做「跳过动画重新 roll」——已确定结果永不重算（当前也没有这个问题）。
- 不做卡池保底继承到「不同类型的池」（武器池 ↔ 角色池）。
- 不做客户端本地预测/预演结果（会泄漏概率与结果）。
- 不做抽卡结果的任务/生涯联动（既有缺口，另立需求）。

### 11.6 未覆盖 / 注意事项

1. **“服务端已结算但响应丢失”** 的客户端重放未在 Unity 里真实制造（需注入丢包）；服务端重放路径已用 TestClient 证明，客户端 `retryable/retryPending/复用 request_id` 映射为代码路径 + 超时/断线回调。
2. 唤取活动（`type=1`）的种子排期仍是首次启动的相对时间，过期后需 `--activity-rotate 1` 拉回当前窗口；签到（`type=2`）已改为**服务端启动时自动续期 30 天**，也可用 `--activity-rotate 3` 手动续期（2026-10-26 修复：此前续期只处理 `type=1`，导致唤取恢复后侧栏只剩 1 个活动，看起来像签到被删）。
3. `gacha_pity` 首次缺失时从流水惰性反推，反推出的 `guaranteed_up` 可能让老玩家下一次 5★ 直接必 UP；如需保守上线，可把反推结果统一置 false（当前实现按真实历史反推）。
4. 唤取入包仍未联动任务收集类/生涯统计（`RaiseItemGained` 未接），属既有缺口，不在本次范围。
5. **xLua 生成目录坑**：本项目 xLua 运行时代码在 `Assets/ThirdParty/XLua`，但生成器常量原本指向 `Assets/XLua/Gen`；直接跑 `XLua/Generate Code` 会生成第二套 Wrap 并触发上千条 `CS0101`。已把 `GeneratorConfig.common_path` 改到 `Assets/ThirdParty/XLua/Gen/`，以后不要再生成到 `Assets/XLua`。

### 11.7 签到活动丢失问题（2026-10-26 追加修复）

**现象**：抽卡改造后活动中心只剩「长刃唤取·苍鳞」，签到不见了。

**原因**：签到排期（`activity_config #3`）的窗口是首次种子时的「启动时刻 + 7 天」，早已过期；`GmRotate` 只处理 `type=1`，把唤取拉回来的同时不会给签到续期；活动列表只返回当前时间窗内的行，所以签到从侧栏消失。数据与 `player_sign_records` 均未删除。

**修复**：
- `SeedActivityConfigs` 末尾调用 `RenewExpiredSignIn`：`type=2 AND end_at_ms <= now` 的行自动续期（start = now-1h，end = now+30 天）。
- `GmRotate` 显式指定 `type=2` 活动时走「只续期」分支，不动正在进行的唤取（`--activity-rotate 3`）。

**验证**：
- 服务端重启后 `--activity-list` 返回 2 个活动（#1 唤取剩余 6.23 天、#3 签到剩余 29.99 天）。
- Unity 重开活动中心：`serverActivities=2`、侧栏 `长刃唤取·苍鳞、签到`；切到签到页后 `signDays=1/7`、`signCells=7`、按钮「签 到」可用。
