# 对战好友邀请功能方案

> 目标读者：后续维护战斗联机 / 好友 / UI 框架的同学。
> 本文是施工蓝图，代码落地后请在各节追加「实测结论」，避免文档与实现漂移。

---

## 0. 一句话方案

把「邀请」做成**游戏服（8888）上的信令**，把「进房」仍交给**NGO Listen Server（7777）**：

```
房主点击「邀请好友」→ 8888 建房+发邀请 → 8888 推给在线好友
     → 好友弹窗点「同意」→ 8888 回执房主地址 → 好友 NGO 直连 7777 → 进入房间选人
```

服务器**不托管对战流量**，只做「谁在邀请谁、凭据是否有效、结果通知对方」这三件事。这样既不动现有战斗架构，又能拿到离线/过期/归属校验/拒绝回执这些只有服务端能给的语义。

## 1. 目标与验收

### 1.1 必须做到

1. 对战大厅与对战房间内都有「邀请好友」入口。
2. 房主无需先手动建房：点「邀请好友」自动创建 Host 房间再打开邀请面板。
3. 邀请面板列出好友（头像/名字/**在线状态**），在线好友可一键邀请。
4. 被邀请方**在任意界面**收到弹窗（类似火影/三角洲的对战邀请卡），显示邀请人、倒计时、同意/拒绝。
5. 点「同意」**直接进入房间**（选人 → 准备 → 房主开始），不再输入 IP。
6. 房主能收到「已接受 / 已拒绝 / 已过期 / 对方离线」四种结果反馈。
7. 对局双方的昵称在对战房间内正确显示（现在只显示英雄名）。

### 1.2 明确不做（本期）

- 不做公网 NAT 穿透 / 中继（仍要求同一局域网或同机）。
- 不做观战、3 人以上房间、邀请入队。
- 不做服务端权威的房间列表（房间仍只存在于房主的 NGO 进程里）。
- 不改战斗场景与 `RoomState` 的选人/准备/开局语义。

### 1.3 验收口径

- 协议级：邀请/同意/拒绝/取消/过期/非好友/离线/重复邀请 8 条用例全绿。
- 客户端：弹窗出现时机、同意后的连接动作、忙时自动拒绝、房主结果提示，用运行时断言（不是截图）验证。
- 视觉：弹窗与邀请面板样式用一次录屏门禁（VLM 只验形态与中文渲染）。

## 2. 现状盘点（施工前必须知道的事实）

### 2.1 两条互不相干的链路

| 链路 | 实现 | 端口 | 谁在管 |
| --- | --- | --- | --- |
| 账号/好友/聊天/邮件/任务 | `ClientNetworkManager`（TCP + protobuf，帧=`[len][msgId][body]`） | 8888 | `competeserves/Server`（.NET 8） |
| 对战联机 | `BattleNetworkLauncher` + NGO 1.13 `NetworkManager`/`UnityTransport` | 7777 | **房主进程自己**（Listen Server） |

结论：**服务器不知道任何房间的存在**。邀请要做，必须让 8888 临时充当「介绍人」，它只需要知道房主自报的 `address:7777`。

### 2.2 对战侧代码

- `Assets/Game/Scripts/Battle/Lobby/BattleLobbyView.cs`：创建房间 / 加入房间 / 关闭，字段 `createRoomButton`、`joinRoomButton`、`closeButton`、`statusText`。
- `Assets/Game/Scripts/Battle/Lobby/JoinRoomView.cs`：手填 IPv4 → `BattleNetworkLauncher.StartClientAsync(ip)`。
- `Assets/Game/Scripts/Battle/Lobby/BattleRoomView.cs`：英雄选择 + 3D 预览 + 准备 + 房主开始；对手栏 `enemyNameText` 当前显示的是**英雄名**，没有玩家昵称。
- `Assets/Game/Scripts/Battle/Network/BattleNetworkLauncher.cs`：`StartHostAsync()` / `StartClientAsync(address)` / `ShutdownAndDestroy()`，固定端口 `DefaultPort = 7777`，`SetConnectionData(DefaultAddress, 7777, "0.0.0.0")`（监听全网卡）。
- `Assets/Game/Scripts/Battle/Network/RoomState.cs`：服务端裁判，`RequiredPlayerCount = 2`、`HeroCount = 2`，NamedMessage 已有 6 条（选人/准备/查询对端）；`_players` 里只有 `ClientId → (IsReady, CharId)`，**没有玩家身份**。

关键约束：`BattleRoomView.OnClose()` 会在非战斗跳转时 `ShutdownAndDestroy()`。所以**房主必须停在房间界面等好友**，邀请入口必须也在房间界面里。

### 2.3 服务端侧可复用的能力

| 能力 | 位置 |
| --- | --- |
| 玩家在线判定 | `SessionManager.Instance.GetSessionByPlayerId(pid)` / `PlayerManager.Instance.GetPlayer(pid)` |
| 好友关系校验 | `new FriendRepository().AreFriends(a, b)` |
| 昵称解析 | `new AccountRepository().QueryPlayer(pid)` → `(found, name)` |
| 主动推送 | `session.Send(MessageID.Xxx, msg)` |
| 一次性凭据 + TTL + 原子摘除 | 先例：`Database/DungeonRepository.cs` 的 60s 掉落令牌 |

### 2.4 UI 框架约束

- 新增界面三件套：`UIType` 枚举成员 → `UIConfig.json` 条目 → **与 uiType 同名的 `UIView` 子类**（框架按类名解析）。
- `UIConfig.json` 的 path 指向 `Assets/Game/UI/**`；YooAsset `ui` 包按**目录**收集 `Assets/Game/UI`，新预制体自动进包，无需改收集配置。
- 弹窗用 `isWindow: true`（不暂停下层界面）+ 全屏 Backdrop 挡点击，`uiLayer: TopLayer`。
- 预制体由 `Assets/Game/Scripts/Battle/Lobby/Editor/BattleLobbyPrefabBuilder.cs`（菜单 `Tools/Battle/P3 一键构建`）程序化生成，绑定表写在 `FinishPrefab` 里。

## 3. 核心设计决策

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| D1 | 信令走 **8888**，对战走 **7777** | 复用现成登录态/好友关系/推送能力，零改造战斗架构 |
| D2 | 邀请凭据由**服务端**持有（`inviteId`），响应时只认 `inviteId` | 客户端不能伪造"我要进某人的房"；地址也由服务端转交，避免任意客户端下发 IP |
| D3 | 房主地址由**房主客户端自报**（`GetLocalIPv4()`），服务端只做透传 | 服务器在 8888 看到的只是各自到服务器的连接地址，无法推断房主对好友的可达地址 |
| D4 | 一个房主同时只能有 **1 条待回应邀请**；邀请 **60s** 过期 | 1v1 房间先到先得会让第二个同意者拿到"房间已满"，体验差；单条 + 可取消最干净 |
| D5 | 邀请是**单次**的：同意/拒绝/过期/取消都立即销毁记录 | 防重放；避免同一条邀请被点两次进入两个不同状态 |
| D6 | 服务器**不校验**房主是否真的开着房（无从校验） | 好友同意后连接失败是正常分支，客户端要给明确兜底文案，而不是假装成功 |
| D7 | 收到邀请时若本机**已有联机会话**（在房间/在战斗），自动拒绝并回执房主 | 与真实游戏一致；避免把玩家从对局里拽出来 |
| D8 | 对手昵称靠「邀请结果里带的 `playerId+name` 缓存」＋ NGO 侧 `Hello(playerId)` 对齐 | NGO 的 `clientId` 与账号 `playerId` 没有天然映射；手动填 IP 进房时退化为 `玩家{id}` |

## 4. 用户流程与时序

### 4.1 房主发起邀请

```
房主                                8888                      好友(在线)
 │ 点「邀请好友对战」                   │                          │
 ├─ BattleNetworkLauncher.StartHost() ──► (7777 监听)              │
 │ 打开 BattleInviteView（好友列表）    │                          │
 │ 点某个好友的「邀请」                 │                          │
 ├─ BattleInviteRequest{target,addr} ─► │                          │
 │                                      ├ 校验:登录/好友/在线/配额   │
 │ ◄─ BattleInviteResponse{inviteId} ───┤                          │
 │                                      ├─ BattleInviteNotify ───► │
 │ 「等待 XXX 回应…」（可取消）           │                          │  弹窗：XXX 邀请你对战 (60s)
 │                                      │                          │  点「同意」
 │                                      │ ◄─ BattleInviteRespond ──┤
 │ ◄─ BattleInviteResultNotify{accepted}┤                          │
 │                                      ├─ RespondResponse{addr} ─►│
 │ 「XXX 已接受，正在连接…」              │                          │ NGO StartClient(addr:7777)
 │                                      │                          ├──────────► 房主 7777
 │ RoomState: 玩家 1 进入房间，座位 1     │                          │ 进入 BattleRoomView
 │ 对手栏显示 XXX 的昵称                 │                          │ 选人/准备
```

### 4.2 拒绝 / 过期 / 离线

| 情况 | 服务端动作 | 房主看到 | 好友看到 |
| --- | --- | --- | --- |
| 拒绝 | 销毁邀请，推 `ResultNotify{result=declined}` | 「XXX 拒绝了邀请」 | 弹窗关闭 |
| 60s 无响应 | 定时清理，推 `ResultNotify{result=expired}` | 「邀请已过期」 | 弹窗自动消失 |
| 房主取消 | 销毁邀请 | 面板恢复可邀请 | 弹窗消失（下一条邀请可正常展示） |
| 好友离线 | 立即返回 `InviteResponse{success=false,"对方不在线"}` | 面板红字提示，不产生邀请 | — |
| 好友在对局中 | 好友端自动拒绝 | 「XXX 正在对战中」 | 只有一条轻提示，不弹窗 |

### 4.3 客户端状态机（好友侧）

```
Idle ──收到 Notify──► Showing(弹窗)
                        ├─ 同意 ──► Connecting(StartClientAsync) ──成功──► InRoom
                        │                                   └─失败──► Idle + 错误提示
                        ├─ 拒绝 ──► Idle (发 Accept=false)
                        └─ 超时 ──► Idle (本地自动关闭)
```

### 5.2 字段表

```protobuf
message BattleInviteRequest {
  int32  target_player_id = 1;   // 被邀请的好友ID（必须是好友且在线的校验在服务端）
  string room_id          = 2;   // 房主本次房间的标识（GUID，仅用于日志/取消归属）
  string host_address     = 3;   // 房主自报的 IPv4（好友用它直连 7777）
  int32  host_port        = 4;   // 固定 7777；留字段是为将来可配置
}

message BattleInviteResponse {
  bool   success     = 1;
  string message     = 2;   // 失败原因（中文直出 UI）
  int64  invite_id   = 3;   // 服务端生成，同意/拒绝时原样带回
  int64  expire_at_ms= 4;   // Unix 毫秒，客户端倒计时用它（禁用本地时长推算）
}

message BattleInviteNotify {
  int64  invite_id        = 1;
  int32  from_player_id   = 2;
  string from_player_name = 3;   // 服务端解析，客户端不回查
  string host_address     = 4;
  int32  host_port        = 5;
  int64  expire_at_ms     = 6;
  string room_id          = 7;
}

message BattleInviteRespondRequest {
  int64 invite_id = 1;   // 归属校验：只有 target_player_id 能回应
  bool  accept    = 2;
  string reason   = 3;   // 客户端拒绝原因（"正在对战中" 等），可空
}

message BattleInviteRespondResponse {
  bool   success          = 1;
  string message          = 2;
  string host_address     = 3;   // accept=true 才有值
  int32  host_port        = 4;
  int32  host_player_id   = 5;
  string host_player_name = 6;
  string room_id          = 7;
}

message BattleInviteResultNotify {
  int64  invite_id          = 1;
  int32  target_player_id   = 2;
  string target_player_name = 3;
  int32  result             = 4;   // 1=accepted 2=declined 3=expired 4=cancelled
  string message            = 5;   // 直出文案
  string room_id            = 6;
}

message BattleInviteCancelRequest { string room_id = 1; int64 invite_id = 2; } // invite_id=0 表示按 room_id 全取消
message BattleInviteCancelResponse { bool success = 1; string message = 2; int32 cancelled = 3; }
```

## 6. 服务端设计

### 6.1 新增 `Manager/BattleInviteService.cs`

纯内存注册表（对战邀请是短命信令，不需要落库；进程重启即全部失效是正确语义）。

```csharp
sealed class BattleInvite {
    public long   InviteId;
    public int    InviterId;
    public string InviterName;
    public int    TargetId;
    public string HostAddress;
    public int    HostPort;
    public string RoomId;
    public long   ExpireAtMs;   // 单调时钟 + 60s
}

static class BattleInviteService {
    const int TtlMs            = 60_000;  // 邀请有效期
    const int InviterCooldownMs= 1_500;   // 同一房主两次邀请最小间隔
    static readonly ConcurrentDictionary<long, BattleInvite> invites;
    static readonly ConcurrentDictionary<int, long> inviterCurrent;  // 房主 → 当前邀请（1 条上限）
    static readonly ConcurrentDictionary<int, long> lastInviteTicks; // 限频

    static bool TryCreate(int inviterId, string inviterName, int targetId,
                          string address, int port, string roomId,
                          out BattleInvite invite, out string error);
    static bool TryTake(long inviteId, int responderId, out BattleInvite invite);  // 原子摘除
    static int  CancelByInviter(int inviterId, long inviteId, string roomId);
    static int  CancelAllFor(int inviterId);      // 房主退出/断线时
    static List<BattleInvite> SweepExpired(out ...);  // 定时/惰性清理并返回过期项
}
```

`TryCreate` 的校验链：

1. `inviterId <= 0 || targetId <= 0` → "参数错误"
2. `inviterId == targetId` → "不能邀请自己"
3. `!AreFriends(inviterId, targetId)` → "对方不是你的好友"
4. `string.IsNullOrWhiteSpace(address) || port <= 0` → "房主地址无效"
5. 冷却未过 → "邀请太频繁，请稍后再试"
6. `inviterCurrent` 已有在途邀请 → "已有待回应的邀请，请先取消"
7. 目标不在线 → "对方不在线"
8. 目标正在对本房主…（无此语义，跳过）

并发：同一会话串行处理、跨会话并发，用 `ConcurrentDictionary` + `TryRemove`（原子摘除）保证"两个同意只有一个人成功"。

### 6.2 新增 `Handler/BattleHandler.cs`

```csharp
public static void HandleBattleInvite(ClientSession session, ReadOnlySpan<byte> body)
public static void HandleBattleInviteRespond(ClientSession session, ReadOnlySpan<byte> body)
public static void HandleBattleInviteCancel(ClientSession session, ReadOnlySpan<byte> body)
```

发送侧关键点：
- 身份只认 `session.PlayerId`（与聊天一致，客户端传不了别人的 ID）。
- 昵称用 `AccountRepository.QueryPlayer`。
- 推送失败（收件人刚掉线）要回滚：`TryCreate` 成功后 `GetSessionByPlayerId == null` → 撤销邀请并返回"对方不在线"。
- 同意成功时：先 `Send(RespondResponse{addr...})` 给好友，再 `Send(ResultNotify{accepted})` 给房主；两封信互相独立，任一失败只记日志。

### 6.3 过期清理

- 惰性：每次 `TryCreate` / `TryRespond` 前 `SweepExpired()`。
- 主动：`Program.cs` 里挂一个 5s 的 `System.Threading.Timer`（与 `AgentReminderService` 同风格），把过期项推 `ResultNotify{expired}` 给仍在线房主。
- 断开清理：`SocketServer` 的会话关闭路径调 `BattleInviteService.CancelAllFor(playerId)`（作为邀请方）与 `CancelByTarget(playerId)`（作为被邀请方），避免房主闪退后好友点同意连到一个死地址。

### 6.4 路由

`Handler/MessageHandler.cs` 的 `switch` 增加三条：

```csharp
case MessageID.BattleInviteRequest:        BattleHandler.HandleBattleInvite(session, body); break;
case MessageID.BattleInviteRespondRequest: BattleHandler.HandleBattleInviteRespond(session, body); break;
case MessageID.BattleInviteCancelRequest:  BattleHandler.HandleBattleInviteCancel(session, body); break;
```

### 7.2 新增 `Assets/Game/Scripts/Battle/Invite/BattleInviteManager.cs`

`MonoBehaviour` 单例 + `RuntimeInitializeOnLoadMethod(BeforeSceneLoad)` 自举 + `DontDestroyOnLoad`（照 `ChatManager` 先例）。它是唯一订阅邀请推送的地方，保证"在 zhuye / 背包 / 好友面板里都能弹"。

职责：

| 方法/字段 | 说明 |
| --- | --- |
| `Instance` | 全局单例 |
| `OnInviteNotify(notify)` | 入队；`BattleNetworkLauncher.HasSession` 为真 → 立即回 `accept=false, reason="正在对战中"` 并只弹轻提示 |
| `Accept()` / `Decline()` | 由弹窗调用；同意后 `StartClientAsync(host_address)`，成功则关大厅/房间/邀请面板并 `Open(BattleRoomView)` |
| `PendingInvite` | 当前展示中的邀请（含 `expireAtMs`，按服务器时间倒计时） |
| `OnResultNotify` | 房主侧：把结果转成 `BattleToast`（复用 `BattleInviteView` 的状态行或全局 toast 回调） |
| `KnownPlayerNames` | `Dictionary<int,string>`：记录 `ResultNotify{accepted}` 带来的 `target_player_id → name`，供 `RoomState` 对齐 NGO `clientId` |
| `ResetForAccountSwitch()` | 登录成功时清缓存，防串号（照 `ChatManager.OnLoginResponse`） |

倒计时用**服务器给的 `expire_at_ms`**，与 `ActivityListResponse.server_time_ms` 同口径，避免本地时钟漂移。

## 9. 边界与异常

| 场景 | 行为 |
| --- | --- |
| 好友不在线 | 邀请直接失败（不产生记录），面板红字"对方不在线" |
| 好友正在对局 | 好友端自动拒绝，房主收到"XXX 正在对战中" |
| 房主重复点邀请 | 服务端 1.5s 冷却 + 单条上限，面板按钮本地也置灰 |
| 两人同时同意 | `TryTake` 原子摘除，后到者返回"邀请已失效" |
| 好友同意但房主已关房 | `StartClientAsync` 超时/失败 → 弹窗显示兜底文案，不回大厅崩溃 |
| 好友同意但不在同一局域网 | 同上（NAT 限制，文案提示"请确认与房主在同一网络"） |
| 房主闪退 | 8888 侧会话关闭 → `CancelAllFor` → 好友弹窗消失 |
| 好友在战斗中收到邀请 | `HasSession == true` → 自动拒绝 |
| 邀请面板开着时第二人入房 | 面板自动关闭并 toast"XXX 已加入房间" |
| 断线重连 | `ClientNetworkManager.ConnectionBroken` → Manager 关闭弹窗、清空在途邀请 |

### 12.2 客户端（Unity Play）

1. 登录 `test` → 打开对战大厅 → 点「邀请好友对战」→ 断言 `BattleNetworkLauncher.IsHost == true` 且 `BattleInviteView` 已打开。

3. 用 TestClient（好友账号）给 `test` 发邀请 → 断言弹窗打开、`fromNameText` 与对方账号一致、倒计时递减。

## 13. 已知限制

1. **同局域网限制**：房主地址是私网 IP，跨公网不可达（与现有"手填 IP 加入"完全一致）。
2. **服务端不知道房间真实状态**：房主关房后仍可能已发出邀请，好友同意时表现为"连不上"，由客户端兜底文案处理。
3. **不再支持"先创建房间再等人"以外的房间发现**：没有大厅列表，邀请是唯一便捷入口。
4. **好友在线状态来自 TCP 会话**：`PlayerManager` 在线但被顶号/断线的窗口期内可能出现误判，与好友列表现状一致。
5. 邀请记录不落库，服务端重启后全部失效（符合短命信令语义）。

## 14. 实测结论（2026-10-22）

### 14.1 协议级（TestClient，8888）

| # | 用例 | 结果 |
| --- | --- | --- |
| 1 | 邀请在线好友 | 房主收 `InviteResponse{success,inviteId,expireIn≈60s}`；好友收 `Notify`（昵称/地址/房间正确） |
| 2 | 好友同意 | 好友收 `RespondResponse{success,host 昵称/ID/地址}`；房主收 `ResultNotify{result=1}` |
| 3 | 好友拒绝 | 房主收 `result=2`（带拒绝理由）；好友收 `success=true 已拒绝` |
| 4 | 60s 超时 | 房主收 `result=3 邀请已过期`；好友收 `邀请已失效（邀请已过期）` |
| 5 | 非好友 | `success=false 对方不是你的好友` |
| 6 | 对方离线 | `success=false 对方不在线` |
| 7 | 同会话重复邀请（间隔 1.8s，越过 1.5s 冷却） | `success=false 已有待回应的邀请，请先取消` |
| 8 | 房主取消 | 房主收 `cancelled=1`；好友收 `房主已取消邀请` |
| 9 | 房主断开 | 邀请随会话关闭自动撤销（好友再回应返回"邀请已失效"） |

### 14.2 客户端（Unity Play，LOGIN 场景 + 真实服务端）

- 登录 `test` 后由好友账号下发邀请：**1.8s 收到弹窗**，昵称 `bit_a_154846`、倒计时 `剩余 60 秒`、同意按钮可用。
- 点「同意」：弹窗关闭 → `BattleRoomView` 打开 → `StartClientAsync("10.174.148.91", 7777)` 发起连接 → `HasSession=true`；对端无监听时走既有的连接超时兜底（预期分支）。
- 房主侧：`EnsureHostRoomAsync` 建房成功（`roomId` 生成、本机 IP `10.174.148.91:7777` 显示在面板），好友列表 6 行、在线/离线状态与按钮可用性正确、离线行按钮置灰；邀请在线好友后 `AwaitingResponse=true`、待回应文案带倒计时；等待期间再次邀请被本地拦截；取消后状态复位。
- 已在房间/对战中收到邀请：自动回 `accept=false, reason="正在对战中"`，房主收到「test 正在对战中」，**不弹窗**。
- 视觉门禁：`screenshots/battle_invite_ui.mp4`（VLM 逐帧确认面板/弹窗/倒计时 60→57/按钮/无乱码无裁切）。

### 14.3 环境依赖（重要，影响可复现性）

本工程当前解析到 `com.unity.collections 2.5.8`，而 `com.unity.transport 1.5.0` 与 `com.unity.netcode.gameobjects 1.13.1` 只兼容 collections 1.x。为保证编译，本次把这两个包**内嵌到 `Packages/`** 并打了最小兼容补丁：

| 包 | 改动 |
| --- | --- |
| `Packages/com.unity.transport` | `Runtime/IPCManager.cs`：3 处 `NativeHashMap.Count()` → `ChannelCount()`（用 `GetKeyArray` 实现，1.x/2.x 都能编译）；删除自带 `Tests/`（测试程序集与 collections 2.x 存在同名类型冲突） |
| `Packages/com.unity.netcode.gameobjects` | `BatchedSendQueue.cs` / `UnityTransport.cs`：为 `DataStreamWriter/DataStreamReader` 加类型别名，消除与 `Unity.Collections` 的同名类型冲突；删除自带 `Tests/` |

注意：
1. `Packages/*` 被 `.gitignore` 第 80 行忽略，所以这两个内嵌包**不会进 git**。换机器/重新克隆工程时需要重新内嵌并打补丁，否则会回到 `CS1955` + `CS0104` 的编译错误。
2. NGO 2.x 全系（含 2.13.3）在 registry 上声明 `unity: 6000.0`，本工程 Tuanjie 2022.3.62t11 **无法安装**，不能靠升级解决。
3. 若以后把 collections 钉回 1.2.4，这两个内嵌包可删除（回到 registry 版本即可），但需关闭编辑器后改 manifest 再重启（运行期改 manifest 会被 UPM 内存状态覆盖）。
