# 背包分区归位设计方案

## 1. 现状（实测）

背包槽位是一个连续空间，分两段（服务端 `BagRepository`）：

- 武器区 `[0, WeaponCapacity=500)`：放装备实例（`item_type = 3`），定长，满则转邮件；
- 道具区 `[500, ∞)`：放可堆叠道具，按需扩容，永不「满」。

服务端已经管住的两件事：

- `SwapSlots` 拒绝跨区换位，回执「不能跨背包换位」；
- `GrantIntoSlots` 里装备只找武器区空槽。

仍然会错位的两处：

1. **历史数据**：分区改造（2026-10-30）之前，道具都存在 `[0,500)`。把这些道具搬回道具区的唯一入口是玩家手动点「整理」，不点就一直留在武器区。实测账号 `test`（Id=1）打开背包为「武器区 24 件、道具区 0 件」，其中 `1001 治疗药剂`、`1003 铁矿` 等全是道具，全部显示在「武器背包」页签里。
2. **入包找堆叠不限区**：`GrantIntoSlots` 为非装备补堆叠时扫描整个槽位数组（注释写明「兼容历史数据把道具放在武器区的情况」）。只要武器区还残留同 id 的未满堆叠，后续入包会继续往那里堆，道具被不断「钉」在武器区。

结论：规则本身已经在，缺的是「归位时机」——目前只发生在玩家手动整理时，而不是自动发生。

## 2. 设计

口径：装备只允许出现在武器区 `[0,500)`，非装备只允许出现在道具区 `[500,∞)`；客户端两个页签按区渲染（已实现），数据层保证两边不会串。

服务端两处改动，都在 `Server/Database/BagRepository.cs`：

### 2.1 读取快照时自动归位

`GetSlots(playerId)`（背包列表请求 2401 的数据来源）在读到快照后先判断有无错位：

- 武器区里出现非装备；
- 道具区里出现装备。

只要命中一条，就调用现有的 `Tidy(playerId)` 做一次分区整理（它已实现：装备逐件保留实例 ID 按稀有度排到 0 号槽起，道具按 `max_stack` 合并、按类型/稀有度排序排到 500 号槽起，并把历史放进武器区的道具搬到道具区），随后重新读一次快照返回。

这样归位发生在「打开背包」这条必然路径上，玩家不需要点整理，也不会看到错位数据。归位复用单一分区实现（`Tidy`），不新增第二套排序规则。`Tidy` 自身是 玩家写锁 + 事务 + `FOR UPDATE` + 差异回写，幂等：没有错位时不触发，触发时再执行结果也是确定的。

### 2.2 入包补堆叠限制在本区

`GrantIntoSlots` 为非装备补同类未满堆叠时，扫描范围从整个槽位数组收窄为道具区 `[ItemRegionStart, slots.Length)`；装备的入包路径本来就只找武器区空槽，不变。

目的地固定：道具新占空槽仍在道具区（不足按 `ItemCapacityStep=60` 扩容），装备仍在武器区（满则剩余转邮件）。这样「钉在错误区」的来源被切断，`2.1` 的归位只需处理历史存量。

## 3. 影响面

- 服务端：仅 `Server/Database/BagRepository.cs`。
- 协议：不变（`2401` 响应字段与槽位下标语义不变，客户端按 `bag.Capacity` 划分武器的起始槽位，两端口径一致）。
- 客户端：不改代码。跨区换位在前端无法产生（两个页签各自渲染一个区，拖拽落点必在同一区），服务端 `SwapSlots` 的拒绝口径保持。
- 数据：`player_items` 表结构不变，只是错位行的 `slot_index` 被搬到正确区（装备的 `instance_id` 随行保留）。

## 4. E2E 验收项

1. 用 `test/123456` 打开背包：`武器背包` 页签只出现装备，`道具背包` 页签出现 `1001 治疗药剂`、`1002 高级治疗药剂`、`1003 铁矿` 等道具，且数量与归位前一致（合计不变）。
2. 归位后重启一次服务端进程再打开背包：结果一致（已落库，不依赖内存）。
3. 入包验证：请求若干道具（如签到/唤取/邮件领取）后，新道具只出现在道具区；武器区槽位下标集合不再新增道具。
4. 跨区换位仍被拒：对武器区与道具区各取一个槽位请求 `SwapSlots`，回执为「不能跨背包换位」。
5. 同区换位、使用、丢弃、整理行为与改造前一致。

## 5. 风险

- `GetSlots` 在存在错位时会多一次「整理 + 重读」，属于打开背包路径上的一次额外事务；错位清空后不再触发（幂等），不构成常态开销。
- 装备数量超过武器区容量 500 的极端情况：`Tidy` 既有行为是把排不进的装备留在原处而不是丢弃，归位逻辑沿用该行为，不会让物品消失。
- 归位会改变槽位下标，客户端若在归位瞬间持有旧快照做落点判断，可能落空一次；归位发生在打开背包的响应之前，界面拿到的就是归位后的快照，不受影响。

## 6. 实施与实测

已实施（服务端 `Server/Database/BagRepository.cs`）：`GetSlots` 读到错位先 `Tidy` 归位再返回；`GrantIntoSlots` 为非装备补堆叠的范围收窄到道具区。

实测（账号 `test`，Id=1；先重启服务端进程再验证）：

- 归位生效：归位前「武器区 24 件 / 道具区 0 件」→ 归位后「**武器区 17 件 / 道具区 7 件**」。
- 分区内容正确：武器区 = `1012`×15 件 + `1014`×1 + `1015`×1（全为 `item_type=3` 装备）；道具区 = `1002`×12、`1001`×19、`2001`×107、`1007`×1、`1008`×1、`1003`×23、`1004`×3（全为非装备）。
- 数量守恒：各物品数量与归位前逐一相同（1012 的 15 件在改造前各占一格，归位后仍是 15 格），合计 24 件未变。
- 幂等：再次请求背包列表，槽位分布与数量完全一致，不再触发归位。
- 跨区换位被拒：对武器区 `0` 与道具区 `500` 请求换位，数据无任何变化。
- 同区换位正常：道具区 `500`↔`501` 成功交换（`1002` 与 `1001` 互换），再换回后恢复原状。

未覆盖：服务端入包路径的堆叠范围收窄，没有单独造一次“武器区残留同 id 堆叠”的入包场景（归位后武器区已无道具，该分支在正常数据下不再被触发）；入包路径本身在归位前后都只把新道具放进道具区。
