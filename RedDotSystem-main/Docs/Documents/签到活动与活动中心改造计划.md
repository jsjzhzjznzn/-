# 签到活动 + 活动中心左侧栏 改造计划

> 状态：计划稿（2026-10-17）。实施完成后在文末补"实施结果"。
> 目标一句话：活动面板从「单活动全屏页」升级为「鸣潮式活动中心」——左侧活动栏（唤取角色 / 签到）+ 右侧内容页切换；并新增签到活动的全栈链路（协议 / 服务端 / 热更 UI）。

---

## 0. 需求与现状差距

| 项 | 现状 | 目标 |
| --- | --- | --- |
| 活动面板结构 | 全屏只有唤取一个活动，无入口栏 | 左侧竖栏列出进行中的活动（唤取角色 / 签到），点击切换右侧内容页 |
| 活动数量 | 服务器同一时间窗只排 1 个唤取活动；客户端壳只缓存列表第一个 | 唤取与签到**同时在线**；壳缓存完整列表，Lua 按列表建侧栏 |
| 签到 | 无 | 鸣潮式 7 天累计签到：每天可签 1 次、按累计次数解锁第 N 天奖励、服务端权威发放入包 |
| 活动类型 | `activity_config.type` 只有 1（武器唤取） | 新增 type=2（每日签到）；GM 轮换只作用于 type=1，签到常驻 |

## 1. 总体架构（沿用既有「固定壳 + 热更内容」分工，不新增第三种东西）

```
活动入口按钮(zhuye HUD)
   └→ ActivityShell.OpenActivity() ── 拉活动列表(2901) ──→ 面板打开
         └→ LuaActivityHost.BuildContextTable / ActivityBridge ──→ 热更层 activity_main.lua
               ├→ bridge.GetActivityCount/GetActivityInfoAt(i)   ← 完整活动列表（新）
               ├→ 侧栏按钮：按活动列表克隆 SidebarButtonTemplate，点击切页
               ├→ GachaPage（原唤取页，逻辑不变，路径挂到 GachaPage 下）
               └→ SignInPage（新）：bridge.RequestSignInList/ClaimSignIn → 服务端 2907-2910
服务端
   ├→ activity_config：新增活动3（type=2 签到，与唤取同窗）
   ├→ sign_config（7 天奖励配置）+ player_sign_records（签到记录）
   └→ SignInRepository.Claim：单事务 + 玩家行锁 → 签到入包（满包转邮件）
```

关键原则（与既有系统一致）：
- **改版式不用改 Lua、改逻辑不用重编客户端**：签到页全部内容在热更包里，上线后改奖励/文案 = 发一版新包。
- **服务端权威**：能不能签、签第几天、发什么，全由服务端裁决；客户端只渲染与转发。
- **壳的边界不动**：ActivityShell/LuaActivityHost 只加"活动列表缓存 + 签到请求转发"，不含任何活动内容。

## 3. 签到玩法规则（鸣潮式，服务端裁决）

1. **奖励按"第 N 次签到"解锁**，不按日历天：只能签 `day = signed_days + 1`（断签不断进度，第 3 天没签，之后签的还是第 3 天的奖励）。
2. **每个自然日只能签一次**：`player_sign_records` 上 `(player_id, sign_id, claim_date)` 唯一键硬约束；claim_date = 服务器本地时区 `yyyy-MM-dd`。
3. **活动窗口外不可签**：签到活动在 `activity_config` 有自己的排期（本期与唤取活动 A 同窗，7 天）。
4. **签到即发奖入包**：奖励直接进背包（满包自动转邮件，与唤取/任务奖励同口径），并触发 `QuestHandler.RaiseItemGained` 联动收集类任务与生涯统计。
5. 回执带**完整 7 天状态快照 + 背包快照 + 涉及物品配置**——客户端零二次拉取（与 GachaDrawResponse 同模式）。
6. **E2E/联调口**：环境变量 `CS_SIGN_TODAY`（`yyyy-MM-dd`）可覆盖"今天"，每次判定实时读取不缓存——用于验证跨天连续签到，不用等真实日期。

### 3.1 7 天奖励种子（item_config 既有物品，零新资源）

| -- | ---- | ---- |
| 1 | 治疗药剂(1001) | ×2 |

## 4. 协议（ActivityPacket.proto 追加 + MessageID 29xx 段补位）

```
SignInListRequest  = 2907 { sign_id }                     → SignInListResponse  = 2908
SignInClaimRequest = 2909 { sign_id }                     → SignInClaimResponse = 2910
SignInDayInfo { day, item_id, name, icon_key, rarity, count, claimed }
```

- `SignInListResponse`：`success, message, sign_id, total_days, signed_days, today_signed, server_now_ms, days[]`
- `SignInClaimResponse`：`success, message, sign_id, day(本次签到的天次), total_days, signed_days, today_signed, days[], slots[](背包快照), configs[](物品配置)`
- `sign_id` = 签到活动在 `activity_config` 的 `activity_id`（type=2）。`ActivityInfo.type` 注释更新为「1 武器唤取 / 2 每日签到」。
- 2911/2913/2914（切换推送/GM 轮换）不动；2912 留空。
- `build_proto.bat` 三端同步生成（客户端 / 服务端 Generated + TestClient 引用同源）。

### 5.2 表结构

```sql
sign_config        (sign_id INT, day TINYINT, item_id INT, count INT,
                     PRIMARY KEY(sign_id, day))                     -- 7 天奖励配置
player_sign_records(player_id INT, sign_id INT, day TINYINT,
                     claim_date CHAR(10), claimed_at_ms BIGINT,
                     PRIMARY KEY(player_id, sign_id, day),
                     UNIQUE KEY uk_date(player_id, sign_id, claim_date))  -- 序列闸 + 每日一签闸
```

### 5.3 Claim 事务口径（与 GachaRepository.Draw 同款）

```
PlayerWriteLock.Acquire(playerId)
  单事务 + LockPlayerRow
    ├ 活动窗口校验（activity_config: type=2 且 now∈[start,end)）
    ├ LoadSlotsForUpdate → 今日已签校验（claim_date = today）→ 序列校验（day = signed+1 ≤ total）
    ├ INSERT player_sign_records（唯一键冲突 = 并发重复签，直接判失败）
    ├ GrantIntoSlots 入包；放不下 → overflow 记账
    ├ SaveSlots；overflow → MailRepository.InsertOverflowMail（同事务转邮箱）
    └ Commit
成功后：GetSlots + 涉及物品 configs + 新签到状态 组装回执
```

## 9. 边界与不做的事

- **红点**：活动入口/侧栏"今日未签"红点不在本期（活动入口按钮本就没有红点系统接入；后续若做，接既有 MH 红点框架）。
- **补签/月历**：只做 7 天累计签到，不做补签、月历、连签额外奖励。
- **阿福提醒**：签到满包转邮件后的附件提醒依赖既有巡检（AgentReminderService 每 3 分钟扫未领附件），不新增触发点（与唤取同口径）。
- **签到的活动切换**：签到活动也在 `ActivityChangeNotify`（2911）语义内——若运营改库下线签到活动，面板侧栏实时消失/出现。
- **多签到活动并存**：协议与表结构天然支持多个 sign_id，本期只种 1 个。

### 验证结论

- **协议级 E2E（TestClient，账号 signe2e1=49）**：
  - 初始状态 0/7、今日未签、7 天奖励与种子一致（药剂×2/铁矿×10/强化石×3/铜矿×10/高级药剂×2/媒介×5/媒介×10）；

  - 服务端带 `CS_SIGN_TODAY=2000-01-01` 重启后：第 2 天签到成功（铁矿×10，2/7）——**序列闸（signed+1）与日期闸（每日一签）双验证**；同假日期再签被拒；
  - `--activity-list`：唤取 + 签到双活动并存；GM 轮换（`--activity-rotate 1`）复活过期的唤取活动 A，**签到活动未被误关**（GmRotate 只作用于 type=1）。

- **录屏 VLM 门禁**：screenshots/sign_activity_e2e.mp4 逐项确认——左侧竖栏双按钮与选中态、签到页布局（摘要/7 格/大按钮）、签到成功 toast 与格子状态迁移、切页、唤取页要素、结果卡牌；中文零乱码、无异常配色。

### 与计划的偏差

1. **唤取活动排期过期**：DB 里的活动 A/B 排期种子是 2026-09-29 首次种子时的相对时间，7 天窗口已自然过期（与本次改动无关）。E2E 中用 GM 轮换把它拉回窗口（`--activity-rotate 1`）；长期运营需注意 INSERT IGNORE 种子不会自动续期。
2. **顺手修了一处玩家侧编译错误（用户文件）**：`Assets/Scripts/GAS/CueAnimancerAnimation.cs` 把 `using Sirenix.OdinInspector` 包在 `#if UNITY_EDITOR` 里，而多数字段的 `[BoxGroup]/[LabelText]` 在条件编译外——编辑器能编译、打 AssetBundle（玩家侧编译）必炸 CS0246，本次发布 1.1.0 即被阻塞。已把该 using 移出条件编译（Odin Attributes DLL 全平台启用，语义不变）。
3. TestClient 的 `--sign-list/--sign-claim` 需要带活动 ID（`--sign-claim 3`）：GetArg 约定是"取后一个参数"，裸 flag 会得到 null。
