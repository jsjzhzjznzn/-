# 战斗命中管线分层改造方案（P0 + P1）

> 编写日期：2026-11-10
> 定位：施工单。把「命中判定」从各个攻击来源里抽出来，收敛成一条分层管线：
> 收集来源上下文 → 查全局规则产出掩码与响应 → 收集目标状态 → 逐目标筛选 → 结算。
> **P0 要求行为零变化**（arc 默认 360 = 整球，规则默认值等于现状），P1 只新增阵营过滤。

---

## 0. 结论先行

| 项 | 内容 |
|---|---|
| 现状 | 命中判定分散在 2 处（玩家连招球、BOSS 扇形），两处口径不一致；无阵营概念、无友军伤害规则 |
| 目标 | 一条 `CombatPipeline` 入口，四个步骤可分别测试替换；调用点只负责「给出上下文」和「拿着结局播表现」 |
| 手感 | P0 不改变任何现有命中结果（arc=360、遮挡=关、友军=关） |
| 不改 | 服务端（它不参与伤害裁定）、`DamageRequest` 线上字节、`TakeDamage` 的无敌/死亡锁、`DamageCalculator` 的六阶段公式 |
| 改动面 | 新增 5 个文件；改 5 个文件（2 个调用点 + ComboData/AttackDef 各加字段 + EventCenter 加一个事件） |

## 1. 现状分析

### 1.1 现有链路

| 环节 | 现状 | 位置 |
|---|---|---|
| 玩家命中判定 | `Physics.OverlapSphereNonAlloc`（整球，无角度、无遮挡），排除自身子树，逐 Collider `GetComponentInParent<HealthModel>` | `CharacterCombo.AttackDetection` / `AttackTrigger` |
| BOSS 命中判定 | `OverlapSphereNonAlloc`（半径 = `range*0.5`，球心前移 `range*0.5`）+ 扇形角度 `arc*0.5` | `EnemyBrain.ResolveAttackHit` |
| 挑战怪物 | 无判定几何，直接对 `target` 的 HealthModel 结算 | `ChallengeMonster.DealDamage` |
| 测试假人 | 同上 | `BattleTestDummy`（`#if UNITY_EDITOR`） |
| DoT | 无判定，Buff tick 直接扣血 | `BuffDotEffect.OnTick` |
| 攻方算伤害 | 攻击力 × 倍率 → ×(1+增伤) → 暴击掷骰 | `DamageCalculator.CalculateOutgoing` |
| 跨端传递 | `DamageRequest{damage, isCritical, sourceId, isDoT}` 走 `RequestDamageServerRpc` | `HealthModel.RequestDamage` |
| 受方结算 | 防御 → 减伤 → 保底；`TakeDamage` 再做无敌拦截（DoT 无视）、扣血、死亡锁 | `HealthModel` |
| 表现 | 派发 `E_OnDamage` / `E_DamageBlocked` / `E_OnDeath`，飘字/受击/震屏/闪避各自订阅 | `EventCenter` |

### 1.2 由此产生的四个真实缺口

1. **两处判定口径不一致**：玩家是整球、BOSS 是扇形。同一个"背后挥刀"，玩家能打到、BOSS 打不到。
2. **玩家侧无遮挡判定**：球形判定会穿透薄墙。工程里唯一的 Linecast 只用在自动索敌（`HasLineOfSight`）。
3. **无阵营概念**：`NetSeatId` 只用于选相机，两个玩家之间没有"敌/友"区分。一旦加入召唤物或队友，友军伤害无法拦截。
4. **无统一决策点**：是否可打、打谁、打几个，散落在各调用点里，新增攻击来源必须照抄一遍。

### 1.3 架构前提（决定管线只能跑在哪里）

- 服务端不参与伤害裁定：`competeserves` 全仓除装备快照外没有任何 Damage 相关逻辑。
- 出手伤害在攻方出手瞬间算定并固化，受方只做自己那一半结算。
- 因此管线**只能运行在攻方所在端**（单机 = 本地；联机 = 攻方拥有者，实为房主权威血量）。
- 结论：原图里"服务端按服务端状态给每个目标重新裁定一次"这一步在本项目**不实现**，它是防作弊能力，不是分层能力。

## 2. 设计

### 2.1 分层与文件

| 层 | 原图对应 | 本项目落地 | 文件 |
|---|---|---|---|
| ① 收集来源上下文 | 投射物 / 法术场 / 枪械 | 各攻击来源填 `AttackContext` | `Combat/AttackContext.cs`（新） |
| ② 规则 + 掩码 + 响应 | 玩法全局配置 / 检测规则 / 目标要求 | `CombatRunRules`（规则值，每次运行读一次）+ `CombatQuery`（过滤产出候选） | `Combat/CombatRunRules.cs`（新）、`Combat/CombatQuery.cs`（新） |
| ③ 目标状态快照 | 角色 / 衍生生物 / 场景 | 逐目标拍 `TargetSnapshot`（存活/无敌/眩晕/沉默/无敌 Buff） | `Combat/CombatPipeline.cs`（新，内部 struct） |
| ④ 进一步筛选 | 距离 / 角度 / 遮挡 | `HitFilter` 规则：遮挡 → 角度 → 距离，可在招式上单独关闭 | `Combat/CombatPipeline.cs`（新） |
| 结算 | — | 调 `DamageCalculator.CalculateOutgoing` → `RequestDamage` | 复用现有 |
| 结局 | — | `HitReport`（命中列表/被拦列表/是否空挥），调用方据此播打击感 | `Combat/CombatPipeline.cs`（新） |

统一入口：

```csharp
public static class CombatPipeline
{
    // 同步执行：收集 → 规则 → 目标快照 → 筛选 → 结算，返回本次结局
    public static HitReport Resolve(in AttackContext ctx);
    // 只做判定不结算（粘刀/弹刀/自动索敌这类"几何查询"复用同一套规则）
    public static int QueryCandidates(in AttackContext ctx, in FilterSpec filter, Collider[] buffer);
}
```

### 2.2 步骤 ①：来源上下文

```csharp
public enum AttackDelivery { Melee, Skill, Dot, EnemyAttack, Scripted }

public struct AttackContext
{
    public GameObject attacker;     // 出手者（飘字/命中事件/打击感都用它）
    public Vector3 origin;          // 判定球心（已含前移量）
    public Vector3 forward;         // 朝向（角度筛选基准，已水平化）
    public float radius;            // 判定半径
    public float arc;               // 扇形角（度），360 = 整球
    public int layerMask;           // 物理层过滤
    public AttackDelivery delivery;
    public float damageMultiplier;  // 近战/技能读 ComboData
    public float critRate;
    public float critMultiplier;
    public float flatDamage;        // 招式不读攻方属性时直接用（BOSS/怪物/假人）
    public BuffData hitBuff;        // 命中附带 Buff
    public int maxTargets;          // 0 = 不限
    public bool pierce;             // 是否穿透继续打下一个
    public ulong sourceId;          // 联网用的攻击者 NetworkObjectId（未 spawn 时为 0）
}
```

- `flatDamage > 0` 时不读攻方属性，直接作为出手伤害；`damageMultiplier` 走 `CalculateOutgoing`。
  这样 `EnemyBrain`（`AttackDef.damage`）、`ChallengeMonster`（`attackDamage`）、`BattleTestDummy` 都能无损接入。
- DoT 不进管线：它没有几何判定，`BuffDotEffect` 继续直调 `HealthModel.TakeDamage`。

### 2.3 步骤 ②：全局规则与掩码

```csharp
public struct CombatRunRules
{
    public bool friendlyFire;         // 默认 false
    public bool requireLineOfSight;   // 默认 true（P0 由招式单独关闭）
    public LayerMask environmentMask; // 遮挡检测用的层
}
```

- 取值顺序：场景内 `CombatRunRulesSource`（MonoBehaviour，可选，挂在任意场景物体）> 静态默认值。
  缓存策略：每次 `Resolve` 读一次（`FindObjectOfType` 结果静态缓存 + 场景切换清缓存），不做每帧查找。
- **掩码**：`CombatQuery` 用同一 `layerMask` 做 `OverlapSphereNonAlloc`，再执行：
  1. 排除 `attacker` 自身及其子树（等价现状的 `IsChildOf`）；
  2. 归属解析：`GetComponentInParent<HealthModel>()`，无 HealthModel（地形/装饰）丢弃 —— 与现状一致；
  3. 存活判定：`HealthModel.IsAlive`，并保留 `Player.IsDead` 检查；
  4. 阵营过滤（P1）：见 2.6。

### 2.4 步骤 ③：目标状态快照

每个候选目标在结算前读一次，字段只读一次，结算期间不重读（避免同一帧内状态漂移）：

```csharp
private struct TargetSnapshot
{
    public HealthModel health;
    public GameObject root;
    public bool alive;
    public bool invincible;      // HealthModel.IsInvincible（闪避窗口）
    public bool buffInvincible;  // CharacterState.IsInvincible（Buff 无敌）
    public bool stunned;         // CharacterState.IsStun
    public bool silenced;        // CharacterState.IsSilence
}
```

- 快照只用于**决策**（例如眩晕/沉默状态决定是否给响应），不参与数值。
- 「可重写的条件」（原图第 3 步）在本项目落到 `AttackContext` 上的招式级覆盖：`ignoreInvincible`（预留，P0/P1 不启用）与 `arc/layerMask/maxTargets` 的招式级配置。

### 2.5 步骤 ④：进一步筛选

固定顺序（便宜的先做），任一关单独可被招式关闭：

| 顺序 | 规则 | 实现 | P0 默认 |
|---|---|---|---|
| 1 | 遮挡 | 攻方胸口 → 目标胸口 `Physics.Linecast(environmentMask)` | 关（`requireLineOfSight=false` 由招式传入） |
| 2 | 角度 | 水平化后 `Vector3.Angle(forward, toTarget) > arc*0.5` 丢弃 | 关（arc=360） |
| 3 | 距离 | 已在 OverlapSphere 里，不需要额外判断 | — |

- Linecast 起止点复用 `EnemyBrain.UpdateTargetInfo` 与 `CharacterCombo.HasLineOfSight` 的现成口径（攻方 `+up*1.4`，目标 `+up*1.0`）。
- 角度用**水平投影**，与 `EnemyBrain.ResolveAttackHit` 现有做法一致（斜坡场景下 3D 夹角会失真）。

### 2.6 P1：阵营与友军伤害

- 新增 `Combat/CombatFaction.cs`：

```csharp
public enum CombatFaction { Neutral, Player, Enemy }

public static class CombatFactionUtil
{
    // 归属规则：自或父级上的 Player → Player；EnemyBrain/ChallengeMonster → Enemy；
    // 其余（召唤物/环境物件）→ 跟随其父级，取不到则 Neutral
    public static CombatFaction Resolve(GameObject go);
    public static bool IsFriendly(CombatFaction a, CombatFaction b); // a==b 且非 Neutral
}
```

- `AttackContext` 增加 `faction`（由调用方填，或管线内部用 `CombatFactionUtil.Resolve(attacker)` 解析）。
- 规则：`friendlyFire == false` 时，`IsFriendly(ctx.faction, targetFaction)` 的候选被**丢弃并计入 `HitReport.blocked`**。
- 现状影响：1v1 联机两个玩家都是 `Player`，当前攻击层掩码是 `enemy` 且怪物也被强制设成 `enemy` 层，所以行为不变；真正生效要等召唤物或队友进场的招式把 `layerMask` 放开。这一点必须在验收里显式确认（见 §5 第 4 项）。

### 2.7 结局

```csharp
public struct HitReport
{
    public int hitCount;        // 实际命中数
    public int blockedCount;    // 被规则/筛选拦下数（友军、遮挡、角度、死亡）
    public bool anyCritical;
    public GameObject firstTarget;
    public Collider firstCollider;
    // 由调用方读取，用于 HitFeelService 的顿帧/震屏/特效（保持"一次打击帧只播一次"）
}
```

`HitReport` 是 struct，无引用字段集合（除 GameObject/Collider 引用），每次打击帧零 GC 分配。

## 3. 调用点改造

### 3.1 玩家连招（`CharacterCombo.AttackTrigger`）

```
现状：AttackTrigger → TryStickToTarget → TryDeflect → AttackDetection(球) → 循环结算 + HitFeelService
改造：AttackTrigger → Context(P0 全字段取自 ComboData, arc=360, 遮挡关)
                  → CombatPipeline.Resolve → 按 HitReport 播一次 HitFeelService
```

- `_hitTargets` 去重、逐个目标独立掷暴击、命中附带 Buff、`E_Attack` 派发顺序全部保持。
- 粘刀/弹刀/自动索敌继续用 `CombatQuery.QueryCandidates`（它们本来就要几何查询），P0 时 `arc` 参数使用 `ComboData.autAimMaxAngle`/`75f`，不引入新配置。

### 3.2 BOSS 行为树（`EnemyBrain.ResolveAttackHit`）

- 改成 `AttackContext{origin = transform+up*0.9+forward*range*0.5, radius = range*0.5, arc = def.arc, flatDamage = def.damage, delivery = EnemyAttack, layerMask = playerMask}`。
- 几何与现状完全等价；`HitsLanded` / `HitFramesResolved` 从 `HitReport` 读取，行为树统计口径不变。
- BOSS 侧 `HitFeelService.EnemyHitPlayer` 仍由调用方在命中后调用一次。

### 3.3 挑战怪物 / 测试假人

- 改为 `AttackContext{origin = target.position, radius = 0.01f, arc = 360, layerMask = target层, maxTargets = 1}`，即"半径极小的整球 + 第一个命中"，等价现在的"直接打目标"。
- 好处是它们也自动获得存活/死亡判定和友军过滤，不再各写一份。

### 3.4 事件

新增 `E_EventType.E_AttackBlocked`（`HitData`），由管线在"被规则拦下"时派发一次（用于将来播"格挡/闪避提示"）。P0 无人订阅，属于预留钩子，不改变现有表现。

## 5. 验收项（E2E，全部实测）

| # | 验收项 | 方法 | 判定 |
|---|---|---|---|
| 1 | 编译 | `unity_editor.refresh` | 0 个 `error CS` |
| 2 | **行为零变化（玩家）** | tiaozhan 场景，玩家站在 BOSS 背后挥刀，对比改动前后 | 改动前后命中目标集合、伤害数值、暴击结果完全一致（arc=360、遮挡关） |
| 3 | **行为零变化（BOSS）** | BOSS 攻击玩家，正面/侧面/背后三种站位 | 与改动前一致（扇形 arc 未变） |
| 4 | 判定口径等价性 | 同一帧同时记录旧 `AttackDetection` 与新 `QueryCandidates` 的 Collider 集合 | 两集合逐元素相同（正控：故意把玩家移到 BOSS 背后，两侧应都为空或都非空） |
| 5 | 友军过滤正例 | 手动把两个 Player 层改到同一 `layerMask` 下，`friendlyFire=false` | `HitReport.blocked` 增加、`hitCount` 不变、目标血量不掉 |
| 6 | 友军过滤反例（正控） | 同上但 `friendlyFire=true` | 目标血量掉、`hitCount` 增加 |
| 7 | 挑战怪物链路 | ChallengeMonster 对玩家出手 | 血量按 `attackDamage` 掉，`E_OnDamage` 正常派发 |
| 8 | 测试假人链路 | BattleTestDummy 自动攻击 | 同上 |
| 9 | 打击感不重复 | 一次打击帧打两个目标 | `HitFeelService.PlayerHitEnemy` 只调用一次（顿帧不叠加） |
| 10 | 零 GC | 连续 300 次 `Resolve` | `GC.GetTotalMemory(true)` 前后差 0B |

> 缺口 #4 的「无人订阅的 E_AttackBlocked」不在 P0 验收范围，它是 P1 之后的钩子。

## 6. 风险与取舍

| 风险 | 说明 | 处理 |
|---|---|---|
| P0 声称零变化但实际不等价 | OverlapSphere 的 Collider 顺序可能不同，而首次命中目标决定打击感基准（`firstHitHealth`） | 不改 OverlapSphere 的缓冲复用方式；`firstTarget` 仍取"遍历顺序里的第一个有效目标"，与现状一致 |
| Linecast 遮挡在 P0 打开会改变手感 | 薄墙打不中、模型凹槽挡命中 | P0 一律关；开关随招式暴露，P2 才逐步开 |
| 阵营解析依赖 `Player`/`EnemyBrain` 类型 | 召唤物/衍生生物现在不存在，规则只能是推断 | 默认 `Neutral`，不参与友军判定；等衍生生物出现时补归属 |
| 全局规则用 `FindObjectOfType` | 场景切换开销 | 结果静态缓存 + `SceneManager.activeSceneChanged` 清缓存 |
| 服务端不参与裁定 | 客户端改内存可绕过管线 | 与现状同一安全等级（出手伤害本就是客户端算定），不在本方案范围 |

## 8. 明确不做

| 不做 | 原因 |
|---|---|
| 引入 GAS / AttributeSet / GameplayEffect | 项目已有的 Buff/Attribute 体系就是这个角色的替代，双轨会冲突 |
| 服务端重算出手伤害、逐目标裁定 | 现有架构明确不做数值上限校验；改它要动协议与 Netcode，收益是防作弊而非分层能力 |
| 修改 `DamageRequest` 字段顺序 | 线上字节格式只能追加，改序会让新旧构建解析错位 |
| 在 `TakeDamage` 里复制一份规则判断 | 管线负责「决策」，`TakeDamage` 负责「结果」；混在一起会出现两套真相 |
| 护盾 / 无敌帧重写 / 元素抗性 | 项目当前没有护盾系统；`TargetSnapshot` 预留字段，不实现 |
| 投射物 / 法术场 / 枪械实现 | 项目当前无此类来源；`AttackDelivery` 枚举预留，等真实来源出现再接 |
| P2 角度收紧 | 会改变手感，需要逐招调数值，单独一轮做 |

### 验证过程中的三条排障结论

- **BOSS 的实测位置会漂移**：行为树在持续选招/位移，脚本摆位后立刻查询会读到旧位置。要精确验证必须先把 `brain.enabled=false` 冻结 AI，再摆位并等待 0.4s。
- **判定球心在攻方胸口高度**：BOSS 站到玩家背后超过约 0.6~0.9m 就整体落到球外（球心前移 0.9m + 半径 1.5m），此时"背后打不中"是几何结论而非角度筛选；正反例必须挑"球内且在背后"的站位才能证明角度开关有效。
- **血量要同帧读回**：在 `Resolve` 之后 `yield` 再读 HP 会读到下一帧的同步结果，可能被其它逻辑覆盖而显示为"没掉血"。验证结算一律"先读 → 调用 → 立刻读"。

### 与原方案的差异

1. 计划 5 个新增文件，实际 6 个：`CombatRunRulesSource` 单独成文件（`CombatRunRules.cs` 只放纯数据 struct 与层缓存）。
2. `HitReport` 增加 `hits` 明细列表（`HitEntry`：目标/Collider/是否暴击），因为 `E_Attack` 必须由调用方按目标派发，管线只负责结算。该列表由管线复用，只在本次 `Resolve` 内有效。
3. 无敌窗口的拦下**没有**提前到管线：`TargetSnapshot` 只读取状态供扩展规则使用，`HealthModel.TakeDamage` 仍是唯一拦截点（避免两套真相）。
4. P1 的友军过滤已实测生效（见验收 12），默认 `friendlyFire=false`。当前现实玩法里 `Player` 与 `Enemy` 阵营互斥、攻击层也互斥，所以玩家正常打怪无可观测变化；规则本身已具备，召唤物或放开招式层后即可直接拦截。
5. `HitReport` 额外带 `firstBlocked`：命中为 0 但有拦截时，`E_AttackBlocked` 才有真实的目标可填（初版误填攻击者自身）。
