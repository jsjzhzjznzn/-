Q1. 为什么飘字不能每次命中都 Instantiate/Destroy？ Instantiate/Destroy 的代价不是“一个函数调用”，而是三笔账： 托管堆分配 + GC 尖刺：Instantiate 会 new 出 GameObject/Component 托管包装，Destroy 后这些对象变成垃 圾；高频命中时分配速率飙升，GC 一触发就是帧尖刺。 原生层装配与层级登记：创建 Transform、RectTransform、CanvasRenderer、Text/TMP 组件，挂进父子链，注册到 Canvas 的批次/重建系统里；销毁时还要反注册、断引用。 UGUI 连坐：新对象激活/父级变化会让所在 Canvas 走 SyncTransform，甚至触发 Rebuild/Rebatch；如果飘字和主 UI 同 Canvas，一次命中可能让整屏 UI 跟着重算。 战斗命中是高频事件，以上成本会被“命中次数 × 同时飘字数”乘法放大。 对策 = 对象池：预创建 N 个飘字，借出时重父级、写内容、设位置、最后激活；归还时先禁用、再重父级回池、清数据。隐 藏优先用 CanvasGroup.alpha = 0 + blocksRaycasts = false，而不是 SetActive——SetActive 一样会触发层 级脏化和 SyncTransform，只是比 Instantiate 便宜，不是免费。 借还顺序（加分点）： 借出：先 SetParent 到目标层 → 更新文本/颜色/位置 → 最后 SetActive(true) 或 alpha 置 1。激活放在最后， 是因为激活会触发一次全 Canvas SyncTransform，万事俱备再激活只脏一次。 归还：先 SetActive(false) 或 alpha 置 0 → 再 SetParent 回池。先禁用再重父级，旧层级只脏一次；反过来会先 因父级变化脏一次，禁用时再脏一次。 补一句：池化后仍要注意隐藏方式。SetActive 开关在 UGUI 下仍有连坐成本；高频显隐优先用 CanvasGroup/禁用 Canvas 组件，而不是反复 SetActive。
Q5. UI 对象池的归还是“先禁用再重父级”还是反过来？ 归还：先禁用，再重父级。 借出：先重父级 → 更新数据 → 最后激活。 原因：每次父级变化都会让旧层级和新层级参与布局/同步计算。先禁用再重父级，旧层级只脏一次；先重父级再禁用，父级变 化脏一次，禁用又脏一次，等于两次。 借出时最后激活，是因为激活会触发全 Canvas SyncTransform；把重父级、写文本、设位置都做完再激活，只脏一次。

Q3. 什么是 UGUI 的 Canvas 重建？为什么飘字会“连累”整个 UI？

UGUI 重建分两层：

C# 层 SendWillRenderCanvases：元素自身内容变化（文本、颜色、Sprite、Layout）触发 Rebuild，包括

Layout 重建和 Mesh 重建。

C++ 层 Canvas.BuildBatch（Rebatch）：任何元素顶点脏了，整个 Canvas 按深度/材质重新贪心合批。

关键：合批以 Canvas 为单位，对全部元素生效。一个飘字变字，同 Canvas 下几千个元素跟着重排/重批。再加上

SyncTransform：父级或自身 Transform 变化会让该层级参与同步。

三段流水线触发条件表（加分点）：

流水线 触发条件 代价

SendWillRenderCanvases 元素内容变化：text/color/sprite/layout

中～高，看元素数

Canvas.BuildBatch 任意元素顶点脏，整 Canvas 重批 高，随 Canvas 元素数上升

SyncTransform Transform/RectTransform 变化 低，但激活/父级变化会放大

二、为什么飘字场景特别在意字符串 因为飘字是高频 + 每次内容都不同的。 血条：数值变化频率低，偶尔一次 string 分配无所谓。 飘字：每次命中都要显示一个新数字，一秒可能几十次。 如果每次都写： tmpText.text = $"伤害{damage}"; 那么每次命中都会 damage.ToString() → 分配一个 string $"伤害{...}" 插值 → 再分配一个 string 赋值给 .text → TMP 内部再解析这个 string，生成字符和顶点 第 1、2 步是纯托管堆垃圾，跟渲染没关系，纯粹是“为了拼出这行字”产生的。高频命中下，这些垃圾快速堆积，GC 一触发 就是帧尖刺。 所以问题不在飘字本身，而在于“用字符串给飘字填内容”这个习惯。
三、那不用字符串，飘字怎么填内容 TMP 提供了绕过 string 的接口： // 不用 string，直接给字符数组 tmpText.SetCharArray(charArray, start, length); 于是链路变成： 旧：int → ToString() → string → 插值 → string → TMP 解析 → 字符/顶点 新：int → WriteInt() → char[] → SetCharArray → 字符/顶点 WriteInt 那段代码，就是“int → char[]”这一步的手动实现，替代 ToString()。 目标不是消灭字符串这个概念，而是消灭“每次飘字都 new 一个 string”这个分配行为。

Q18. “顶点数 <256 的网格不适合 GPU Instancing”——那 4 顶点的数字 quad 用 instancing 矛盾吗？ 不矛盾，因为手册警告的前提不适用。 Unity 手册的警告针对的是 单实例 GPU 吞吐：顶点太少，喂不满 GPU，单实例效率低。但飘字/图标的瓶颈在 CPU 侧提 交与 DrawCall 数，不在单实例 GPU 效率。 实测： 4 顶点 × 1 万实例 → 123FPS，GPU 完全无压力。 关键辨析： 手册结论有适用前提，教条套用会错过正确方案。飘字场景下，CPU 提交成本才是矛盾主要方面，GPU 吞吐是次 要方面。 加分点： 把这类“官方文档需要辨析前提”的意识扩展： 不要用“<256 结论”否定 UI instancing。 也不要用instancing 万能论”去合批 SRP Batcher 已搞定的场景。 核心： 看瓶颈在哪一侧，而不是背结论
