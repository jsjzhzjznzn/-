## 方案 5 的生产落地思路（完整链路）

1. **飘字管理器**：接收战斗飘字请求，按**类型（普通伤害 / 暴击 / 治疗）、生成时间**分组。同批次同类型的飘字

打包为一组，交给一个`UGUIFloatingTextBatch`实例。

2. **Mesh 对象池**：预先创建一批`UGUIFloatingTextBatch`，复用而不是动态实例化。设置全局最大 Mesh 数量上

限（做限流，保护微信小游戏内存）。

3. **分帧投递**：战斗瞬间爆发大量飘字时，分多帧入队，不要同一帧瞬间生成几十个 Mesh，避免卡顿尖峰。

4. 每组 Mesh 内部：统一运动曲线（向上飘 + 透明度淡出），组内所有飘字起点可以不一样，但速度 / 淡出时间统一；

5. 回收：Mesh 动画播放完毕，回收到对象池，清空文本列表，重置顶点数据，等待下一次复用

## 二、GPU Slider（GPU 血条）方案核心思想 **把所有血条打包到同一个 / 少数几个 Mesh，血条填充比例、颜色、位置、透明度全部放到 GPU Shader 里计算；CPU 只负责提交一份实例数据，不再逐血条做 UI 网格重建。** > 本质：血条不再是 UGUI 元素，而是**世界空间的面片（Quad）**，用 GPU Instancing 批量渲染。 > 一个 Quad = 一个血条面片，所有血条共享同一份 Mesh、同一份材质。
### 两种实现路线 ### 路线 A：GPU Instancing + MeshRenderer（最常用，兼顾开发成本与性能）
1. 准备一个基础血条 Quad Mesh（静态，固定 4 顶点）； 2. CPU 维护**实例数据缓冲区**：每个实例存储：怪物世界坐标、血条总宽度、当前血量比例、血条背景色 / 前景色、偏 移高度、是否显示等； 3. 每帧 CPU 只更新**实例数据数组**，传给材质的`MaterialPropertyBlock`或实例 Buffer； 4. Shader 内部：
- 用实例 ID 拿到对应怪物数据； - 把 Quad 顶点从模型空间变换到怪物头顶世界位置； - 在片元着色器里，根据**血量比例做裁剪 /alpha discard**，实现血条填充效果； - 计算屏幕空间偏移、Billboard（血条始终面向相机）； 5. 渲染：GPU Instancing 一次性渲染成千上万个血条实例，**只消耗 1 个 DrawCall**。 ✅ 优点
- DC 极低，上万血条依然 1~ 几个 DC； - CPU 不再逐血条更新 Transform，不需要 Mono 每帧跟随；CPU 仅更新实例数据数组； - 不依赖 UGUI，没有 Canvas Rebuild 开销； - 可以搭配对象池管理怪物逻辑，血条渲染完全剥离。
⚠️ 局限
- 实例数组有上限，需要预先分配；超出上限需要分多个 Instancing 批； - 屏幕外怪物，CPU 依然需要填充实例数据（可做 CPU 侧预剔除，不把不可见单位写入实例数组）； - 动态文本（血量数字）不能直接进这套方案，数字要单独处理（可以复用前面聊的**多 Mesh 飘字合批**方案搭配）； - 实例数据数组如果每帧 new 会产生 GC，需要**预分配数组，原地覆盖写入**。
### 路线 B：ECS + ECS Graphics（最高负载，几万～几十万单位，适合开放世界 / 大规模怪物群） > ECS Graphics（Unity DOTS）本质：彻底抛弃 GameObject + MonoBehaviour，用纯数据驱动。 1. 所有单位是 Entity，血条信息是 Component（血量、颜色、位置）； 2. ECS Graphics 直接把 Entity 数据作为实例 Buffer 送入 GPU； 3. JobSystem 多线程在 CPU 更新位置、血量；Burst 编译大幅降低 CPU 开销； 4. GPU Instancing 合批渲染，没有 GameObject/Transform 组件开销。
✅ 优点 - 内存极致紧凑，没有对象头、组件额外内存； - Job+Burst 并行更新实例数据，能扛几十万单位； - 没有 Mono 的遍历开销。

DOTS Instance Shader（`DOTS_INSTANCING_ON`宏，`UNITY_ACCESS_DOTS_INSTANCED_PROP`）。 > 6. Spawn 限流：每帧最多生成 N 条飘字，压制瞬间爆发峰值。
# 通用必加优化（全部方案适用） 1. **实体池**：禁用频繁 Create/DestroyEntity，用`IsActive`组件标记，空闲实体复用 2. **Spawn 限流**：每帧最大生成 N 个飘字，抑制 AOE 瞬时峰值 3. **视锥剔除**：Simulation Job 提前剔除屏幕外飘字，不送入渲染阶段 4. **Burst 检查**：禁止托管类型，字符串一律 FixedString，查找表用 BlobAsset 5. 材质开启 GPU Instancing，否则 Entities Graphics 无法 BRG 合批
动画驱动：如果用 DOTween 等补间动画，每次初始化都有 GC 开销。有项目经验表明，直接在 Update 里用数学计算坐标 （如 Mathf.Lerp、贝塞尔曲线）代替 DOTween 来驱动飘字运动，性能更好且无 GC。 闭 Pixel Perfect 确实能解决很多 UI 卡顿问题，但它的作用机制是消除了“移动触发重建”这一环，而不是解决所有性能 问题。
为什么 Pixel Perfect 会导致卡顿 Pixel Perfect 开启后，Unity 会强制所有 UI 元素的顶点对齐到像素网格。这意味着每当飘字发生位移（哪怕只移动了 零点几个像素），引擎就需要重新计算它的顶点位置，把它“吸附”到最近的像素边缘。 飘字恰好是持续移动的元素，所以 Pixel Perfect 会让它每帧都触发顶点重建，进而导致整个飘字 Canvas 的网格被标 记为 dirty，触发 Canvas.SendWillRenderCanvases 开销。 但有一个反例需要注意 有开发者报告过一个看似相反的情况：在特定情况下，开启 Pixel Perfect 反而解决了 Canvas 首次加载时的大量资源 消耗问题。分析原因可能是开启后简化了部分 GPU 缓冲设置和布局重算。
