# 背包测试发放与挑战成绩防作弊方案

## 一、现状分析

### 1.1 背包测试发放（BagGrant）

`MessageHandler.HandleBagGrant` 只校验「已登录」，随后直接调用 `BagRepository.Grant` 按请求里的 `itemId` / `count` 发物品。任何登录玩家都能为自己刷出任意物品与任意数量，这是服务端权威性上的空洞。

调用方有两个，都是联调便利入口：

- `BagView.OnGrantClicked`：背包界面的「加物品」按钮，按配置表顺序循环发放。
- `ActivityBridge.GrantItem`：供热更 Lua 调用的测试发放。

### 1.2 挑战成绩上报（ScoreSubmit）

`LeaderboardHandler.HandleScoreSubmit` 的校验只有三条：已登录、挑战 ID 在白名单（1/2/3）、分数在 `[0, 1_000_000]`。分数由客户端给出，服务端没有任何事实可以交叉验证。

需要先说明一个与审计结论不同的事实：**客户端目前根本不发送成绩**。`ChallengeManager.Finish` 只把用时显示到 HUD，全工程 `SendScoreSubmit` 没有任何调用点（仅 `ClientNetworkManager` 保留 API）。因此该漏洞的实际影响面是「协议已开放、可用任意客户端伪造」，而不是「正常玩家会被冒名」。

## 二、设计

### 2.1 BagGrant：仅调试账号可用

服务端维护一个调试账号白名单，来源是环境变量 `CS_DEBUG_ACCOUNT_IDS`（逗号分隔的账号 ID，空表示**全部禁止**）。判断点在 `HandleBagGrant` 入口，位于已登录校验之后、解析请求之前：

- 不在白名单：直接回 `Success=false, Message="测试发放未开放"`，不读请求体、不碰数据库。
- 在白名单：行为与现在完全一致。

选择「默认全禁 + 环境显式开放」而不是「默认全开 + 环境关闭」，是因为漏配环境变量时应当失败在「功能不可用」，而不是失败在「人人可刷」。客户端两个入口保持不变，普通玩家点「加物品」只会得到提示。启动时把生效的白名单打印一次（只打数量与 ID，便于本机联调确认）。

### 2.2 挑战成绩：服务端开局记录 + 用时下界校验

`ScoreSubmitRequest` 增加 `run_id` 字段（字段号 3，`string`），服务端为每次挑战维护「本局开局事实」：

1. **开局**：客户端进入挑战场景时发送开局请求（复用现有的 `ChallengeStartRequest`，若不存在则新增 2305/2306），服务端在本会话上记录 `run_id`、`challenge_id`、开局时间戳，并对同一会话的重复开局做覆盖。
2. **上报**：`ScoreSubmit` 携带 `run_id`，服务端校验：
   - `run_id` 与本会话记录一致（一次性，用后立即失效，防重放）；
   - 挑战 ID 与本会话记录一致；
   - 服务端自算 `elapsed = now - startAt`，要求 `elapsed >= MinSettleMs`（低于 1 秒的结算视为异常）；
   - 上报分数不超过该耗时对应的服务端理论上限：对「用时型」榜（挑战 2/3 的分数是耗时或反耗时）直接以服务端 `elapsed` 为准入账，**不采用客户端数值**；对「积分型」榜（挑战 1）要求 `score <= elapsedMs` 的上界关系成立（每秒最多 1 分），超出即拒绝。
3. `run_id` 缺失或会话无开局记录：拒绝入账并提示「成绩缺少开局记录」。

这套约束的可信基础来自「服务端掌握开局时刻」：客户端即使伪造分数，也无法伪造出比真实经过时间更长的局。它对「改分数直接刷榜」有效，对「外挂加速游戏内时间」无效——后者要服务端校验战斗过程，属于战斗逻辑服务器化，不在本次范围。

「用时型」榜的服务端入账用 `elapsed` 而不是客户端字段，需要客户端在开局响应里拿到 `run_id` 并在结算时提交；由于客户端当前尚未做成绩上报，本次同步在 `ChallengeManager.Finish` 里补上「开局 → 结算上报」的最小链路，让排行榜真正有数据。

## 四、E2E 验收项

1. 未配置 `CS_DEBUG_ACCOUNT_IDS` 时，任何账号发 `BagGrant` 都返回「测试发放未开放」，且 `player_items` 无变化。
2. 配置白名单为账号 1 时，账号 1 的 `BagGrant` 正常发放，其它账号仍被拒。
3. 无开局直接上报成绩 → 拒绝并提示缺少开局记录。
4. 开局后立即（< 1 秒）上报 → 拒绝（疑似异常结算）。
5. 开局后等待正常耗时再上报合法分数 → 入账成功，排行榜可见。
6. 同一 `run_id` 重复上报 → 第二次被拒（一次性）。
7. 上报的 `challenge_id` 与开局记录不一致 → 拒绝。
8. 积分型榜（挑战 1）上报超过耗时上限的分数 → 拒绝。

## 五、风险

- **规则会改变现有联调习惯**：TestClient 的 `--score` 之前可直接刷榜，改后需要先发开局请求。TestClient 需同步改造为「开局 → 上报」两步，否则其成绩验证能力失效。
- **时钟来源**：服务端耗时用单调时钟（`Stopwatch`）而不是墙钟，避免系统改时间影响判定；跨进程重启后开局记录丢失，客户端需能接受「开局记录失效、本次成绩不入账」。
- **作弊边界**：本次只解决「伪造分数」；「外挂加速」与「服务端战斗模拟」不在范围内，需在文档与验收中明确。

## 六、实测结论（2026-11-09）

全部验收项通过（服务端编译 0 错误、客户端 refresh 0 错误）：

| 验收项 | 实测结果 |
|---|---|
| 未配置白名单时 BagGrant | `Success=False, "测试发放未开放"`，启动日志「CS_DEBUG_ACCOUNT_IDS 未配置，背包测试发放对所有账号关闭」 |
| 白名单 `CS_DEBUG_ACCOUNT_IDS=1` | 账号 1 发放成功（`已发放 1 个`），其它账号仍被拒 |
| 无开局直接上报 | `"成绩缺少有效开局记录"` |
| 开局后立即上报 | `"结算耗时异常，成绩不予记录"` |
| 开局等待后上报 | 入账成功，排行榜可查 |
| 同一 runId 重复上报 | 第二次 `"成绩缺少有效开局记录"`（一次性消费生效） |
| challengeId 与开局不一致 | `"挑战ID与开局记录不一致"` |
| 积分型榜超上限分数 | `"成绩超出玩法上限，不予记录"` |
| 击杀竞速榜分数覆盖 | 上报 1 分，实际入账 2514（= 服务端耗时），客户端数值被忽略 |
| TestClient `--score 90` | 开局 → 上报 → 回执「新纪录！当前排名 3」，全链路可用 |

实现落地时补充的三点事实：

- 迷雾信标（挑战 3）是**积分型**榜（评级×100 + 剩余回合 + 探索百分比），原本就有真实上报调用点 `FogHuntGame.SubmitScore`，因此按积分型处理并在 `StartGame` 补开局登记；只有击杀竞速（挑战 2）是纯用时型。
- 挑战场景 `ChallengeManager` 原本只显示用时、**从不发送成绩**，本次补了「开局 → 结算上报」链路，排行榜从此才有真实数据。
- **积分型榜只用玩法理论上限约束，不叠加按耗时的速率上限**：各玩法每秒得分差异极大（迷雾信标一局可达数万分，而挑战 1 的积分量级完全不同），任何统一的「每秒 N 分」都是拍脑袋值，会误杀正常玩家。挑战 1 在客户端已无玩法入口，仅作为榜单默认值与 Agent 查询目标保留。
