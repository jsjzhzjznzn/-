# 账号密码哈希与登录限流方案

## 一、现状分析

服务端 `AccountRepository` 的两条账号路径都是明文密码：

```sql
-- 登录
SELECT Id FROM accounts WHERE Account = @Account AND Password = @Password
-- 注册
INSERT INTO accounts (Account, Password) VALUES (@Account, @Password)
```

`accounts` 表（`Migrations/001_InitAccounts.sql`）只有一列 `Password VARCHAR(128)`，库里存的就是玩家原始密码。这带来三个问题：

1. **拖库即全损**：数据库一旦泄露，所有玩家密码直接可用，且玩家在别处复用同一密码的账号一并沦陷（撞库）。
2. **日志与备份面**：任何带 `SELECT *` 的备份、慢查询日志都可能记录明文密码。
3. **登录无限流**：`MessageHandler.HandleLogin` 是裸调用，每会话只有 20 帧/秒的通用令牌桶（`ClientSession.RequestRatePerSecond`）。对登录接口而言这个额度足以做在线暴破——每次尝试的成本只有一次 `accounts` 索引查询。

客户端侧不受影响：`LoginRequest.Password` 协议字段不变，客户端仍然提交明文密码（TLS 之外由部署层承担传输安全，本次不改）。

## 二、设计

### 2.1 密码存储：PBKDF2 + 每账号随机盐

采用 `Rfc2898DeriveBytes`（PBKDF2-HMAC-SHA256，.NET 8 内置，无新增依赖）：

| 参数 | 取值 | 说明 |
|---|---|---|
| 盐 | 16 字节 `RandomNumberGenerator.Fill` | 每账号独立，注册时生成 |
| 迭代次数 | 210,000 | OWASP 2023 对 PBKDF2-HMAC-SHA256 的推荐下限 |
| 派生长度 | 32 字节 | |
| 存储 | `Salt`、`PasswordHash` 两列，均存 Base64 | `PasswordHash CHAR(44)`、`Salt CHAR(24)` |

选 PBKDF2 而不是 bcrypt/Argon2 的理由：项目已有 .NET 8 运行时，`Rfc2898DeriveBytes.Pbkdf2` 是内置 API；bcrypt 需引入第三方包，Argon2 在 .NET 无官方实现。PBKDF2 配 21 万次迭代属于可接受强度，且实现零依赖、可审计。

### 2.2 表结构与渐进迁移

`Migrations/022_AddPasswordHash.sql`：新增两个可空列，**保留 `Password` 列**。

```sql
ALTER TABLE accounts ADD COLUMN Salt CHAR(24) NULL, ADD COLUMN PasswordHash CHAR(44) NULL;
```

迁移是渐进的，不是一次性脚本改库：

- **新注册**：写入 `Salt` + `PasswordHash`，`Password` 写空串（非 NULL，保留列定义不变）。
- **老账号首次登录**：先按「有 `PasswordHash` 才走哈希」判断；没有则退化为与 `Password` 明文比较，比对成功后**当场把盐与哈希写回该行**，后续登录一律走哈希。
- **无需批量回填脚本**：老账号只要登录一次就完成升级；长期不登录的账号其明文密码也不会被登录路径使用。

之所以保留 `Password` 列而不立刻删除：现有 TestClient、自动化验证脚本与手工 SQL 都在依赖它，且回填尚未完成前删列会让老账号全部无法登录。回填完成后再单独做一次删列迁移。

### 2.3 定长时间比较

哈希比较使用 `CryptographicOperations.FixedTimeEquals`，避免逐字节早退泄露前导匹配长度。

对于**老账号的明文比较路径**，服务端取回该行的 `Password` 后在内存中与客户端提交值做定长比较（两侧转 UTF-8 字节后补齐到较长一侧再比），不使用 SQL 的 `Password = @Password`，避免把明文比较下推到数据库并让索引/执行计划泄露信息。

### 2.4 登录限流

在 `ClientSession` 上增加账号维度的失败计数（不动现有的每会话令牌桶）：

- 每次登录/令牌登录失败，`authFailures` 自增，并记录 `lastAuthFailureTimestamp`。
- 达到 `AuthFailureLimit = 5` 次后，进入 `AuthLockoutMs = 60_000` 的冷却窗口；窗口内任何登录请求直接返回「尝试次数过多，请稍后再试」，不查库。
- 冷却窗口结束自动清零；**成功登录立即清零**。
- 计数挂在会话上而不是账号上：换会话即重来。这是单进程架构下的取舍——账号维度的全局封锁需要跨会话共享状态（Valkey），属于分服阶段的事，本次不做，避免引入单点。

注册接口沿用同一套限流（`HandleRegister` 同样计数），因为注册也是每次一击数据库。

### 2.5 与附件方案的取舍

附件那套「鉴权服 + Gate 分离 + JWT 票据」属于多进程/多区服形态。本项目单进程、目标 1000 并发，拆 Gate 只增加一跳转发而不产生收益，因此本次只落地两件对当前架构直接有效的事：密码哈希与登录限流。Token 票据、一致性哈希选服、会话跨进程共享留到真正分服时再做。

## 四、E2E 验收项

1. 新账号注册后，库内 `PasswordHash`/`Salt` 非空、`Password` 为空串，用正确密码可登录。
2. 老明文账号（如 `test/123456`）用正确密码登录成功，且该行被自动回填 `PasswordHash`/`Salt`；再次登录仍成功。
3. 错误密码登录失败（错误码/文案与原来一致），且失败计数递增。
4. 同一会话连续 5 次错误密码后，第 6 次即使密码正确也被拒绝并提示「尝试次数过多」；等待冷却后再用正确密码可登录。
5. 成功登录一次后失败计数清零。
6. 不存在的账号登录失败，且响应文案与错误密码一致（不暴露账号是否存在）。
7. 重复注册同名账号仍返回「该账号已被注册」。
8. 自动登录令牌（`--token-login`）路径不受影响。

## 五、风险

- **性能**：21 万次 PBKDF2 在单次登录中约几十毫秒，属于可接受开销（登录是低频操作）；但它会让并发登录形成 CPU 尖峰，配合 2.4 的限流共同控制。
- **老账号路径**：明文比较分支在回填完成前一直存在，属临时状态；一旦全部回填完成即可删除该分支与 `Password` 列。
- **回填触发条件**：只有登录才触发回填，从不登录的账号会长期保留明文，需在运维侧安排一次「登录后回填覆盖率」检查。
